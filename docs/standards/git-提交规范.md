# Git 提交规范

代码、配置、基础设施和文档提交统一采用 Conventional Commits。提交信息描述本次改动产生的结果，提交内容围绕一个完整目的。

## 提交信息格式

```text
type(scope): 简短描述

必要时说明修改原因、关键影响和验证结果。

必要时添加关联任务或破坏性变更说明。
```

- `type` 使用下表中的英文小写类型。
- `scope` 使用英文小写模块或文档类别，通常填写；难以用单一范围概括的跨模块提交可以省略。scope 可以包含连字符，如 `api-client`。
- 描述可以使用中文，采用“增加、修复、调整、移除”等动词说明实际结果，保持单行简洁；避免只写“更新”“修改”或“完成任务”。
- 正文和页脚与标题之间留一个空行；简单变更可以只有标题。复杂变更在正文说明原因、影响和实际验证，任务关联可用 `Refs: #123`。

| 类型 | 使用场景 |
|---|---|
| `feat` | 新增功能或能力 |
| `fix` | 修复错误行为 |
| `docs` | 修改文档，包括 AGENTS.md、规范、设计和计划 |
| `refactor` | 调整代码结构，保持功能行为 |
| `perf` | 改善性能 |
| `test` | 增加或调整测试 |
| `build` | 修改构建、打包或依赖配置 |
| `ci` | 修改 CI 配置和自动化检查流程 |
| `chore` | 其他维护性变更，如忽略文件配置 |
| `revert` | 撤回已有提交；正文引用被撤回提交的 SHA 并说明原因 |

常用 scope 按改动对象选择：应用使用 `chat`、`admin`；公共包使用 `ui`、`api-client`、`shared`；后端和基础设施使用 `backend`、`rag`、`agent`、`workflow`、`infra` 等实际模块名。文档使用 `docs` 或更具体的 `agents`、`plan`、`architecture`、`standards`、`adr`、`reviews`。具体模块改名后以实际代码和目录为准。

```text
feat(chat): 增加会话历史查询
fix(rag): 修复检索权限过滤
docs(agents): 精简开发规范
docs(standards): 增加 Git 提交规范
refactor(api-client): 合并重复的请求处理逻辑
```

## 自动提交时机

用户已授权 Agent 在独立任务完成并验证通过后自动创建本地 Git 提交，无需逐次确认。该规则适用于功能、修复、重构、配置和文档任务；用户明确要求暂不提交时遵从。

- **每完成一项独立任务就提交。** 实现、必要测试和文档同步完成，相关检查实际通过后，立即创建提交，再开始下一项独立工作。长任务按可以独立验收的功能点或子任务分段提交。
- **验证通过才提交。** 业务代码执行相关测试及现有构建/类型检查等必要检查；纯文档执行链接、引用和示例检查。测试失败时先修复；必需检查因环境、依赖或输入缺失无法执行时，报告阻塞与剩余检查，保持本任务改动未提交，不将未验证结果标记为通过。
- **提交范围保持准确。** 任务开始时记录工作区与暂存区状态；只提交本任务拥有的改动，保留用户或其他任务的未提交、已暂存内容。存在其他暂存内容时，先确保本次提交与其隔离；无法可靠区分时说明范围阻塞。
- **初始提交包含必要依赖。** 尚无提交历史时，按已授权任务范围核对并纳入必要项目文件，形成可独立理解、引用完整的初始基线；未知或无关文件保持原状。
- **提交信息写清结果。** 标题按 Conventional Commits 描述本次实际行为变化；涉及多项关联调整时，正文列明关键改动与实际验证结果。有关联 Task/Issue 时填写真实标识，便于从提交回溯到实施任务。
- **提交后确认并报告。** 核对实际生成的提交及剩余工作区状态，交付说明包含提交 Hash、标题和验证结果。提交失败时报告实际错误与恢复所需条件，保持改动，不将失败记为已提交；没有实际改动时不创建空提交。

自动提交的授权范围是本地提交；远程推送按用户明确授权执行。

## 提交粒度

- 一次提交解决一个完整问题，使改动可以独立理解、验证和撤回。
- 实现及其必要测试、配置、生成制品和文档同步可放在同一提交，避免拆成依赖缺失的中间状态。
- 无关修复、大范围格式化和独立重构分别提交；多模块共同完成同一功能时，可以放在同一提交。
- 提交内容以暂存区为准，逐项核对文件与差异，只纳入本次任务的改动，保留其他工作区内容。

## 提交前检查

1. 使用 `git status --short` 确认改动范围，查看实际文件内容和差异，核对新增文件是否完整。
2. 按 [AGENTS.md](../../AGENTS.md)、相关开发规范与版本验收计划执行本次改动需要的检查。前后端命令从实际配置和 CI 获取；公共包或 API 变更覆盖受影响消费者。
3. 明确选择要提交的文件，使用 `git diff --cached` 审查完整暂存差异，并运行 `git diff --cached --check` 检查空白错误和冲突标记；将拟用提交信息传入 `pnpm exec commitlint` 校验。完成条件：暂存内容准确，相关检查通过，提交信息与实际改动一致。

纯文档改动检查本地链接、引用和示例；业务代码按现有验证入口执行，不为文档改动补造业务测试。验证结果如实记录，受限或未执行的检查说明原因。

以下是提交本规范及其阅读入口的命令示例：

```bash
git add -- AGENTS.md docs/README.md docs/standards/git-提交规范.md
git diff --cached
git diff --cached --check
git commit -m "docs(standards): 增加 Git 提交规范与阅读入口"
```

## 破坏性变更

不兼容的 API、数据、配置或行为变更在标题的类型或 scope 后添加 `!`，并在页脚使用 `BREAKING CHANGE:` 说明不兼容行为、受影响消费者和迁移方式。此标记适用于所有提交类型。

下面仅示意提交信息格式，具体变更按实际契约填写：

```text
feat(api-client)!: 调整客户端返回结构

BREAKING CHANGE: 返回值由响应包装对象改为业务数据对象，调用方需调整结果读取方式；发布前完成消费者适配和兼容验证。
```

契约变更及既有决策的调整沿用 AGENTS.md 的决策与兼容规则。

## 自动校验状态

Agent 在开发任务中按“自动提交时机”主动执行检查与本地提交。工程已提供 commitlint 配置与 CLI，CI 工作流会校验新增提交信息；本地尚未配置 Husky。格式校验与实际差异审查共同执行，自动提交时机按本规范控制。
