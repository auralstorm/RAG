# 前端代码规范

日期：2026-11-24。适用于 Chat、Admin 两个前端应用及前端公共包。本文维护组件、Hook、状态、交互与验证规则；具体依赖版本、脚本和命令在实际源码仓维护。

工程组织依据 [ADR-0014](../adr/0014-monorepo-and-independent-frontend-apps.md) 和 [V1.0 代码结构](../plan/V1.0-MVP/05-code-structure-and-backlog.md)；API 字段、状态、事件与权限依据 [统一契约](../architecture/统一契约与跨版本演进规则.md)。本规范按目标版本实现相关行为，后续 Agent/Workflow 能力不自动成为 V1.0 交付范围。

## 1. 技术基线与初始化冻结项

| 类别 | 当前要求 |
|---|---|
| 工程 | Monorepo；Chat/Admin 两个独立应用，共用后端 API，分别启动、构建和部署 |
| 前端基础 | Vite + React + TypeScript；pnpm workspace 管理应用和公共包 |
| 代码检查 | TypeScript 严格检查、ESLint、Prettier；配置和依赖版本按实际 Vite 工程锁定 |
| 组件方案 | 优先评估此前讨论的 Ant Design、ProComponents、Ant Design X 组合；初始化时落实依赖、版本和主题适配 |
| 路由、请求缓存、状态库 | 初始化时选定实际需要的方案并记录职责；React Router/TanStack Router、TanStack Query、Zustand/Redux、Axios 等不是本规范已经冻结的必选依赖 |
| 样式与测试工具 | 业务样式建议 CSS Modules；组件库主题沿用其正式机制；测试工具在初始化时按检查场景冻结 |

初始化任务记录所选工具、版本、配置与验证入口；选定后应用和公共包沿用同一基线。已有配置与锁文件优先核验，不依据文档中的候选名称重复引入同类依赖。

- 一个 Feature 可以包含列表、详情、编辑等多个页面；应用的 `routes/` 将具体页面挂到路由，不强制所有页面共用一个 `index.tsx`。
- Feature 私有组件、Hook、业务编排与视图类型保留在本 Feature；仅在一个应用内共享的能力保留在该应用内。
- 跨应用且职责稳定的组件、请求协议或工具进入对应公共包。原始 API DTO 使用生成类型或明确映射，Feature 的 `types.ts` 不复制一套后台字段定义。
- 应用依赖公共包，公共包不反向依赖应用，Chat/Admin 不直接导入彼此源码。包间依赖显式声明、保持无环，通过正式 exports 访问。
- 公共 UI 接收展示模型和回调；业务接口、知识库 ACL、审批规则及凭据解析由应用业务层和后端负责。
- 两个应用各自配置登录、API 地址和部署路径；共享包不硬编码应用域名，也不假定两个应用共用一份运行时状态或浏览器存储。

## 3. 组件拆分与页面职责

页面负责路由参数、当前用例的数据和交互编排，以及组合业务组件。业务组件承载独立业务块；基础 UI 提供可配置展示和受控交互。简单页面可以直接编写清晰的 JSX。

### 3.1 拆分判断

以下信号用于评估拆分，最终以职责和接口是否清楚判断：

1. UI 块具有明确的复用场景，或拥有独立交互、生命周期及变更原因。
2. 测试该业务块需要大量无关页面状态，表明职责可能混杂。
3. JSX 与逻辑超过约 120 行时检查职责；行数只是提示，不作为强制拆分或验收门槛。
4. 独立加载、错误边界或性能测量表明隔离该块有实际收益。

两三个简单标签、仅用于排版的片段可保留在原组件。拆分后若需要传递大量内部状态、形成多层转发，应重新调整状态归属或组件接口。

### 3.2 状态归属与受控组件

| 状态 | 推荐归属 |
|---|---|
| 列表数据、详情、任务状态 | 业务数据 Hook 与选定的服务端数据缓存层 |
| 筛选、分页、选中资源 | 最近公共父组件；需分享/返回恢复时按路由约定放 URL |
| 外部按钮控制的弹窗开关 | 按钮与弹窗的最近公共父组件，通过 open/onClose 控制 |
| 表单草稿、局部展开、悬停 | 使用该状态的组件或最近公共父组件 |
| 应用级主题等跨页面状态 | 明确的应用 Provider/store；仅有实际需求时建立 |
| 可由当前 props/state 计算的值 | 渲染时派生，不用另一份 state/useEffect 同步 |

业务数据有一个明确事实来源。组件通过回调通知拥有者，按不可变方式更新；不直接修改 props、缓存对象或父组件状态。受控组件以传入值为准，内部只保留不重复的临时 UI 状态；切换编辑对象时按资源 ID 明确重置或保留草稿策略。

### 3.3 权限与受控弹窗示例

以下仅说明页面编排，假定 Hook 与组件由当前 Feature 提供；权限 Hook 表达当前资源的交互能力，后端仍执行上传授权。示例不定义新的 API 字段或组件库选型。

```tsx
import { useState } from 'react';
import { DocUploadModal } from '../components/DocUploadModal';
import { KnowledgeTable } from '../components/KnowledgeTable';
import { useKnowledgeDocuments } from '../hooks/useKnowledgeDocuments';
import { useKnowledgePermissions } from '../hooks/useKnowledgePermissions';

interface KnowledgeBaseDetailPageProps {
  knowledgeBaseId: string;
}

export function KnowledgeBaseDetailPage({
  knowledgeBaseId,
}: KnowledgeBaseDetailPageProps) {
  const { items, isLoading, error, refresh } =
    useKnowledgeDocuments(knowledgeBaseId);
  const { canUpload } = useKnowledgePermissions(knowledgeBaseId);
  const [isUploadOpen, setUploadOpen] = useState(false);

  function handleOpenUpload() {
    if (canUpload) setUploadOpen(true);
  }

  function handleUploadSuccess() {
    setUploadOpen(false);
    refresh();
  }

  return (
    <section>
      {error ? <p role="alert">文档加载失败，请重试。</p> : null}
      <KnowledgeTable items={items} isLoading={isLoading} />
      {canUpload ? (
        <>
          <button type="button" onClick={handleOpenUpload}>上传文档</button>
          <DocUploadModal
            knowledgeBaseId={knowledgeBaseId}
            open={isUploadOpen}
            onClose={() => setUploadOpen(false)}
            onSuccess={handleUploadSuccess}
          />
        </>
      ) : null}
    </section>
  );
}
```

数据 Hook 处理请求错误与过期响应，refresh 的失败进入可展示的错误状态；路由切换资源时按资源 ID 重置该页面的局部状态。权限撤销后弹窗不继续显示，提交时仍由后端重新授权。

## 4. TypeScript、Hook 与组件编写

- 使用函数组件。组件类型在模块顶层定义，不在另一个组件内创建新的组件类型，避免重挂载、失焦与状态丢失。
- Props 只读并有明确类型；复杂接口单独声明 interface/type，简单接口可就近声明。外部未知数据先使用 unknown，再经实际 Schema/校验缩窄，不用 any 或类型断言绕过契约。
- 自定义能力使用 is/has/can 等布尔命名，回调使用 onXxx、处理函数使用 handleXxx。复用组件库的 open、loading、disabled、value 等正式属性名，不为命名风格改写其 API。
- Hook 按 React 规则在顶层调用；业务请求通过本 Feature 的 Hook 和公共客户端完成，组件不各自创建请求实例、刷新凭证或重复实现错误处理。
- useEffect 用于与外部系统同步，依赖保持完整并清理订阅、定时器和连接。用户提交逻辑放事件处理器，纯派生值在渲染时计算；禁止用空依赖规避检查或默认阻止重复 effect 掩盖资源清理错误。
- useMemo/useCallback 根据测量、memo 消费者或确需稳定的依赖使用，不为简单计算或所有函数默认添加缓存。高频更新使用函数式状态更新，避免读取旧闭包中的累积消息。
- 渲染列表均提供稳定资源 ID/事件 ID 等 key；仅有明确静态顺序且不依赖项状态时才评估 index，不在动态列表中生成随机 key。
- 条件明确为 boolean 时可使用 `condition && <Component />`；数量、长度等使用 `count > 0 ? <Component /> : null` 或显式布尔判断，避免页面出现 0/NaN。
- 组件与 Hook 使用命名导出；路由懒加载需要 default 时按已选路由约定配置或做显式映射。公共包提供明确 exports/必要子路径，不将全部业务组件通过大范围 export * 聚合。
- 导入按 React、第三方库、公共包、应用/Feature、类型等约定组织；使用 type-only import。遵循库的正式 exports，不深导入未公开且没有类型支持的内部路径。

## 5. 请求、服务端状态与权限

公共 `api-client` 负责平台 DTO/生成类型、认证请求、错误归一、幂等参数及适用流式协议；Feature 的 api.ts/Hook 负责用例组合与页面数据映射。请求缓存库和全局状态库各自职责在初始化时记录，同一数据不在多处维护独立权威副本。

- 沿用 [V1.0 API](../plan/V1.0-MVP/03-database-and-api-design.md) 的 `/api/v1`、UTC、分页及错误 Envelope；识别 `error.code`、message、request_id、retryable。界面显示可理解的原因和必要 Request/Trace ID，原始 details 按权限脱敏。
- 请求和缓存按当前身份、资源及适用组织/Workspace 范围区分。登录主体、权限或协作范围变化后清理/重新验证相关数据，缺少必需身份时不请求受保护内容。
- 页面卸载、资源/筛选变化时取消不再需要的请求或丢弃旧响应，旧请求不能覆盖新资源数据。重复刷新可由选定数据层去重；独立请求按依赖关系并发，不以 useEffect 链构造无必要的瀑布。
- 401 进入已实现的登录/刷新流程，避免多个请求各自无限刷新；403 显示权限不足，不自动重试或凭缓存继续展示已撤权内容。冲突、过期与版本不一致按契约回查。
- 前端权限控制可见性和交互，后端执行当前主体、角色及资源授权。按钮隐藏、只读表单、模型输出和客户端缓存都不能授予访问或执行权。
- 已有幂等写入按同一操作复用 Idempotency-Key，重试保持原输入/绑定版本；新的操作使用新 Key。禁用按钮只能改善交互，不能代替服务端幂等；未知结果先回查，不盲目重放。

## 6. Chat、Agent 与 Workflow 交互

### 6.1 流式请求与连接生命周期

流式传输在公共协议 Adapter 统一解析，组件消费消息/业务状态。具体路由、鉴权、事件版本、游标及补拉方式沿用目标版本契约；POST 流式请求使用支持其方法与认证的客户端，不能假定原生 EventSource 支持 POST 或任意认证头。

- 使用支持分段字节/事件边界的正式解析器与增量解码，不能把单个网络 chunk 当作完整 JSON/SSE 事件。
- 连接、请求和更新绑定 conversation_id/message_id/run_id/instance_id 等适用资源及本次执行标识。切换会话、卸载或启动新请求时清理旧连接并阻止迟到事件写入当前界面。
- 协议提供 event_id/sequence 时按资源去重、保持顺序，缺口按正式协议补拉；补拉游标只推进到连续处理位置，不因收到一个较大序号跳过遗漏事件。
- V1.1 Run、V1.4 Workflow 按统一契约的持久事件/游标恢复。V1.0 接口若未提供可恢复游标，应明确展示中断并回查已保存消息，不承诺不存在的自动续流能力。
- 重连沿用原资源 ID、游标和操作 Key，不自动创建第二个 Run/Workflow。重试有界，登录失效/权限拒绝按错误规则处理。
- 关闭读取连接或 AbortController 只表示客户端停止接收；取消执行调用已定义的服务端取消接口并等待状态确认。取消请求未闭合时展示“取消处理中”，不直接认定任务或外部动作已撤销。

### 6.2 状态、内容与可用性

Run 的公共 status、execution_phase 和 UI 文案分别映射，不把“生成中/人工处理中”等展示词写回公共枚举。已提交、审批中、外部写入中、结果不确定、确认成功分别展示；仅依据服务端确认事实显示成功。详见 [统一契约第 4/10 节](../architecture/统一契约与跨版本演进规则.md) 和 [V1.4 交互设计](../plan/V1.4-Enterprise-Workflow-and-Integration/05-chat-admin-workflow-and-connector-ux.md)。

- 模型生成内容及流式 Markdown 视为不可信输入；原始 HTML 默认关闭，需要扩展时走明确的净化规则，链接按允许协议和正式资源访问规则处理。
- 来源、附件、报告与外部结果链接由后端鉴权后提供；不从模型文本推导资源访问权，也不将对象 Key 当公开 URL。资源撤权后重新验证来源访问。
- 展示授权的业务步骤、工具摘要、引用、Token/费用及等待原因；不展示模型隐藏思维链、凭据、未授权参数或敏感 Trace 正文。
- Vite 的 VITE_* 配置会进入客户端产物，只保存公开环境配置；模型/Connector 密钥由后端保管，不写入前端配置、日志、存储或包产物。
- 表单、加载/空态、错误、权限不足、断线、未知结果和部分完成均有明确提示。交互保留键盘访问、焦点管理、表单标签与错误关联；流式播报按增量节奏处理，避免每个 Token 重复朗读全文。

## 7. 组件库、主题与性能

### 7.1 组件与样式分工

采用此前讨论的推荐组合时，Ant Design 承担通用控件，ProComponents 用于适合的 Admin 表格/表单/布局，Ant Design X 用于 Chat 对话交互。版本、Provider、React 兼容及依赖关系在初始化验证后落地；这些组件不改变平台的鉴权、流式协议或审批契约。

已有 Button、Input、Modal、Table 等基础能力优先直接复用组件库；只有统一主题、无障碍、交互或多个消费方存在稳定需求时才建立公共封装。业务感知组件保留在 Feature，公共 UI 不请求知识库、模型或审批接口。

组件库外观使用其正式主题 Token/Provider，业务布局与局部样式建议 CSS Modules。初始化时记录实际样式基线；不为单个页面随意叠加另一套全局样式方案。动态尺寸/位置可使用必要的行内样式，全局覆盖需限定范围并验证两个应用。

### 7.2 性能边界

- 根据实际消息量、Trace 节点、文档/表格行数决定分页、窗口化或虚拟化，保持稳定 key、滚动位置和流式更新行为。
- 编辑器、文档预览、图表/Trace 可视化等重模块按路由或使用时懒加载；Vite 应用使用 React.lazy/import() 或所选路由机制，提供加载和失败状态。
- 流式增量可按可解释节奏合并渲染，避免每个 Token 触发全应用重渲染；输入响应、取消与最终内容完整性仍须验证。
- 优化依据 React Profiler、浏览器测量和真实负载；memo、动态加载或窗口化变更同时验证状态、焦点、错误和断线行为。

## 8. 命名、工程检查与交付

组件/Page/类型使用 PascalCase，Hook 使用 use 开头的 camelCase，变量/函数使用 camelCase，常量使用 UPPER_SNAKE_CASE，业务目录统一 kebab-case。示例采用 knowledge-bases 等既有模块名，命名以源码仓统一约定为准。

ESLint 以实际 Vite + TypeScript 工程为基础，使用与已锁定版本匹配的配置，统一 Hooks、依赖、未使用变量和类型检查；初始化时优先采用现代 flat config。Prettier 统一格式，规则在 workspace 共享。新增 ESLint 预设需验证兼容性，不默认引入 CRA/Airbnb 配置；自动生成的客户端与业务代码分别执行适用检查。

测试依据实际行为风险选择：组件/Hook 测试可就近放 `.test.tsx/.test.ts`，跨应用和端到端场景按源码仓测试目录管理。Vitest、React Testing Library、Playwright 等作为初始化候选，选定后使用真实配置；不为纯展示封装或每个组件强制增加重复测试。

| 变更 | 至少验证的实际场景 |
|---|---|
| 页面/表单 | 加载、空态、错误、校验、关键交互和适用权限 |
| 请求/状态 Hook | 资源切换、旧响应、取消/清理、错误和缓存范围 |
| 流式交互 | 分段解析、适用事件去重/补拉、断线、迟到事件、取消及最终内容 |
| 管理/审批动作 | 重复提交、当前权限、冲突/过期/未知结果，成功状态来自后端事实 |
