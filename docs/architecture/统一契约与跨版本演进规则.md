# 统一契约与跨版本演进规则

日期：2026-11-24。性质：单企业范围同步后的跨版本设计基线；实际代码、物理 DDL 和迁移结果须在实施阶段验证。

## 1. 权威范围与变更方式

- [总体版本路线图](../plan/总体版本路线图与架构演进规划.md) 负责产品版本、范围、依赖和验收；技术架构文档描述目标态及能力分层。
- 本文件是公共实体命名、兼容映射、状态、事件和权限动作的唯一设计解释源。版本详设描述本版增量及实现方式；摘要若与本文件不同，应同步修订，不能各自选择一套字段。
- 已批准 ADR 变更本文件时，必须同时更新受影响版本与验收。部署范围依据 [ADR-0013](../adr/0013-single-enterprise-deployment-scope.md)，运行契约方案记录于 [ADR-0007](../adr/0007-agent-runtime-incremental-contract.md)。
- 实施代码仓中的 OpenAPI 由统一 DTO/路由生成，JSON Schema 按对象维护，物理结构由 Alembic 迁移维护；三者分别版本化，并通过 CI Diff、契约测试和升级测试对应本文件。本目录新增的是设计权威，不能当作机器可执行制品已经交付。
- 每版 Phase 0/M0 的 Owner 是架构负责人，Backend/RAG/QA 负责相关制品与证据。任务关闭须有决策、契约制品、文档同步和兼容验证，创建目录不能替代验收。
- `schema_version` 统一为字符串：Definition 起点为 `"1.0"`；事件与其他对象分别维护版本。不得把产品版本、Definition 版本、事件版本和数据库 revision 混用。

## 2. 单一企业部署与企业内部授权

V1.0–V2.0 均采用单一企业内部独立部署，范围依据 [ADR-0013](../adr/0013-single-enterprise-deployment-scope.md)。部门、团队、用户组、KB 与 Workspace 表达企业内部成员及资源范围。

资源沿用稳定 ID、主体/Owner、父子关系和当前用户/角色/KB ACL。任何企业内跨部门、跨用户或跨 Workspace 的访问均由服务端显式授权；组织成员或 Workspace 成员身份不自动授予所有关联 KB、Agent、Workflow、工具或费用读取权限。

Redis Key、对象 Prefix 和任务资源使用部署实例 namespace 区分环境；缓存还包含有效授权摘要或按主体隔离，撤权后失效。ES 检索、来源查看、对象下载、Worker、评测和管理接口执行同一当前资源授权。

唯一约束按真实业务语义维护：Run 创建沿用非空主体/Agent/Key 约束，Agent Key 在本部署内唯一，外部 operation_key 保持稳定。普通版本升级继续采用明确兼容窗口、字段映射及数量/Hash 校验。

### 2.1 V1.0 平台主体与身份授权契约

P0-04-02 的 User 是稳定的逻辑平台主体，`AccessContext.subject_id` 与关联中的 `user_id` 指向其 ID。V1.0 admin_users/employees 的原 ID 继续作为 ADMIN_USER/EMPLOYEE 来源标识，经唯一 SubjectBinding 显式映射；同值 UUID 不代表同一主体，也不按显示名/email 自动合并。外部身份按 provider_key、精确 issuer、精确 subject 选择，关联必须已由可信登录流程核验。该逻辑契约不替代 P1-03 的物理 DDL 与迁移决策，不能凭本节重命名存量表或改 FK。

User 状态保留 ACTIVE、DISABLED、LOCKED、PENDING_DEPARTURE、DEPARTED，只有 ACTIVE 可用；ExternalIdentity 有 ACTIVE/DISABLED 状态。Role/Permission 与 UserRole/RolePermission 分离，固定系统角色代码 SUPER_ADMIN、KB_ADMIN、AUDIT_READONLY 必须受保护；角色标签不会自行产生操作权限或资源 Grant。Permission.code 使用 resource.action。ResourceGrant 保留 ADMIN_USER/EMPLOYEE/ROLE/GROUP，并允许 USER 明确引用规范 User.id；旧来源类型必须验证对应映射，缺失时拒绝，MANAGE 可读但 READ 不能管理。

AccessContext 是可信服务端生成的 subject_id、identity_id、伪名 actor_ref、environment、purpose、policy_version 与有效时间视图，不包含客户端可自授的角色/权限/KB 字段。AuthorizationSnapshot 从当前身份、操作权限、角色/组成员与 ACL 独立加载，身份归属、版本、用途、时间和资源关系均检查；缺失、歧义、停用、撤权或过期拒绝。PolicyDecision 绑定当次动作/主体/KB/Policy 版本，不是可重放凭据。请求关联 Context 与授权 Context 保持分离。

上述对象从独立 `schema_version="1.0"` 起维护，版本字段为字符串，未知版本拒绝。源码、公共/内部 Schema 分类和范围见 [身份与授权契约](../api/iam-policy-contracts.md)；内部身份键、关联与授权事实不进入前端类型或当前应用 OpenAPI。真实 OAuth/JWT、数据库约束、固定角色默认矩阵和 Policy→Retriever 集成仍按对应主线任务验证。

### 2.2 V1.0 知识资产、入库与索引版本契约

P0-04-03 将逻辑 Document 的 ACTIVE/DELETING/DELETED 生命周期与 DocumentVersion 的 UPLOADED→PARSING→PARSED→CHUNKING→EMBEDDING→INDEXING→INDEXED→PUBLISHED 处理状态分开。原件、Hash/大小/MIME、Parser、解析产物和 Chunking/Pipeline 固定在具体版本；最新版本不等于当前在线版本，失败的新版本不能使旧已发布版本失效。索引 Chunk 的 status=PUBLISHED 保留发布投影语义，不能由逻辑 Document 的 ACTIVE 自动推导。

DocumentVersionRef 明确 document_version_id、document_id、kb_id 和数值 document_version；存量 document_versions.id/version 及旧 Document.version/object_key 等设计在实施迁移时显式映射，不凭本节直接改列。IngestionJob 的 Key 绑定版本、pipeline、任务类型与目标阶段，跨阶段/重试不变；Stage Key 独立计算。Job 成功只表示固定处理目标完成，去重记录、事件序号、租约及实际持久恢复仍需数据库/Worker 证据。

IndexVersion 增加 READY 表达已验证未发布，ACTIVE 才表示已确认在线，ROLLED_BACK 表示可回滚的已发布历史。Embedding 的模型/config_version/dimensions 与 Chunking/Pipeline 都固定在 IndexVersion；Manifest 绑定单 KB、每个文档至多一个版本。验证报告绑定索引 ID、Manifest 与配置摘要，计数及 Mapping/ACL/检索/质量检查全部通过后才能准备发布；回滚查询恢复目标历史向量空间。

PublicationPlan 仅是包含原 Key、CAS 期望和 alias/绑定的执行意图，不表示数据库/ES 已修改；IndexPublication 由真实执行层在确认后记录。在线读取同时校验当前身份/KB ACL、文档及版本关系、活动 index/alias/Manifest 与当前文档 ACL，空限制集合拒绝所有，旧/缺 Policy 不默认继承。源码、公共/内部 Schema、状态与兼容映射见 [知识契约](../api/knowledge-contracts.md)；真实迁移、上传/解析、Worker、原子发布、对账与 Retriever 集成继续按 P2/P3 验收。

### 2.3 V1.0 解析、Chunk 与 Retriever 契约

P0-04-04 的 ParsedDocument/Chunk 复用 DocumentVersionRef；Parser 输出包含有序页面/块、明确格式的 SourceLocation、结构化表格与安全告警。PDF 保留真实页码及规范化坐标，Markdown 使用原文 Unicode 码点范围，DOCX 使用原始正文元素位置，不伪造分页。Chunk 的原文位置与 ParsedBlock.text 的半开切片范围分开；内容摘要、来源顺序、版本与父子范围关系均校验，SDK 原始对象和任意 metadata 不进入平台模型。

正式命名为 RetrievalRequest/Result，保留 query/kb_ids/filters/access_context/top_k/config_version/trace_id 和 chunks/diagnostics。客户端 RetrievalSelection 仅能选择业务范围，可信服务端构造 AccessContext 与当前 RetrievalFacts；当前 KB/文档 ACL、活动 index/alias/Manifest 与完整版本关系共同限定查询。空可读版本清单跳过搜索，显式越界资源拒绝；查询向量使用活动索引固定的 Embedding/Chunking/Pipeline，不用 KB 的期望新配置。

结果返回前以新加载事实重新校验原/current 范围、Trace/config/上限和活动索引，并与权威已发布 Chunk 的版本、内容及来源一致。搜索响应自报的 ID/正文不能作为权威验证证据；撤权、删除、来源伪造或索引切换拒绝结果。来源类型、公共/内部制品与原草案映射见 [解析与检索契约](../api/parsing-retrieval-contracts.md)。本轮纯规则和 Protocol 不代表 Docling、Tokenizer、实际 Retriever/ES 或数据库集成通过，继续按 P3/P4 验收。

### 2.4 V1.0 Provider、ModelConfig 与 Model Gateway 契约

P0-04-05 以 Provider/ModelConfig 固定注册标识、状态、能力/限制与配置版本。SecretReference 仅为私有不透明 ID/版本/环境引用，供应商端点、代理和 vendor_model_key 留在 StoredProvider/StoredModelConfig；公开模型不能包含明文 Key、密文、私有引用或供应商路由。旧 providers/models 表设计与已有 EmbeddingBinding 的显式映射见 [模型网关契约](../api/model-gateway-contracts.md)，本轮没有物理迁移。

ModelRequest/Response 按 Chat/Embedding/Rerank 载荷校验固定请求/Trace/模型/配置。Embedding 始终保持原向量空间；未知用量保留 null，Token/费用的供应商确认与估计来源分开。ModelFailure 仅有稳定代码、可重试/未知结果与安全用量；流事件保持单尝试的连续顺序、载荷和唯一终态，不代表持久化续流。

调用复用当前身份绑定，并由可信服务端策略提供模型/操作许可、当前注册、凭据环境、准入与绑定请求的 TokenMeasurement；身份校验本身不授予模型/KB 权限。当前禁用、撤权、过期、配置/能力/维度/预算不符拒绝。重试使用原请求/配置/Deadline 和原/current 较小尝试上限，未知结果或已开始输出拒绝重放；交付前再次验证当前身份与模型许可。实际 Secret、LiteLLM、限流/并发、Token 计量、网络/取消/重试和费用事实按 P2/POC-04 验收，纯规则与 Schema 不替代这些保证。

## 3. Agent Definition 与版本迁移

### 3.1 规范命名

V1.2 Agent DTO、领域清单和新增存储清单统一使用 `agent_key`、`owner_user_id`、`current_version_id`。current_version_id 只指当前生产可用版本，草稿有独立 ID。Owner 必须解析为平台用户；V1.0 的 admin_users/employees 与统一用户身份之间通过可信 Identity 映射适配，不能假定原 UUID 或主体类型相同。

旧 DTO 已有消费者时，`key`、`owner_id`、`current_published_version_id` 作为显式兼容别名保留一个已评审窗口；双字段不一致时拒绝写入，不静默覆盖。实际持久化列已经不同的，先建立映射与兼容迁移，不能因文档统一而直接改列。

### 3.2 V1.1→V1.2 转换表

| V1.1 | V1.2 目标 | 转换规则 |
|---|---|---|
| agent_key | agents.agent_key + agents.id | Key 保持稳定，生成/查找实体 ID；记录旧 definition ID 到新实体映射 |
| name / description | Agent 元数据及 definition.identity | 复制展示语义，不隐式改变业务范围 |
| owner_subject_id | owner_user_id | 经 Identity 映射解析；无法映射的记录进入人工处理，阻止该记录切换 |
| instruction_ref | prompt.prompt_version_id | 引用已固定 Prompt Version；旧文本建立不可变版本及来源 Hash |
| model_profile_id | model.model_profile_id | 固定或记录版本快照，Secret 仍为引用 |
| retriever_profile_id | knowledge[].retrieval_profile | 解析已授权 KB 范围，不能从 Retriever 名称推导新增权限 |
| allowed_tool_keys | tools[].tool_id | 通过既有 Tool Registry 查找 ID/版本，保持 Allowlist；无匹配工具时拒绝迁移该配置 |
| max_steps / timeout_seconds | runtime 对应字段 | 原值保留；迁移器不得自动放宽预算 |
| Token / max_cost 限额 | runtime.budget | 保留输入、输出、总 Token 和成本上限；未知成本上限按原策略处理 |
| config_version / config_json | agent_versions 快照及 legacy_config_version 元数据 | 每个旧快照对应确定版本；保留原始配置、Hash、来源版本及转换记录 |
| ACTIVE / DISABLED | agents.active / suspended | DISABLED 不能通过迁移自动恢复；旧版运行继续接受当前授权检查 |

V1.2 Definition `runtime.budget` 为受控预算对象：`max_input_tokens`、`max_output_tokens`、`max_total_tokens`、可选 `max_cost`。其他运行时字段仍沿用既有模板/超时限制。V1.1 配置是转换源，不宣称其平坦结构天然属于嵌套 JSON Schema 的子集。

V1.1 注册入口在兼容窗口作为 Registry Adapter 复用，Tool Catalog 复用原 Tool Registry 的查询与版本解析。新定义从 V1.2 Registry 管理；不得并行维护独立生产 Allowlist。历史 Run 保持启动时的 config_version，完成版本映射后增加 agent_version_id，不静默切换配置。

V1.3 新增 planning / execution / delegation / verification / human_in_the_loop 等可选扩展。V1.2 快照缺这些字段时使用原单 Agent 模板、不启用委派及高风险动作；新增能力显式生成新版本。迁移器保留原始 Definition，未知主版本默认拒绝，历史版本不静默重写。

### 3.3 Agent 与 Version 状态分离

Agent：`draft → active ↔ suspended → archived`；归档前校验活跃 Run 和资源引用，归档不能隐式破坏历史审计。

Version：`draft → validating → ready → published → superseded`；验证失败进入 `rejected`，修改产生新草稿；不得把 `INVALID`、Agent 的 suspended 或 archived 写入 Version 枚举。

发布/回滚用事务和 CAS 更新当前生产指针。回滚目标必须是经校验可用的历史快照；生命周期元数据可按发布事务更新，definition_json 和内容 Hash 不可修改。已启动 Run 继续绑定旧快照；授权撤销仍实时生效。

## 4. Agent Run、Step 与 Checkpoint

### 4.1 Run 持久化基线

V1.1 原字段持续保留：`id`、`agent_key`、`config_version`、可空 conversation_id、`requester_subject_id`、`status`、`idempotency_key`、`trace_id`、`input_ref`、`output_ref`、`budget_json`、`started_at`、`finished_at`、`error_code`、`created_at`、`updated_at`。

- requester_subject_id 是可信授权主体，principal_ref 仅为脱敏视图/观测引用，不能替换授权查询列。
- V1.2 增加 agent_id / agent_version_id；存量行完成映射前可空，新生产 Run 必须绑定有效发布快照，并保留兼容 config_version。
- V1.3 增加 goal_summary、execution_phase、waiting_reason、deadline_at、cancel_requested_at、total_steps、token_usage_json、cost_estimate、error_summary、original_run_id（终态纠错时的来源 Run 引用）。消耗指标不能代替 budget_json 上限。
- 所有持久化结束时间使用 finished_at；completed_at 是已有外部消费者需要时的显式兼容别名，不能直接重命名旧列。
- token_usage_json 为输入/输出/总 Token 的结构化用量；Trace/DTO 的 token_usage 映射到此结构。Run 的用量汇总必须涵盖恢复和子任务，不重置全局预算。

客户端创建 Run 使用 `Idempotency-Key`（旧 client_request_id 显式映射）；由可信层解析主体。单企业下唯一键为 `(requester_subject_id, agent_key, idempotency_key)`，三列必须非空。API 必须在接受请求时返回/记录最终 Key；缺 Key 的客户端可由网关首次生成，但客户端重试必须复用同一 Key。

同 Key、同请求摘要返回原 run_id/status；同 Key 不同 Agent Version 或输入摘要返回冲突。去重记录和 Run 创建同事务、数据库唯一约束防并发重复；Run 保留期内不删除去重键，清理后的去重窗口由部署配置明确。Step 去重和 Tool 副作用去重独立存在，不能替代 Run 创建去重。

请求使用 `agent_version=published` 等版本选择意图时，先按主体/Agent/Key 查去重记录；重试意图一致则复用首次解析的快照，不能因为当前发布指针变化而重新绑定版本。只有新 Key 才解析当前发布版本；同 Key 显式改版本或输入返回冲突。

### 4.2 公共状态与执行阶段

V1.1/V1.2 公共状态保留：QUEUED、ACCEPTED、RUNNING、WAITING_APPROVAL、WAITING_INPUT、CANCEL_REQUESTED、SUCCEEDED、FAILED、CANCELLED、TIMED_OUT。V1.3 显式增加 PAUSED，旧客户端未知状态应呈现不可执行等待状态并回查，不能自动恢复。

V1.3 的 INITIALIZING、PLANNING、PLAN_VALIDATING、EXECUTING、VERIFYING、SYNTHESIZING、REPLANNING、RETRYING 是 execution_phase，不替换公共 status。等待审批使用 WAITING_APPROVAL；等待澄清/复核使用 WAITING_INPUT，并记录 waiting_reason；主动暂停使用 PAUSED。`WAITING_FOR_HUMAN` 是 UI 聚合名称，不写入 Run 枚举。

典型迁移：QUEUED → ACCEPTED → RUNNING → SUCCEEDED/FAILED/TIMED_OUT；RUNNING → WAITING_APPROVAL/WAITING_INPUT/PAUSED → RUNNING；活动状态 → CANCEL_REQUESTED → CANCELLED。终态纠错使用新 Run 关联 original_run_id，不直接恢复终态。若采用 Resume Attempt，则它是同一非终态 Run 的执行尝试，不能绕过终态规则。

### 4.3 Step 与 Checkpoint 增量

- Step 保留 V1.1 的 sequence_no、node_key、step_type、状态、attempt、摘要、error_code、latency_ms、token_usage_json、started_at/finished_at。V1.3 增加可空 task_id、capability_ref、input_hash、output_ref、idempotency_key 和 cost_estimate；sequence_no 仍是 Run 内唯一单调序号，不能改成 Task 内重复 step_index。
- Checkpoint 保留 checkpoint_seq、schema_version、checkpoint_ref、agent_config_version、created_at、expires_at、deleted_at。V1.2 增加 agent_version_id，V1.3 增加 state_hash 和 status；state_ref 是 checkpoint_ref 的内部适配名称。版本和 TTL 不能因新清单漏列而删除。
- 新 Plan/Task/Handoff/HumanInteraction/Artifact 表可以独立建立；复用 Run/Step/Checkpoint。恢复必须验证快照完整性、有效授权和剩余预算；外部提交状态未知时核对或补偿，不盲目重放。

### 4.4 运行 API 与事件兼容

| 接口 | 演进规则 |
|---|---|
| POST /api/v1/agents/{agent_key}/runs | V1.1 兼容入口保留，由 Registry Key Resolver 映射到确定 Agent/Version |
| POST /api/v1/agent-runs | V1.3 新入口；与旧入口调用同一 Run Service 和幂等约束 |
| GET /api/v1/agent-runs/{run_id}/events | 保留 V1.1 SSE 默认行为；显式 Accept: application/json 可按 after_seq 分页补拉，响应类型写入 OpenAPI |
| GET /api/v1/agent-runs/{run_id}/stream | SSE 兼容传输入口，与 events 使用同一持久化序列 |
| POST .../{run_id}/approval-result | V1.1 内部回调保留，转换为同一审批决定服务，不能绕过角色/动作绑定检查 |

Run 事件保持公共类型 run.accepted、run.started、run.waiting_approval、run.waiting_input、run.completed、run.failed、run.cancelled；V1.3 增加 run.paused/run.resumed 和 Plan/Task/Delegation/Evidence 等事件。数据库 sequence_no → SSE sequence；sequence 字段与 schema_version 的旧消费者保持兼容。

## 5. 人工介入与 Approval Contract

V1.1 冻结最小请求/决定协议，由现有外部审批方或受控 Mock 提供决定；V1.3 以 human_interactions 持久化人工交互并适配原回调；V1.4 企业审批流程引用相同 approval_id/decision_id，增加审批人分配、升级、撤回等流程实体。

| 对象 | 最小字段及约束 |
|---|---|
| ApprovalRequest | approval_id、run_id、step_id、requested_action、target_resource、parameter_hash、input_summary、risk_level、policy_decision_ref、approver_role、expires_at、idempotency_key、status |
| ApprovalDecision | decision_id、approval_id、decision（approved/rejected/expired/cancelled）、decision_reason、decided_by、decided_at、parameter_hash |

请求初始 status=pending；决定写入后转 approved/rejected/expired/cancelled，状态和执行成功不等同。V1.1 可靠保存 approval_id、参数绑定及可信外部记录/审计引用，暂停恢复不能只依赖临时消息。V1.3 human_interactions.id 作为 approval_id（仅 interaction_type=approval），通过保留旧 ID 或明确映射承接原审批；DTO approver_role 对应存储 required_role。请求与决定语义分离，可采用同表结果列及追加审计保存。独立流程表允许新增，不能另建平行的审批 ID 空间。

决定前验证审批人、范围、未过期请求及当前参数 Hash；同一 decision_id 重放返回既有结果，不重复唤醒。一次性 Approval Token 绑定 Run/Step/Tool/参数 Hash/资源/有效期，消费与执行幂等协调；参数或有效权限变化时审批失效。澄清和复核不签发高风险动作 Approval Token。

## 6. Evaluation 统一字段与迁移

### 6.1 规范字段

Run 使用 target_type/target_snapshot、agent_id/agent_version_id（RAG-only 评测可空）、dataset_version_id、profile_version_id、status、initiator_id、started_at/finished_at、summary_metrics、report_object_key、trace_group_id。Result 使用 evaluation_run_id、case_id、actual_output、citations、tool_calls、policy_decisions、metric_scores、assertion_results、latency_ms、input_tokens、output_tokens、estimated_cost、failure_category、trace_id。

DTO report_uri 是鉴权后从 report_object_key 解析的限时访问地址，不另存永久公开 URL；Token 总量由分项与供应商口径计算并记录统计版本。旧 evaluation_profile_version_id→profile_version_id、latency→latency_ms、token_usage→分项结构都须明确单位和序列化兼容，不能猜测旧值单位。

### 6.2 V1.0→V1.2→V1.3

| V1.0 数据 | V1.2 目标 | 保留方式 |
|---|---|---|
| eval_datasets / version | evaluation_datasets + evaluation_dataset_versions | 固定原样本和版本；保留旧 ID 到新 ID 映射 |
| eval_cases.dataset_id | evaluation_cases.dataset_version_id | 解析所属历史版本，question→输入，expected_answer/ground_truth_refs→参考答案/证据断言 |
| eval_runs.dataset_id / rag_config_version / index_version_refs | evaluation_runs + target_snapshot（JSON 元数据） | target_type=rag；固定 RAG/索引快照，无 Agent 的历史记录不得填造 agent_version_id |
| eval_case_results | evaluation_results | 保留指标、错误和来源版本；旧报告不可覆盖，无法比较的指标显式标记 |

V1.2 评测对象至少区分 rag / agent；Agent Gate 只消费匹配 Agent Version 的报告。新增版本化 Evaluation Profile 固定指标/评分器/阈值/Judge 配置；缺少历史评分器版本的记录标记不可严格复现，不能补造已知版本。

V1.0→V1.2 迁移采用兼容读写、数量/Hash 校验和旧接口 Adapter。V1.3 复用 Dataset/Run/Result，仅增加 plan/execution/evidence/collaboration/safety/cost 指标；不新建一套平行评测数据库或发布门禁。

### 6.3 评分器与优先级

保持现有技术基线：RAGAS Adapter 承担适用的 RAG 语义指标，确定性 Scorer 承担引用、参数、Policy 和任务断言，其他 Judge/Scorer 按指标扩展。RAGAS 具体版本和适用指标由 POC 冻结，不在本轮替换选型。

- V1.0 最小 Golden Dataset、基础检索/回答/引用评测和回归门禁是 P0 必交付；复杂实验和额外指标可列 P1。
- V1.2 至少一种语义评分方式及适用的 RAGAS Adapter 接入为 P0；其余 Judge、校准和指标扩展可列 P1。每项门禁固定 metric/scorer/version/threshold/dataset；必选评分器失败或未执行时不得把样本记为通过。
- 安全硬门禁使用确定性断言与授权结果；语义 Judge 不能单独证明安全。RAGAS 与确定性 Scorer 覆盖不同职责，不能按名称重复对同一指标维护两套默认权威分数。

## 7. 管理动作、权限与事件字典

### 7.1 动作到权限

| API 动作 | Policy Action | 资源 Permission | 额外条件 |
|---|---|---|---|
| 创建 Agent | agent.create | 既有组织级创建授权 | 有创建角色及合法归属；不能从单个 Agent 权限推导组织创建权 |
| 编辑/草稿/复制/归档 | agent.edit / agent.archive | edit | 资源归属、引用和并发检查；复制还要求创建权 |
| Playground / 评测 | agent.test / agent.evaluate | test / evaluate | 受控测试身份、Sandbox、资源授权与配额 |
| 发布 | agent.publish | publish | Schema、资源、评分器和 Gate 全部通过 |
| 回滚/暂停/恢复 | agent.rollback / agent.suspend / agent.resume | operate | 历史目标校验或当前状态检查，理由、并发控制及审计 |
| 查看敏感运行信息 | agent.view_trace | view_trace | 平台隐私策略；身份溯源仍走独立高危授权 |

所有动作同时执行 RBAC、资源 ACL 和当前主体校验。普通 Owner 默认无 publish/operate，只有显式授权可操作；超级管理员也经过 Policy 和审计。operate 不授予编辑、发布或工具调用权限；组织可通过 Policy 对其覆盖动作进一步收紧。

### 7.2 发布记录与公共事件

| 发布记录 action | 审计结果事件 | 对外/内部集成事件 |
|---|---|---|
| publish | agent.version.published | agent.version.published |
| rollback | agent.version.rolled_back | agent.version.rolled_back |
| suspend | agent.suspended | agent.suspended |
| resume | agent.resumed | agent.resumed |

agent.version.validated 的 payload 记录验证结果及错误，不能仅因产生事件就视为验证通过。失败管理动作写 action/result 审计，不发成功结果事件。agent_release_events.event_type 存规范结果事件名，业务 action 保存在 metadata，不能再用 rollback 充当事件类型。

审计可以包含 created/updated/archived/definition.changed/access.changed 等更多动作，集成事件按消费者需求发布，不要求两套清单一一相等。旧 `agent.version.rollback` 仅为接收兼容别名，转换为 rolled_back 后以同 event_id 去重，不能双发产生两次业务操作。

## 8. 后续能力与范围准入

- Search Gateway 在当前实现中指 Search Adapter：ES DSL 转换、查询/索引操作和平台治理边界。按当前能力估算，不固定代码行数，不新增多后端路由或独立部署要求。
- GraphRAG 是未排期的远期研究项，需场景及 POC 后另行 ADR；Advanced RAG 的有限多跳检索不以知识图谱为前置依赖。HR/CRM 业务 Agent 与生产 Connector 分别按版本和授权范围演进。
- Multi-Agent 保留为 V1.3 规划能力；M0 形成真实复杂场景、单 Agent 基线与质量/成本/延迟比较标准，M3 开始前确认收益。收益未证实时形成范围 ADR 由产品/架构确认是否延后；不得自行删除既定交付，也不得以文档数量代替收益证据。
- V1.4/V2.0 在实际立项前补其详设；V1.1–V1.3 的 Mock、最小 Approval Contract 和单企业模式能够独立验收，不依赖未交付的 Workflow/Approval Center。生产副作用启用前必须满足对应授权、审批、幂等与补偿条件。

## 10. V1.4 Workflow、业务动作与审批增量

V1.4 详细设计入口见 [开发包 README](../plan/V1.4-Enterprise-Workflow-and-Integration/README.md)。本节是新增公共对象/状态/执行域的设计解释源；本版新增表/API 的唯一详细清单位于 [V1.4/06](../plan/V1.4-Enterprise-Workflow-and-Integration/06-database-api-and-contract-design.md)，其余文件按此引用。

### 10.1 独立 Workflow 与公共状态

- Workflow Definition 使用 workflow_key、owner_subject_id、current_version_id 和定义生命周期；Workflow Version 使用 definition_json、schema_version、definition_hash 和不可变资源 Binding，发布策略沿用版本快照原则。
- Workflow Instance 使用 workflow_version_id、requester_subject_id、input_ref/output_ref、idempotency_key、request_hash、status、terminal_reason、deadline_at、origin_agent_run_id；来源 Agent 与流程执行 Owner 分开，不能把实例写入 agent_runs。
- Workflow Step 使用 instance_id、step_key、sequence_no、step_type、status、resolved_input_ref、parameter_hash、action_id/approval_id、result_ref、deadline_at。Attempt 保留每次尝试、错误与外部调用引用，不能覆盖历史成功/失败事实。

Workflow Instance 状态：QUEUED、RUNNING、WAITING_APPROVAL、WAITING_EVENT、PAUSED、CANCEL_REQUESTED、COMPENSATING、NEEDS_REVIEW、SUCCEEDED、FAILED、CANCELLED、TIMED_OUT。NEEDS_REVIEW 为未闭合业务事实的非终态；补偿完成通过结果/审计说明，不新增“全部历史被回滚”的含义。

Workflow Step 状态：PENDING、RUNNING、WAITING_APPROVAL、WAITING_EVENT、RETRY_WAIT、SUCCEEDED、FAILED、SKIPPED、CANCELLED、UNKNOWN。分支跳过和外部提交 UNKNOWN 分别记录；Workflow 状态不扩充 Agent Run 的枚举。

声明式步骤允许 validate/condition/approval/tool/wait_event/timer/confirm/notify/end。DAG、字段/分支/Deadline/重试/补偿和资源 Binding 经 Schema 与发布 Gate 校验。原始文本或模型输出不能直接改流程或审批规则。

### 10.2 Business Action 与 Tool 执行域

Business Action 表达逻辑外部效果，Tool Call 表达一次调用。Action 字段：action_id、execution_scope、Owner/Step、tool_version_id、connector_instance_id、parameter_hash、idempotency_key、status、external_operation_ref、external_resource_ref、authorization_grant_ref、compensates_action_id、started_at/finished_at。

Action 状态：PENDING、AUTHORIZED、SUBMITTING、SUCCEEDED、FAILED、UNKNOWN、COMPENSATING、COMPENSATED。UNKNOWN 不自动重放；补偿是对已确认成功动作的独立 Action，与 forward Action 用 compensates_action_id 关联，并使用自己的幂等 Key/授权。原 Action 的 Attempt 和外部响应记录保持不变。

ToolCallRequest/Tool Call 在原字段基础上增加 execution_scope=agent/workflow、workflow_instance_id/workflow_step_id/action_id。Agent 请求保留 run_id/agent_key 和原授权；Workflow 请求使用可信 Workflow 身份与版本 Binding，Agent 字段可空，所有调用仍进入同一 Gateway/Policy。新增 Scope 不能由普通客户端伪造。

V1.4 内部结果增加 commit_state=NOT_STARTED/CONFIRMED_SUCCEEDED/CONFIRMED_FAILED/UNKNOWN；旧 DTO 保持兼容状态，未知提交用稳定错误码和 retryable=false 映射。实际迁移先识别存量调用方与 Owner，无法归属的旧行不能随意填 Agent ID。

### 10.3 Approval 与 Grant 扩展

ApprovalRequest 增加 execution_scope、workflow_instance_id/workflow_step_id/action_id；原 run_id/step_id 在 Agent Scope 必填，在 Workflow Scope 可空，并要求 Workflow Owner 字段必填。默认 agent 兼容旧调用方；数据库检查每项审批有唯一合法执行域。

复用 human_interactions 与 approval_id/decision_id，新增审批策略版本、阶段、Assignment/委托/升级记录；阶段决定不能直接签发请求级批准 Token。阶段全部通过时生成原 ApprovalDecision，保留历史字段/回调与审计。

Approval Token 增量绑定 execution_scope/action_id。首次消费以 CAS 兑换绑定 Action 的持久 Grant，重试检查同一 Grant、参数和当前授权；Grant 到期/撤回/参数变化使未提交动作停止。消费同一 Token 不创建第二个授权或 Action。补偿操作获得独立授权，不能借原批准扩大权限。

### 10.4 事件、幂等与恢复

Workflow/Action/Approval 事件复用 event_id/event_type/schema_version/occurred_at/aggregate_id/correlation_id/payload；Workflow 流增加 instance_id 和单调 sequence，数据库唯一 `(instance_id, sequence_no)`。公共事件名与 payload 详见 V1.4/06。

创建实例按非空 `(deployment_namespace, requester_subject_id, workflow_key, idempotency_key)` 唯一；published 选择意图重试保留首次快照，改输入/显式版本返回冲突。外部动作按 `(deployment_namespace, connector_instance_id, operation_key)` 去重，所有 Attempt 保留 Key。Trigger 按稳定 source_event_id 去重；Schedule 按 trigger_id/scheduled_for_utc 去重。

PostgreSQL 记录可运行步骤、定时器、租约、Outbox 与操作事实；RabbitMQ/Celery 执行有界任务，恢复扫描以数据库状态修补派发。外部副作用在 DB 事务外执行，租约锁不替代外部幂等/唯一约束。跨天等待不依赖 Worker 常驻或单个内存倒计时。

### 10.5 Evaluation 与权限增量

复用 evaluation_runs/results/profile/dataset；V1.4 增加 target_type=workflow、可空 workflow_version_id/结果 instance 引用及流程/审批/恢复指标。旧 rag/agent 行和 Gate 语义保持；未知 target_type 的旧 Runner 安全拒绝，不能把 Workflow 测试当作 Agent 测试。

Workflow 资源动作包括定义治理、实例 view/start/pause/cancel/resume、reconcile/compensate 和 Trigger 治理，按现有 RBAC/Policy 的组织授权与实例 ACL 判断。审批扩展 view/decide/withdraw/delegate/reassign 和策略治理；Connector 复用 manage/use 并增加受控 production-enable。规范 Policy Action 与 API→Permission 映射统一见 V1.4/06，避免维护两套动作清单。workflow.start 不授予 tool.invoke 或 approval.decide，来源用户/资源授权在每个外部动作前仍有效。

用户已选择工单创建→审批→结果确认，具体系统和审批制度进入 V1.4 M0 冻结。Workflow/Action 的 deployment_namespace 表示本企业部署实例，不替代主体及资源授权。

## 11. V2.0 企业运营、资源授权、费用与恢复增量

V2.0 入口见 [开发包](../plan/V2.0-Enterprise-Grade-Platform/README.md)，新增存储/API 的唯一详表见 [V2.0/07](../plan/V2.0-Enterprise-Grade-Platform/07-database-api-and-contract-design.md)。所有版本继续采用单企业内部部署，产品范围依据 ADR-0013。

### 11.1 企业内部组织、成员与资源授权

Organization/Workspace 具有稳定 ID，分别表达本企业组织和协作范围。Workspace 可关联本企业 Organization；资源保留 Owner、现有 ACL 及可信父关系。已有 Identity/Policy 的 AccessContext 承载 subject_id、actor_ref、适用 organization_id/workspace_id、environment、purpose、policy_version；这是服务端授权视图，客户端和模型不能自行声明有效权限。

当前成员关系、资源 ACL、角色、环境与 Policy 共同决定访问。缺少必需授权信息时拒绝；未分配 Workspace 的旧资源按既有 Owner/KB ACL 处理，不能据空值查全部或给默认成员扩权。

旧 UUID、Agent/Workflow 快照、客户端及外部 operation_key 保留。新增组织/Workspace 关联仅在实际协作需求下以兼容迁移实现，并验证原授权和派生数据一致性。高权限运维限定目标、目的、时限及审计，不自动获得全部业务内容和凭据。

### 11.2 Model Route 与预算账本

路由使用版本化策略与 route_resolution_id，候选限定能力、授权、区域/上下文、预算/质量。Embedding 绑定原向量空间；Judge/回归不可比因素必须记录，fallback 不扩大约束。

Budget：budget_id、scope、unit/currency、period_start/end、limit、policy_version。Admission/Reservation：admission_id、reservation_id、source_attempt_id、scope、budget_refs、reserved_amount/units、price_version_ref、dispatch_state、status、expires_at。预算可用额度扣除已记费用与有效/待核对预留，多级约束同事务准入。

Reservation 状态：RESERVED、DISPATCHED、HELD_REVIEW、SETTLED、RELEASED；过期仅触发检查，已派发/未知的预留不能因 TTL 自动 RELEASED。每个真实网络重试/fallback 是独立 Attempt 和消费，消息重放不重复预留。

Usage/Ledger：usage_id、source_event_id/attempt_id、workspace_id/subject_id、Run/Workflow/模型引用、route/price 版本、Token/计量单位、amount/currency、confirmation_state、adjusts_entry_id、occurred_at。追加不可变 Entry，来源/版本去重，修正追加调整；金额采用 Decimal/NUMERIC，内部估算、预留、确认成本与供应商账单分开。

严格预算依据已批准的能力/价格/用量上界；未知或不可验证时不宣称绝对费用保证。Run budget_json、token_usage_json/cost_estimate 保留为限制/兼容视图，不能替换 Ledger。

### 11.3 安全、生命周期与运营

Security Incident 状态：OPEN、TRIAGED、CONTAINING、INVESTIGATING、RECOVERING、CLOSED。Deletion Job 状态：REQUESTED、RUNNING、PARTIAL、VERIFIED、FAILED；依法留存、员工撤权/删除范围及 tombstone 可追溯，备份恢复前重新应用当前撤权与删除规则。

复用 Identity/Policy、Secret、Audit、Evaluation/Trace；V2.0 增加资源归属、路由/环境/恢复版本和运营指标。platform 测试目标只经受控 Adapter，旧 Runner 未识别时安全拒绝；安全/审批/费用/副作用的门禁依确定性证据。

SLO 定义包含目标、成功/时限、窗口、分母/负载、Owner/版本；真实端到端与阶段诊断分别统计。单企业部署的容量/SLO/RPO/RTO 由 M0 及实测确认，不设置未经验证的默认承诺。

### 11.4 Recovery Set、Journal 与准入

Recovery Set 保存 DB/WAL/对象/配置/密钥/归属/账本/操作证据的 Manifest、Hash、游标与恢复覆盖；状态 PREPARING、READY、INVALID、RETIRED。READY 说明制品已验证，不能直接授权生产切换。

Recovery Run 状态：QUEUED、RESTORING、VALIDATING、RECONCILING、AWAITING_RELEASE、COMPLETED、FAILED。Deployment Gate 以 BLOCKED、READ_ONLY、NORMAL 表达当前允许范围，带 deployment_epoch、scope、证据和授权；只读恢复不放行计费模型调用或业务写入。

Side Effect Journal 在外部提交前保存原 Action/admission/Attempt、Owner、Key、参数/配置/价格 Hash、durability_receipt 和后续确认。Journal INTENT 不证明未提交；恢复后按原 Key/外部证据核对已发生效果和未知用量，不重建 Key 或自动清除预留。存储/故障域/密钥/保留及 receipt 由实际方案验证。

当前身份/资源授权、版本/预算/审批/Trigger/Timer/删除状态及独立证据验证后才将新 Epoch 放行。副作用/计费 Worker 恢复保持旧幂等语义，不能凭 DB 回滚或应用回滚撤销外部事实。

### 11.5 兼容与授权

AccessContext 扩展及新增 admission/route/usage、Journal/Recovery 等字段使用兼容 DTO 与明确版本窗口；旧资源/回调/消费者迁移按实际 Owner 验证。新的 API→Policy/权限清单仅在 V2.0/07 维护，不把平台运维权自动授予业务用户。

开发包以单企业内部部署为产品基线。跨地域等增强需求按 M0 明确范围和验收；ADR-0011/0012 仍为 proposed，实际代码、兼容迁移、POC 与认证待实施。已有身份/资源授权、审批、业务 Action、账本和恢复事实保持复用。
