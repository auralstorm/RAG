## **一、平台总体定位**

建设一套企业级统一 AI 平台，而不是单纯的企业知识库问答系统。

平台最终具备六大核心能力：

1. **Knowledge**：企业知识接入、解析、切片、索引。
2. **RAG**：企业知识检索、问答、证据引用。
3. **Agent**：任务规划、工具调用、复杂业务执行。
4. **Integration**：REST、SQL、MCP 和企业系统接入。
5. **Governance**：身份、权限、审计、评测、可观测。
6. **Platform**：模型、供应商、缓存、并发和运行管理。

产品入口采用已经确定的 Chat/Admin 两个独立前端应用，位于同一 Monorepo，共用后端 API，分别启动、构建和部署；工程决策见 [ADR-0014](../adr/0014-monorepo-and-independent-frontend-apps.md)：

* **Chat**：员工问答、Agent 使用、对话历史、任务执行和审批。
* **Admin**：知识库、模型、Agent、Tools、权限、评测、监控和系统配置。

# **三、最终技术选型**

这是目前确定采用的技术基线。对象存储采用 RustFS，通过 S3 Adapter 接入，依据 [ADR-0015](../adr/0015-rustfs-object-storage.md)。

| **技术领域**        | **采用方案**                    | **主要职责**                     |
| --------------- | --------------------------- | ---------------------------- |
| 前端              | Vite + React + TypeScript    | Chat / Admin 两个独立应用       |
| 后端              | Python + FastAPI            | 平台 API                       |
| RAG Framework   | **LlamaIndex**              | 文档处理、检索、Query Pipeline       |
| Agent Framework | **LangGraph**               | Agent 状态和任务编排                |
| Workflow 执行（草案） | 平台确定性解释层 + PostgreSQL/RabbitMQ/Celery | 规则/等待/恢复/补偿；ADR-0009 与 POC 后确认 |
| 文档解析            | **Docling + MinerU**        | Docling 默认，MinerU 复杂 PDF 备选  |
| 搜索引擎            | **Elasticsearch**           | Dense + BM25 + Hybrid Search |
| 模型网关            | **LiteLLM + 自研 Facade**     | 模型路由、限流、统一调用                 |
| 异步任务            | **RabbitMQ + Celery**       | 文档处理、索引、评测和清理                |
| 业务数据库           | **PostgreSQL**              | 平台核心业务数据                     |
| 缓存              | **Redis**                   | 缓存、限流、短期状态                   |
| 文件存储            | **S3 / RustFS**              | 文档原件、解析产物                    |
| 可观测性            | **OpenTelemetry + Phoenix** | Trace、调试、链路分析                |
| 质量评测            | **RAGAS + Golden Dataset**  | RAG 质量评估                     |
| 依赖管理            | **uv + pnpm workspace**     | uv 管理 Python；pnpm 管理前端应用/公共包 |
| 容器化             | **Docker**                  | 开发、测试、部署                     |

注意：以上是已经选择的技术基线，不代表每项都完成了 POC 验证。Elasticsearch、Docling、LiteLLM 等仍需完成实施验收；如果未满足硬性要求，再通过 ADR 调整。

# **四、核心业务技术链路**

## **4.1 离线知识入库链路**

**Knowledge Ingestion Pipeline**

1. 文档上传 / Connector 接入
2. 文件校验、安全扫描、Hash 去重
3. Docling / MinerU 文档解析
4. 文本清洗和结构标准化
5. Metadata 提取和权限标记
6. Structure-aware Chunking + Parent-Child
7. Embedding 向量化
8. Dense + BM25 + Metadata / ACL 索引
9. 索引验证、质量评测、版本发布

关键设计：

* LlamaIndex 主要负责文档处理和 Ingestion Pipeline 组件。
* 默认采用结构化切片和 Parent-Child。
* Embedding 通过 Model Gateway。
* Search 通过 Search Gateway。
* 索引采用 V1、V2 版本化构建。
* 新版本验证通过后原子切换。
* 失败可以回滚，不破坏现有生产索引。

## **4.2 Standard RAG 在线问答链路**

```
员工提问
   ↓
身份认证 / 权限上下文
   ↓
Conversation Context
   ↓
Query Router / Intent
   ↓
Query Rewrite（按需）
   ↓
ACL Filter
   ↓
Dense Search + BM25
   ↓
RRF Fusion
   ↓
Reranker
   ↓
Parent Context Expansion
   ↓
Context Assembly / Token Budget
   ↓
Prompt Assembly
   ↓
LLM Generation
   ↓
Citation Validation
   ↓
Answer Verification
   ↓
SSE 流式返回
```

初始检索参数：

| **参数**            | **初始值** |
| ----------------- | ------- |
| Dense Top K       | 40      |
| BM25 Top K        | 40      |
| RRF Rank Constant | 60      |
| Reranker 输入       | 20      |
| 最终上下文 Chunk       | 5–10    |

后续根据 Golden Dataset 调整。

## **4.3 Agentic RAG 链路**

```
用户复杂问题
     ↓
Query Router
     ↓
LangGraph Agent Runtime
     ↓
Planner
     ↓
Task Decomposition
     ↓
多个 Retriever Tool / Business Tool
     ↓
RAG Engine / Tool Gateway
     ↓
Evidence Collection
     ↓
Answer Synthesis
     ↓
Verification
     ↓
最终答案
```

普通知识问题走 Standard RAG；复杂跨文档问题才进入 Agentic RAG；实时业务数据查询走 Tool Gateway。

这样避免每次对话都承担 Agent 的额外模型调用成本。

# **五、平台的核心安全与治理设计**

| **能力**   | **最终方案**                 |
| -------- | ------------------------ |
| 后台权限     | RBAC                     |
| 资源权限     | Knowledge Base ACL       |
| 内容权限     | Document / Chunk ACL     |
| 检索安全     | 检索前权限过滤 + 结果复核           |
| 模型密钥     | 加密保存、掩码展示                |
| Tool 安全  | Tool Gateway 统一鉴权        |
| Trace 隐私 | 默认匿名、敏感内容脱敏              |
| 高危溯源     | 超级管理员授权 + 原因 + 二次确认 + 审计 |
| 会话删除     | 删除正文、附件、摘要、缓存、关联 Trace   |
| 离职清理     | 待离职立即禁用，7 天后自动删除会话       |
| 系统审计     | 重要操作追加式记录                |

另外，Agent 不能绕过 Policy Engine，不能直接访问向量数据库、数据库和企业业务系统。

# **六、正式纳入的 RAG 质量工程体系**

V1.0 必交付的最小质量闭环，以及后续可增量扩展的质量能力

这是我们后来讨论增加的重点，也是最终架构区别于普通 RAG Demo 的部分。

## **6.1 P0：Trace 分阶段诊断**

每次请求都有统一 Trace：

```
Trace
 ├── Query Understanding
 ├── Query Routing
 ├── Query Rewrite
 ├── Dense Retrieval
 ├── BM25 Retrieval
 ├── RRF Fusion
 ├── Reranker
 ├── Context Assembly
 ├── LLM Generation
 └── Citation Verification
```

管理员能够查看：

* 各阶段输入输出摘要。
* Dense、BM25 召回结果。
* RRF 排名变化。
* Reranker 评分。
* 实际送给 LLM 的 Context。
* Prompt / 模型 / 索引版本。
* Token 消耗。
* 各阶段耗时和错误。

## **6.2 P0：检索调试工作台**

在知识库详情中增加检索调试能力。

支持调整：

* Dense Top K。
* BM25 Top K。
* RRF 参数。
* Reranker 模型。
* Reranker 候选数量。
* 相似度阈值。
* Query Rewrite。
* Prompt。
* Token Budget。

实验环境和生产配置隔离，不允许调试时直接覆盖生产。

## **6.3 P0：最小 Golden Dataset + 基础批量评测；P1：扩展指标与实验**

最小 Golden Dataset、基础检索/回答/引用指标及回归门禁纳入 V1.0 P0。样本数量与质量阈值由业务场景和 POC 冻结；100–200 条仅为扩展参考。复杂参数实验和额外指标可列 P1，不能因此移除基础质量退出条件。

评测包括：

| **类别**   | **指标**                                            |
| -------- | ------------------------------------------------- |
| 检索效果     | Recall\@K、Precision\@K、MRR、NDCG                   |
| 生成质量     | Faithfulness、Answer Relevancy、Factual Correctness |
| 引用质量     | Citation Accuracy                                 |
| Agent 质量 | Tool Call Accuracy、Task Completion                |
| 安全       | 越权、恶意文档、Prompt Injection                          |

## **6.4 配置发布闭环**

## **RAG Quality Engineering Loop**

1. 发现错误问答，获取 TraceId。
2. 定位检索、重排、上下文或生成问题。
3. 在测试环境调整配置和 Prompt。
4. 使用 Golden Dataset 执行批量评测。
5. 通过质量门禁后灰度发布。
6. 监控生产表现，必要时回滚。

**目标是让平台不仅可观测，更能够诊断、实验和持续优化 RAG 效果。**

# **七、能力分层与版本映射**

下表保留原 Phase 术语用于能力分层，不是日历排期，也不是另一套版本验收体系。路线图是版本范围权威；各版本 M0/Phase 0 是该版本内部研发里程碑。

| 能力层 | 内容与界限 | 对应版本 |
|---|---|---|
| Phase 1：基础可信 RAG | 权限、知识入库、Standard RAG、Chat/Admin、Trace、最小 Golden Dataset 与回归门禁 | V1.0 必交付 |
| Phase 2：质量优化 | 扩展指标、参数实验、上下文与缓存优化 | V1.0 P1 及后续增量，不替代基础评测 |
| Phase 3：Agent 执行 | 单 Agent、Tool Policy、Checkpoint 和最小审批协议；再扩展 Planner/Agentic RAG/HITL | V1.1 底座、V1.2 管理、V1.3 高级执行 |
| Phase 4：业务扩展 | REST/SQL/MCP 受控适配、场景驱动协作、HR/CRM 生产集成 | V1.1 适配边界；V1.3 协作准入；V1.4 生产流程 |
| 远期研究 | GraphRAG、独立知识图谱等 | 未排期，场景/POC/ADR 决定，不自动归入 V1.4 |

所有版本采用单一企业内部部署与企业内资源授权，见 [ADR-0013](../adr/0013-single-enterprise-deployment-scope.md)。Search Gateway 在当前实现中指 Search Adapter，不要求独立服务或多后端路由。

# **八、架构决策最终边界**

这里是需要长期遵守的规则。

**平台自主控制的核心资产：**

* Document / Chunk 业务模型。

* 索引版本和发布流程。
* RAG API 与 Retriever Contract。
* Agent 业务状态。

* Conversation / Memory。

* Docling / MinerU：文档解析。

* RabbitMQ / Celery：异步处理。
* Phoenix：Trace 调试界面。
* RAGAS：评测辅助。

## **九、最终结论**

我将目前方案浓缩成一句话：

# **自研平台核心 + 成熟 AI 框架 + 统一 Gateway + 企业级治理**

**LlamaIndex + LangGraph** 构成 AI 执行层；

**RAG Engine + Agent Runtime** 构成核心应用能力；

**Model / Search / Tool Gateway** 统一管理外部资源；

**Policy / Audit / Evaluation / Observability** 保障企业安全与质量。

以上是平台目标态技术架构基线。V1.0 至 V2.0 的交付范围、依赖和验收依总体路线图执行；字段与兼容映射依统一契约规则执行。
