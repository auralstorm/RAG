## 3. 治理级条目证据

### G1：阶段体系和标题定位——成立

证据：[技术架构 L5](<2026-11-23-修订前原文摘录.md:14>) 标题为“最终技术架构总结 V1.0”；[技术架构 L329](<2026-11-23-修订前原文摘录.md:26>) 的 Phase 1–4 将 Golden Dataset 放到 Phase 2、Agent 放到 Phase 3、REST/SQL/MCP 放到 Phase 4。[路线图 L133](<2026-11-23-修订前原文摘录.md:38>) 则以 V1.0–V2.0 划分版本；[路线图 L163](<2026-11-23-修订前原文摘录.md:50>) 将基础评测纳入 V1.0，[路线图 L196](<2026-11-23-修订前原文摘录.md:62>) 将 Runtime 和工具适配纳入 V1.1。两套划分没有明确映射。

但 [路线图 L21](<2026-11-23-修订前原文摘录.md:74>) 已定义路线图负责总体方向、版本边界和治理，最新批准 ADR 与详细设计负责实现细节。因此“排期无权威”过强，准确说法是**两个顶层文件的定位和覆盖规则尚未对齐**。

建议：给架构文档增加目标态定位说明及 Phase→版本映射，明确发布范围依版本需求和退出条件。可以改标题，无需必然删除 Phase 表。

### G2：agent_runs 字段漂移——成立，优先处理

证据：[V1.1/04 L37](<2026-11-23-修订前原文摘录.md:86>) 与 [V1.3/06 L9](<2026-11-23-修订前原文摘录.md:98>) 对同名 `agent_runs` 给出不同字段集合。

| V1.1 定义 | V1.3 定义 | 缺少的决策 |
|---|---|---|
| idempotency_key + 主体/Agent/Key 唯一约束 | Run 字段清单未列出；Step 中有 idempotency_key | 创建 Run 去重与 Step 执行去重是不同职责，须分别保留或明确替代存储 |
| budget_json | token_usage / cost_estimate 等消耗字段 | 预算上限与已消耗量不能直接等同；预算存储与恢复来源需明确 |

| config_version | agent_version_id | 受控配置版本如何迁移到发布快照 |
| requester_subject_id | principal_ref | 主体 ID 与匿名引用是否等价，授权查询如何保持有效 |
| agent_key | agent_id + agent_version_id | 业务 Key、实体 ID 与版本 ID 的关联及存量回填 |
| finished_at | completed_at | 时间字段语义、兼容读写与迁移窗口 |

[V1.3/06 L167](<2026-11-23-修订前原文摘录.md:110>) 仍要求请求幂等键，[V1.3/06 L273](<2026-11-23-修订前原文摘录.md:122>) 要求事务和去重；[V1.3/06 L282](<2026-11-23-修订前原文摘录.md:134>) 还要求不破坏 V1.1/V1.2 表。因此报告不能把“新清单漏列”直接描述为“已经删除旧列”，也不能认定所有幂等机制均无数据库支撑。**成立的是版本升级契约不闭合，照不同文档各自实现会产生风险。**

建议：基于存量表制作增量 Schema 和字段映射，冻结 Run 创建幂等的持久化及唯一约束，验证升级、重复请求与恢复。同步核对 `agent_steps`、`agent_checkpoints`、Run 状态及运行 API 的兼容映射，避免只修一张表。

但 URI 可以由 Object Key 生成，Token 汇总可来自独立列，latency_ms 是合理的单位明确化。这些差异本身不是四处确定冲突。建议冻结响应 DTO、存储结构、毫秒单位、Token 分项及 report_uri 的授权生成规则。

### C5：回滚 API 重复——成立，低影响

[V1.2/04 L153](<2026-11-23-修订前原文摘录.md:684>) 和 [V1.2/04 L192](<2026-11-23-修订前原文摘录.md:696>) 两次列出完全相同的 `POST /api/v1/agents/{agent_id}/rollback`。这是清单重复，没有两套不同请求或行为定义。保留一处定义，另一处引用即可。

### C6：事件字典——成立，部分论证需纠正

[V1.2/01 L192](<2026-11-23-修订前原文摘录.md:708>) 称 rollback 事件，[V1.2/01 L267](<2026-11-23-修订前原文摘录.md:720>) 的审计缩写清单使用 rollback，[V1.2/04 L238](<2026-11-23-修订前原文摘录.md:732>) 的 Event Contract 使用 agent.version.rolled_back。[V1.2/04 L106](<2026-11-23-修订前原文摘录.md:744>) 的发布记录动作又使用 rollback。动作名与结果事件名可以不同，但缺统一字典和映射，容易被各端视为同一事件的不同名称。

建议：分别定义业务动作、审计事件、集成事件及对应关系，冻结规范名称和 payload。审计包含更多管理行为是合理的，不能要求与集成事件一一对等。

### C7：权限——部分成立，尚不能定性为安全漏洞

[V1.2/04 L77](<2026-11-23-修订前原文摘录.md:756>) 的 permission **示例**未单列 rollback/suspend/resume，但包含 operate；[V1.2/02 L205](<2026-11-23-修订前原文摘录.md:768>) 要求回滚/暂停按授权，[V1.2/01 L260](<2026-11-23-修订前原文摘录.md:780>) 和 [V1.2/04 L250](<2026-11-23-修订前原文摘录.md:792>) 要求写接口及所有 API 后端鉴权。

缺口是 operate 是否覆盖三种动作、各动作需要什么角色/资源条件未冻结。建议补“API 动作→Policy Action→Permission→角色/资源条件”矩阵并验证负向访问；可复用 operate 或拆分权限，不必凭列表直接新增三个枚举。

## 5. 风险条目证据

### R1：V1.3 未说明评测扩展——不成立

直接反证：[V1.3/05 L5](<2026-11-23-修订前原文摘录.md:528>)：“将 V1.2 Agent Evaluation 扩展到……”；[V1.3/06 L135](<2026-11-23-修订前原文摘录.md:804>)：“复用 V1.2 Evaluation Dataset / Run / Result 结构，新增……”。该报告项应撤销，而不是补一句已经存在的话。

### R2：V1.2 无兼容义务——不成立

[V1.2/01 L43](<2026-11-23-修订前原文摘录.md:816>) 已要求 Schema 版本、迁移器和历史语义保护；[V1.2/01 L128](<2026-11-23-修订前原文摘录.md:828>) 要求正式 Schema 具备默认值、兼容规则和迁移脚本；[V1.2/04 L258](<2026-11-23-修订前原文摘录.md:840>) 要求兼容迁移、历史版本不静默重写、API 兼容窗口。[V1.3/01 L184](<2026-11-23-修订前原文摘录.md:852>) 则规定新增字段和旧版本安全默认值。

新版本负责消费旧 Schema，是正常向后兼容责任。没有要求 V1.2 提前承诺支持尚未定义的 V1.3 字段。具体跨版本映射不足应归入 G2/G6，不宜以“单边声明”另立缺陷。

### R3：GraphRAG / HR / CRM——部分成立

[V1.0/01 L25](<2026-11-23-修订前原文摘录.md:864>) 排除 MVP GraphRAG；[V1.0/06 L1548](<2026-11-23-修订前原文摘录.md:876>) 将其放入明确不纳入本次验收的后续扩展；[技术架构 L336](<2026-11-23-修订前原文摘录.md:888>) 将它列为远期 Phase 4 P2。MVP 不做、后续再做在逻辑上不冲突。

[路线图 L290](<2026-11-23-修订前原文摘录.md:900>) 的 V1.4 生产 Connector 涉及 HR/CRM/ERP，**没有 GraphRAG**；HRAgent/CRMAgent 只在顶层架构 Phase 表中以这些准确名称出现。不能把三者捆绑成四处相互冲突的同一范围。

建议：GraphRAG 明确作为待验证远期研究，业务 Agent 与 Connector 分别按场景归属版本；统一 Phase 映射即可处理主要歧义，不必全部强行移到 V1.4。

### R4：后续详细设计缺失——部分成立，硬依赖论据不足

V1.4/V2.0 没有独立详设目录，属实。但 [V1.1/README L43](<2026-11-23-修订前原文摘录.md:912>) 排除完整企业审批中心，[V1.3/README L37](<2026-11-23-修订前原文摘录.md:924>) 排除通用企业审批流程，[V1.3/README L38](<2026-11-23-修订前原文摘录.md:936>) 区分 Runtime 与 Workflow，[V1.3/04 L5](<2026-11-23-修订前原文摘录.md:948>) 区分人工介入与企业 Workflow。tenant_id 在前序版本为可空预留。

这些是能力边界和演进接口，不是要求 V1.3 必须调用尚未建设的 V1.4 系统。建议先冻结前序所需的最小接口，待 V1.4 实际立项与业务流程明确后补详设；“V1.3 冻结当天立即启动全部 V1.4 详设”属于投入建议，不是修复现有硬阻塞的必然要求。

### R5：Search Gateway 过度抽象——不成立

[V1.0/01 L83](<2026-11-23-修订前原文摘录.md:960>) 把它定义为平台查询模型→ES DSL 的 Search Adapter；[V1.0/04 L228](<2026-11-23-修订前原文摘录.md:972>) 的 ADR 已要求 Adapter 隔离；[V1.0/06 L685](<2026-11-23-修订前原文摘录.md:984>) 列出批量写入、刷新、删除、健康检查、查询、Mapping/Analyzer 版本等当前职责。[路线图 L98](<2026-11-23-修订前原文摘录.md:996>) 明确逻辑模块不代表独立微服务。

未找到搜索多后端路由、搜索负载均衡或强制独立搜索服务的设计要求；原文的熔断要求主要属于 Model/Tool Gateway。报告把“Gateway”名称推定成了原文未要求的建设内容。

建议：维持适配器边界，按当前职责估算；没有依据限定为“约 300 行”，也不应将必要 ES Adapter 和索引治理工作排除在 V1.0 估算之外。

### R6：Multi-Agent 投入顺序——部分成立

支持证据：[路线图 L697](<2026-11-23-修订前原文摘录.md:1008>) 要求真实场景和评测证明价值；[V1.3/07 L55](<2026-11-23-修订前原文摘录.md:1020>) 将双 Worker 协作列为 M3 验收，[V1.3/07 L177](<2026-11-23-修订前原文摘录.md:1032>) 将其列为交付检查项，未写清业务收益未证实时如何裁剪。

反证：[V1.3/02 L5](<2026-11-23-修订前原文摘录.md:1044>) 明确优先单 Agent + 多 Tool，仅在可隔离专业子任务时委派；[V1.3/07 L100](<2026-11-23-修订前原文摘录.md:1056>) 明确先单 Agent Planner、Agentic RAG，再 Worker；[路线图 L413](<2026-11-23-修订前原文摘录.md:1068>) 明确并行设计不等于提前交付。V1.3 的 7 份详细文档也并非全部专为 Multi-Agent 编写。

建议：在 M0/M3 之间增加真实场景、单 Agent 基线、质量/成本收益和范围裁剪决策。不能仅根据设计文档数量认定已经提前投入实现，也无需未经验证就强制改成 V1.3.5。

### R7：Golden Dataset 优先级——部分成立，报告建议需纠正

[技术架构 L302](<2026-11-23-修订前原文摘录.md:1080>) 标为 P1、[技术架构 L334](<2026-11-23-修订前原文摘录.md:1092>) 放在 Phase 2；[路线图 L184](<2026-11-23-修订前原文摘录.md:1104>) 列为 V1.0 Exit Criteria，确实需要解释两套阶段关系。但 [V1.0/05 L200](<2026-11-23-修订前原文摘录.md:1116>) 明确 P1 可以纳入第一期验收，[V1.0/05 L325](<2026-11-23-修订前原文摘录.md:1128>) 直接写“P1，纳入一期验收”；[V1.0/06 L1405](<2026-11-23-修订前原文摘录.md:1140>) 明确 P0/P1 功能均需完成，[V1.0/06 L1411](<2026-11-23-修订前原文摘录.md:1152>) 要求 Golden Dataset 达标。

因此“P1 不能当退出条件”并非本项目规则。建议明确 V1.0 的最小 Golden Dataset/基础回归是必交付，增强指标和复杂实验可分批；统一优先级定义及 Phase 映射，不能为了消除标签差异就移除质量退出条件。

## 6. 对汇总报告结论和收敛建议的修正

1. **“21 项全部是重述造成的分叉”不成立。** G1 是范围/定位，G3 是租户决策，G4 是评分器落地，R6 是业务收益准入；它们不都属于 Schema 重述。
2. **“G2 + G5 做完，其余 19 项自动收敛”不成立。** [汇总报告 L26](<2026-11-23-修订前原文摘录.md:1164>)、[汇总报告 L115](<2026-11-23-修订前原文摘录.md:1176>)、[汇总报告 L127](<2026-11-23-修订前原文摘录.md:1188>) 的自动消失论断没有闭环依据。建立权威契约后还须修正文档、确定映射、更新消费者和测试；租户、评分器、权限与业务投入决策更不会自动完成。
3. **“冻结机制缺位”应改为“冻结机制已有规划，权威制品及执行证据尚未提供”。** 原文多处已定义 ADR、Contract 冻结、Migration、OpenAPI Diff 和验收责任。
4. **“设计质量已经过关”证据不足。** 当前没有真实 POC、迁移、性能及安全验收结果；原文反而明确仍待验证。可以评价边界设计整体清晰，不能等同于完成验收。
5. **量化建议缺估算依据。** “文档减少 30%”“约 300 行”“两周 vs 两个月”“1–2 天完成契约仓与两份 ADR”等应标为待估算假设，不能作为已证实事实。
6. **清单存在重叠，统计需解释。** G7 的 V1.3 评测部分与 R1 重叠，G5 与 C3/C4/C6 是原因和症状关系。保留分类可以，但不应将所有条目都视为互相独立的缺陷；来源“16 项 + 新增 5 项（含 1 项升级）”与现表计数也缺逐项合并过程。

建议先后顺序：先收敛 G1 与 G2，并落实 G5 的契约权威及实际制品；同时修复低成本 C2/C5/C6。随后补租户 ADR、定义和审批/评测迁移、评分器验收及权限映射。Multi-Agent 和后续版本投入依真实场景决定。每项以“决策、制品、文档同步、兼容验证”完成关闭，不能仅以建目录或开会作为解决证据。
