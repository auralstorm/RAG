# 04｜事件触发、定时调度、补偿与恢复

> 版本：V1.4。公共状态/幂等依据 [统一契约第 10 节](../../architecture/统一契约与跨版本演进规则.md)，表与事件清单见 [06](06-database-api-and-contract-design.md)。

## 1. 事实源与派发

Workflow 状态、Step、Timer、Action、审批及 Outbox 写 PostgreSQL。RabbitMQ/Celery 只投递引用和执行有界任务；Redis 用于限流/可重建租约辅助，不能成为唯一等待状态。

创建/推进步骤和 Outbox 同事务提交。Dispatcher 以唯一 event_id 派发，确认后记录派发结果；发送成功但确认丢失可再次投递，消费者按数据库状态和幂等 Key 去重。

Scanner 扫描 due_at、过期租约、未派发 Outbox 与等待关联事件，以条件更新及 fencing_token 领取工作。周期触发进程使用单领导者/分区协调，扫描任务本身允许重复但不能重复推进业务。扫描间隔、批量和容量门槛在 M0/压测冻结。

Celery Task 不持续占用执行槽等待审批或跨天 Timer；due_at 落库并可重建。进程重启后依据 DB 重算到期工作，不依赖超长 countdown 的可靠性。

## 2. Webhook 与内部事件

入站流程：校验来源身份/签名、时间窗口与请求大小 → 验证 source_event_id/Schema → 校验 Trigger Scope/关联规则 → 持久事件/去重键 → 生成启动或唤醒 Outbox → 返回受理结果。

签名算法、密钥来源、重放窗口与轮换依真实系统冻结。source_event_id 必须稳定；缺失时不能任意用当前时间生成新 ID 来冒充去重。不能建立可靠事件标识的来源保持试验模式，不启用生产自动写入 Trigger。

重复相同事件返回既有处理状态；同 ID 不同有效 payload 返回冲突并审计。未授权签名、越界资源、错误关联和非法状态不能推进实例，拒绝事件不包含明文 Secret。

Webhook、定时器及 UI 决定都是唤醒信号，实际状态推进由领域服务校验。对账 resolved 事件仅来自受控 Reconciliation Service，携带确认结果引用，不能让外部任意事件声称已创建工单。

## 3. Schedule 与 Timer

Schedule 固定 Trigger Version、Workflow 选择、时区、计划规则和执行身份。使用 IANA 时区，实际触发时刻以 UTC 保存；夏令时重复/缺失时间、暂停后补发策略和 missed occurrence 规则在 M0 明确。

每次发生使用 `(trigger_id, scheduled_for_utc)` 唯一键，不以 Worker 执行时间去重。修改日程创建版本，旧已受理任务继续固定对应快照；停用只阻止未受理的后续发生。

实例 Timer 固定 instance/step、用途、due_at、版本和状态。重放/扫描只能领取未完成 Timer；实际唤醒再校验实例仍在等待、当前截止时间和授权。审批升级 Timer 不延长最终审批有效期。

## 4. 故障矩阵

| 故障 | 自动处理 | 必须保留的事实/人工入口 |
|---|---|---|
| DB 提交前失败 | 回滚本地状态，不发任务 | 请求是否已受理可按 Key 回查 |
| DB 成功但 MQ 不可用 | Outbox 重试/扫描修复 | 同 event_id，实例不丢失 |
| Worker 租约过期 | 恢复扫描领取新 fencing_token | 旧 Worker 不能覆盖新状态 |
| 创建调用未发出 | 原 Key 有界重试 | NOT_STARTED 的明确证据 |
| 写入发送后响应丢失 | 原 Key/业务唯一键回查 | UNKNOWN、外部引用及提交 Attempt，不再次创建 |
| 外部已成功但本地保存失败 | 回查并恢复 Action 结果 | 原 Key；禁止新生成 Key 重放 |
| 确认查询临时失败 | 重试只读确认 | 已成功写入事实保持，不能回到 create |
| 审批到期/权限撤销 | 停止后续动作 | expired/Policy 决定和未完成效果 |
| 补偿失败或不可执行 | NEEDS_REVIEW、告警 | 原成功效果及失败补救记录 |

租约和幂等均验证实际竞争窗口；本地原子提交不能保证远程恰好一次。

## 5. UNKNOWN 与对账

UNKNOWN 是“不确定提交结果”，不是业务失败。自动对账调用已验收的只读 Tool，按稳定 operation_key/外部请求引用查询：确认成功则记录工单 ID 并进入 confirm；确认无效果且系统提供可靠唯一约束时，才可原 Key 重试；明确业务失败则按规则结束或补偿；仍未知则 NEEDS_REVIEW。

只读查询返回“暂未找到”可能是最终一致性延迟，不能自动当成“从未创建”。查询覆盖范围、一致性窗口和最大对账时长须由目标系统 POC 定义，之后交人工处理。

人工处理使用受控 reconcile API，记录主体、原因、外部证据、确认结论及 CAS revision；新建对账记录，不修改原响应或把 UNKNOWN 改成无证据成功。人工判断有冲突时继续等待或按业务制度处理，不生成第二个外部创建 Key。

## 6. 补偿

补偿只针对已确认成功的 Action，依据发布快照中的补偿 Binding 和当前外部状态执行。按原成功依赖的反向拓扑顺序处理，多次回放仍使用同一补偿 Action 和幂等 Key。

补偿是新的副作用，重新校验当前主体/服务身份、资源和风险；需要审批时创建独立 ApprovalRequest。不能复用创建工单 Token 来取消工单，也不能因原申请人离职而自动扩大服务账号权限。

工单取消只有目标系统支持且当前工单尚可取消时可执行；已经关闭/执行的工单可能不可撤销，或需要其他业务补救。消息通知已发送也不等于可回收。结果明确列出已发生、已补偿、不可补偿和未知效果。

FAILED 与 CANCELLED 可以附带已确认的不可逆效果及业务认可的处理结果，但不能把未对账的 UNKNOWN 隐藏到终态。NEEDS_REVIEW 在事实闭合前保持非终态；需要制度豁免时记录具体范围、Owner 和外部证据。

## 7. 取消、暂停、恢复与回滚

取消请求以事务标记 CANCEL_REQUESTED，撤销未使用授权并停止新派发。外部调用在途时保留 Step/Action 状态，确认后按政策补偿或记录不可逆效果，最后写明确终结结果。

暂停在步骤安全边界生效。恢复前检查主体、Workflow/Tool Version、凭据、Policy、审批/Grant、期限、租约和待确认 Action。旧快照不兼容时进入人工处理，不能静默升级规则继续写入。

应用回滚保持新增表/列兼容；Workflow 发布指针回滚仅影响新实例。对存量实例的规则切换不是指针回滚，应通过独立受控迁移方案和业务评审处理。

## 8. 故障演练与验收

使用可控 Fake Connector 覆盖“外部成功后断网”“状态保存前进程退出”“重复消息”“旧租约 Worker 迟到”“审批/取消与写入抢占”“升级 Timer 重放”“补偿失败”。目标是每次操作都有可解释事实，并且真实/模拟副作用不重复，不只验证最终页面显示。

记录恢复延迟、Outbox 积压、UNKNOWN 数量/时长、补偿结果和人工处理闭环；指标阈值依业务和测试环境冻结。生产试点必须演练实际系统的幂等、查询一致性和补救方式。
