**执行规则：**

-   技术选型沿用已确认基线；只有 POC 未达到硬性要求时，才通过 ADR 调整。
-   以模块化单体交付 MVP，不因未来扩展目标提前拆分微服务。
-   每个 Task 必须有负责人、Reviewer、关联 PR、测试证据和验收结果。
-   阶段完成必须满足 Exit Criteria；不能用"代码已合并"替代功能验收。

-   任何涉及身份、ACL、审计、删除、密钥和 Tool
    权限的任务，必须有负向测试，不接受仅验证正常路径。

## 2. MVP 范围与明确边界

### 2.1 MVP 必须交付

**Chat（员工入口）** - 企业身份登录（第一期优先完成一种 OAuth/SSO
来源，另一种通过 Adapter 扩展）。 -
新建会话、多轮对话、流式回答、停止生成、历史会话列表与详情。 -
回答中的来源引用、文档跳转或来源详情。 - 每条回答可查看/复制 TraceId。 -
用户只能访问自己的会话和有权限的知识库内容。

**Admin（管理入口）** - 仪表盘只读聚合指标。 - Provider / Model 管理。 -
Knowledge Base、文档上传、入库状态、文档列表和索引操作。 - Trace
查询（仅通过 TraceId，不提供员工会话列表或用户筛选）。 -
后台用户、问答用户、角色管理。 - 操作审计日志。 -
配置中心的第一期配置项。

**RAG 与平台底座** - Docling 默认解析，MinerU 作为复杂 PDF 备选
Adapter。 - 结构化切片、Embedding、Elasticsearch BM25 + Dense +
Hybrid、RRF、可插拔 Reranker。 - ACL
在检索前强制过滤，并对结果做二次权限校验。 - Token
Budget、上下文组装、引用校验、无证据拒答。 - RabbitMQ + Celery 异步
Ingestion。 - PostgreSQL、Redis、S3-compatible Object Storage /
MinIO。 - Model Gateway Facade + LiteLLM。 - OpenTelemetry + Phoenix
Trace。 - Golden Dataset 与基础 RAG Evaluation。 -
文档、索引、会话、用户生命周期和操作审计。

### 2.2 MVP 暂不交付

-   完整的多 Agent 协作、复杂 Planner、自主长任务执行。
-   面向真实生产系统的全量业务 Connector；第一期交付 Connector / Tool
    Contract 和 Mock Connector。
-   任意 SQL 自助执行、任意 URL 抓取、开放式 MCP Tool 自动发现。
-   全面微服务化、跨地域多活。
-   完整知识图谱、GraphRAG、自动知识治理闭环。
-   复杂工作流市场、Agent Marketplace。
-   生产级多模态视频/音频知识库（如未列入单独范围）。
-   允许管理员绕过强制数据生命周期规则的"永久保存"开关。

### 2.3 已确认技术基线

  层次             默认方案                  约束
  ---------------- ------------------------- ---------------------------------------------
  Backend          Python + FastAPI          模块化单体、领域边界清晰
  Frontend         Vite + React + TypeScript Chat 与 Admin 两个独立应用
  RAG              LlamaIndex                通过 Adapter 使用，不把平台业务模型交给框架
  Agent Runtime    LangGraph                 MVP 仅保留边界，复杂 Agent 后续阶段实现
  Parser           Docling；MinerU 备选      统一 Parser Adapter / ParsedDocument
  Search           Elasticsearch             Dense + BM25 + Hybrid + ACL Filter + RRF
  Model Gateway    自研 Facade + LiteLLM     业务策略由平台掌控
  Async            RabbitMQ + Celery         入库、评测、清理等异步任务
  Cache            Redis                     缓存和短期状态，不作为唯一业务事实源
  DB               PostgreSQL                业务事实源
  Object Storage   S3-compatible / MinIO     原件及解析产物
  Observability    OpenTelemetry + Phoenix   统一 Trace / Span
  Evaluation       RAGAS + Golden Dataset    评测可重复、可回归
  Dependency       uv                        锁定依赖版本
  Runtime          Docker                    本地、测试、部署环境一致

### 3.2 RACI 简表

R = 执行，A = 最终负责，C = 协商，I = 知会。

  工作                    Tech Lead   Backend   Frontend   RAG/AI   DevOps   QA   PO
  ----------------------- ----------- --------- ---------- -------- -------- ---- ----
  架构与 ADR              A/R         C         I          C        C        I    I
  API / DB Contract       A           R         C          C        I        C    I
  Chat / Admin UI         C           C         A/R        C        I        C    C
  Ingestion / Retrieval   A           R         I          R        C        C    I
  Auth / ACL / Audit      A           R         C          I        C        R    C
  CI/CD / Runtime         A           C         I          I        R        C    I
  Evaluation              A           C         I          R        I        R    C
  MVP 验收                C           I         I          I        I        R    A

### 3.3 研发协作规则

-   API Contract 先行：前后端基于 OpenAPI / Schema
    并行开发，禁止依赖口头约定。
-   数据模型先行：核心表、状态机、唯一约束、索引和删除策略需先评审。
-   所有跨模块调用走应用服务或明确的
    Contract，不允许随意跨模块读写内部表。
-   所有异步任务必须有 task_id、幂等键、状态、重试策略和错误信息。
-   所有 LLM 调用必须经 Model Gateway；禁止业务代码直接持有供应商 Key。
-   所有检索必须经 RAG Engine / Retriever API；Agent 或 Chat
    层不得直接访问 Elasticsearch。
-   所有 Tool 调用必须经 Tool Gateway 与 Policy Engine；MVP Mock Tool
    也执行同一权限流程。
-   PR 必须包含测试；安全关键变更必须至少一名非作者 Reviewer。
-   每个阶段结束形成测试报告、未解决风险清单和阶段验收记录。

``` text

        |
        v

        |
        +----------------------+
        v                      v

        |                      |
```

检索链路可并行；端到端联调依赖稳定 API。 - P5
中评测集建设、自动化测试、运维仪表盘可并行；最终发布依赖安全和生命周期验收。

## 5. P0：项目启动、POC 与技术冻结（第 1 周）

### 阶段目标

建立研发共同基线，验证关键技术路径在目标环境可运行，完成核心 Contract
和项目范围冻结。P0 不追求完整业务功能。

### 任务清单

#### P0-01 项目仓库与研发规范

**实施进度（2026-11-24）：** 本地工程初始化、锁定安装、检查、测试和启动验收通过，证据见 [P0-01 实施记录](implementation/P0-01.md)；远程 CI、PR 与评审待实际执行。

**负责人：** Tech Lead / Platform\
**依赖：** 无\
**工作内容：** - 建立 Monorepo，按既定代码结构划分
backend、frontend/apps/chat、frontend/apps/admin、frontend/packages、infra、docs、scripts，依据 ADR-0014。 - 建立分支策略、Commit
规范、PR 模板、Code Review 规则。 - 配置 Python / uv、Node / pnpm workspace
版本及锁文件，使用 create-vite React TS 模板初始化 Chat/Admin 最小应用与 FastAPI 工程骨架。 - 建立 lint、format、type check、unit test
的基础命令。 - 建立 `.env.example`，禁止提交真实密钥。

**交付物：** - 仓库初始化 PR。 - 开发环境启动说明。 - 代码规范与 PR
模板。

**验收标准：** - 新开发者按照 README 可在干净环境完成依赖安装。 -
后端、Chat 和 Admin 最小服务可分别启动，两个前端可独立构建，公共包依赖可解析。 - CI 能执行 lint、类型检查和基础测试，公共包/契约变更覆盖消费者。 -
仓库扫描不包含真实 API Key、密码或生产凭据。

#### P0-02 Docker 开发环境

**负责人：** Platform\
**依赖：** P0-01\
**工作内容：** - 编排
PostgreSQL、Redis、RabbitMQ、Elasticsearch、MinIO、Phoenix（或其可用部署形态）。 -
配置健康检查、持久化卷、网络和启动依赖。 -
提供初始化脚本、数据卷清理脚本和本地重置脚本。 -
区分开发、测试配置，不将生产密钥写入镜像。

**验收标准：** - 单条文档化命令可启动基础依赖。 -
服务健康检查通过，重启后持久化数据符合预期。 -
任一依赖不可用时，应用启动或健康状态能明确报告。 -
开发环境可重复初始化，不依赖个人机器上的隐式配置。

#### P0-03 技术 POC 与 ADR

**负责人：** Tech Lead；RAG/AI、Platform 参与\
**依赖：** P0-02\
**工作内容：** - 验证 Docling 对代表性 PDF、DOCX、PPTX
等样本的解析能力。 - 验证 Elasticsearch Dense、BM25、Hybrid 和
Metadata/ACL Filter 的可用性。 - 验证 LiteLLM
到至少一个目标模型供应商的调用。 - 验证 Redis、Celery、RabbitMQ
的任务投递、消费、重试。 - 验证 Phoenix / OpenTelemetry 的基础 Trace。 -
对复杂 PDF 样本评估 MinerU 作为备选 Parser 的必要性。 -
记录技术版本、部署方式、资源配置、已知限制和结论。

**验收标准：** - 每项 POC 有可复现步骤、样本、结果和结论。 - POC
不得只用"能启动"作为通过标准，至少覆盖一次真实输入到输出的链路。 -
未通过项有明确风险、替代方案、责任人和决策日期。 - 只有经过评审的 ADR
才能改变既定技术基线。

#### P0-04 核心 Domain Model 与 Contract 冻结

**负责人：** Tech Lead / Backend / RAG\
**依赖：** P0-01\
**工作内容：** 定义并评审以下最小 Contract： - User / Identity / Role /
Permission。 - KnowledgeBase / Document / DocumentVersion。 -
ParsedDocument / Chunk / ChunkMetadata。 - IngestionJob / IndexVersion /
IndexAlias。 - Provider / ModelConfig。 - Conversation / Message /
Citation。 - Trace / AuditEvent。 - RetrieverRequest /
RetrieverResult。 - ModelRequest / ModelResponse。 - ToolDefinition /
ToolInvocation（MVP 先支持 Mock）。

**验收标准：** - 每个 Contract
有字段、类型、必填规则、枚举、错误语义和版本策略。 - ACL
字段与权限继承规则已定义。 - Document 与 Index Version 状态机已定义。 -
OpenAPI / JSON Schema 与设计文档一致。 - 前后端和 AI/RAG
对关键字段无未决歧义。

#### P0-05 MVP 需求与验收样例冻结

**负责人：** PO / Tech Lead / QA\
**依赖：** P0-04\
**工作内容：** - 确定首期 OAuth 提供方。 - 确定 MVP
支持文件类型、单文件大小、KB 数量、文档数量和并发假设。 -
准备覆盖常见问题、跨段落问题、无答案问题、权限隔离问题的 Golden Dataset
初版。 - 定义 Chat 与 Admin 页面验收流程。 - 冻结明确不做的范围。

**验收标准：** - 每项 MVP 功能都有验收场景和优先级。 -
文件、数据量、并发和性能假设有书面记录。 -
业务验收人确认关键问答样例。 - 新增范围必须走变更评审，不得隐性加入
Sprint。

### P0 阶段 Exit Criteria（M0）

-   [ ] Monorepo、CI、Docker 开发环境可重复运行。
-   [ ] 核心技术 POC 有结果，风险已登记。
-   [ ] 技术基线与 ADR 冻结。
-   [ ] 核心 Domain Model / API Contract 评审通过。
-   [ ] MVP 范围、样本数据和验收场景确认。
-   [ ] 未决阻塞项均有负责人和解决期限。

## 6. P1：工程底座、身份认证与权限骨架（第 2--3 周）

### 阶段目标

交付可运行、可登录、具备基本角色授权和审计能力的系统骨架。此阶段重点是安全边界，不追求复杂业务页面。

### 任务清单

#### P1-01 后端模块化单体骨架

**负责人：** Backend / Tech Lead\
**依赖：** P0-01、P0-04\
**工作内容：** - 建立 API、Application、Domain、Infrastructure 分层。 -
建立统一配置、日志、异常处理、Request ID / Trace ID 中间件。 -
建立数据库迁移机制、Repository 基础和事务边界。 -
建立统一分页、排序、过滤、错误响应格式。 - 约束模块依赖方向，避免 API
层直接操作 ORM 内部对象。

**验收标准：** - 模块依赖规则有自动化或可执行检查。 - API
错误格式统一，包含稳定 error_code 和 request_id。 -
数据库迁移可从空库完整执行。 - 核心业务逻辑可通过单元测试运行，不依赖
Web Server。

#### P1-02 Chat/Admin 独立应用布局与公共包

**负责人：** Frontend\
**依赖：** P0-01、P0-04\
**工作内容：** - 在 P0-01 的两个 Vite + React + TypeScript 应用中分别建立 Chat、Admin
路由、布局和环境配置。 - 将 API Client/生成类型、公共组件与工具放入 frontend/packages 对应包，建立错误处理、登录态和权限态。 -
建立基础组件、表单校验、表格、空状态、加载状态和错误状态。 -
统一视觉规范，应用通过公共包复用能力，各自保持入口、构建产物与部署目标。

**验收标准：** - Chat 与 Admin 分别启动、构建与部署，应用路由及 API 配置清晰；公共包不反向依赖应用，应用间无源码直接导入。 -
未登录访问受保护路由会跳转登录。 -
无权限页面不展示可操作入口，后端仍执行权限校验。 - API
失败、空数据、加载中和权限不足均有明确 UI 状态。 - TypeScript
严格检查通过。

#### P1-03 数据库基础表与迁移

**负责人：** Backend\
**依赖：** P0-04、P1-01\
**工作内容：** - 创建
users、identities、roles、permissions、role_permissions、user_roles
等基础表。 - 创建 audit_events 基础表。 - 设计
created_at、updated_at、deleted_at 和企业内资源 scope；依据 ADR-0013 采用单企业部署，资源访问沿用用户/组织及 KB ACL。 -
建立外键、唯一约束、必要索引和审计写入策略。 -
明确软删除与硬删除适用范围。

**验收标准：** - 空数据库执行迁移成功。 -
重复身份映射、重复角色编码等数据由数据库约束阻止。 -
关键关系有外键或等效完整性保证。 -
迁移回滚策略和备份恢复注意事项有文档。

#### P1-04 登录与身份映射

**负责人：** Backend；Frontend 配合\
**依赖：** P1-03、P0-05\
**工作内容：** - 实现第一期 OAuth / OIDC 登录。 - 验证
issuer、audience、signature、nonce、state、有效期等安全要素。 -
建立外部身份与平台 user_id 的稳定映射。 - 实现登录、登出、Token
刷新或会话续期策略。 - 建立待离职、已离职用户禁止登录的校验入口。 -
预留第二种 OAuth 来源 Adapter。

**验收标准：** - 有效身份可登录并映射到唯一平台用户。 - 无效签名、过期
Token、错误 audience、重放 state 等场景被拒绝。 -
身份映射冲突不会创建重复用户。 -
已标记待离职或已离职用户不能建立新会话。 - 前端不会将供应商 access token
写入不安全的持久化位置。

#### P1-05 RBAC 与 Policy Enforcement 基础

**负责人：** Backend / Tech Lead\
**依赖：** P1-03、P1-04\
**工作内容：** - 实现超级管理员、知识库管理员、只读审计员固定角色。 -
实现自定义角色和权限矩阵。 - 在后端建立统一 Policy Engine /
Authorization Service。 - 定义 API
级权限、资源级权限和字段级敏感操作边界。 -
禁止仅依赖前端隐藏按钮实现授权。 - 对高危操作预留二次确认和审计钩子。

**验收标准：** - 三个固定角色的权限矩阵与产品规则一致。 - 未授权 API
请求返回 403，不泄露资源敏感内容。 - 知识库管理员只能看到分配给自己的
KB。 - 审计员只读，不能修改供应商、知识库、人员和配置。 -
自定义角色不能通过配置获得超出授权管理边界的系统级能力。 -
关键资源访问均经过统一授权服务。

#### P1-06 操作审计基础能力

**负责人：** Backend\
**依赖：** P1-03、P1-05\
**工作内容：** - 定义 AuditEvent
schema：操作者、角色、时间、IP、模块、动作、对象、结果、风险等级、变更前后摘要、request_id
/ trace_id。 - 建立不可由普通业务 API 修改或删除的审计写入接口。 -
对登录、角色变更、权限变更等操作写审计。 - 敏感字段脱敏，不记录 API Key
明文、Token 或密码。

**验收标准：** - 成功和失败的关键安全操作均产生审计事件。 - 普通管理员
API 无法更新或删除审计记录。 - 审计记录包含定位操作所需字段。 -
日志中不存在明文密钥、密码、OAuth Token。 -
审计写入失败时，高风险操作按策略失败关闭或进入可靠补偿队列，不允许静默丢失。

#### P1-07 基础健康检查与可观测性

**负责人：** Platform / Backend\
**依赖：** P0-02、P1-01\
**工作内容：** - 提供 liveness、readiness、dependency health。 -
接入结构化日志、Trace ID、基础 Metrics。 - 接入 OpenTelemetry SDK。 -
建立服务错误率、请求耗时、数据库连接、队列积压的基础观测。

**验收标准：** - 可区分进程存活与依赖可用。 - 一个请求的 request_id /
trace_id 可贯穿 API 日志。 - 关键依赖异常有明确健康状态。 -
不在普通日志中输出用户会话正文和敏感凭据。

### P1 阶段测试

-   单元测试：权限判断、身份映射、状态校验、审计字段生成。
-   集成测试：OAuth 回调、数据库迁移、RBAC API、审计写入。

## 7. P2：Model Gateway、Knowledge Base 与文档接入基础（第 4--5 周）

### 阶段目标

交付模型统一调用入口、知识库管理和文档上传能力；文档上传后可进入可靠的异步处理队列，但不要求本阶段完成最终可检索状态。

### 任务清单

#### P2-01 Provider 管理

**负责人：** Backend；Frontend 配合\
**依赖：** P1-05、P1-06\
**工作内容：** - Provider CRUD：名称、类型、API
Base、密钥引用、超时、代理、备注、状态。 - API Key
加密保存，列表只显示掩码。 - Provider
禁用时下属模型不可调用并显示禁用状态。 - 删除 Provider
时检查关联模型和使用情况，按产品规则执行级联或软删除。 -
所有新增、编辑、禁用、删除操作写审计。

**验收标准：** - 仅超级管理员可新增、修改、禁用和删除 Provider。 -
审计员可读；知识库管理员不可进入。 - API Key 在 DB 中为加密密文，读取
API 不返回明文。 - 禁用 Provider
后关联模型调用立即失败并返回稳定错误码。 -
删除关联资源的行为符合约束，不产生孤儿模型配置。

#### P2-02 Model Registry 与 Model Gateway Facade

**负责人：** Backend / Tech Lead\
**依赖：** P2-01\
**工作内容：** -
模型注册：模型标识、名称、类型、上下文窗口、能力标签、默认模型、状态、权重、限流。 -
建立统一 ModelRequest / ModelResponse Contract。 - 通过 LiteLLM
适配供应商调用。 -
实现超时、重试、并发限制、请求大小限制和错误归一化。 - 支持 Chat
Completion 与 Embedding 两类调用。 -
记录模型调用耗时、Token、状态、错误类别和成本字段（若供应商可提供）。

**验收标准：** - 业务模块不能绕过 Facade 直接调用 LiteLLM 或供应商
SDK。 - 至少一个 Chat 模型和一个 Embedding 模型调用通过。 -
模型禁用、Provider 禁用、超时、限流、供应商错误有稳定错误语义。 -
重试仅用于可安全重试的错误，不对非幂等操作盲目重放。 - 模型 Key
不出现在响应、日志、Trace 或前端。 - Model Gateway 调用具备 request_id /
trace_id 和用量记录。

#### P2-03 Knowledge Base 管理

**负责人：** Backend；Frontend 配合\
**依赖：** P1-05、P1-03\
**工作内容：** - KB CRUD、描述、状态、创建人、默认模型 / Embedding
配置引用、索引配置。 - KB 与用户/角色授权关系。 - KB
状态与删除状态管理。 - KB 聚合用量指标。 - KB 管理 API 执行资源级
ACL。 - 知识库管理员仅查看分配给自己的 KB，MVP 按既定规则只读。

**验收标准：** - 超级管理员可创建、修改、删除和分配 KB。 -
知识库管理员仅能看到授权 KB，且不能修改、删除或分配权限。 -
审计员只读。 - 未授权用户通过猜测 KB ID 也不能访问资源。 - 删除 KB
进入受控生命周期，不直接遗留 ES 索引和对象存储文件。

#### P2-04 Document Upload 与文件安全

**负责人：** Backend / Platform；Frontend 配合\
**依赖：** P2-03\
**工作内容：** - 多文件上传、文件类型白名单、大小限制、文件名规范化。 -
计算 SHA-256 Hash，支持重复文件识别。 - 上传原件到 MinIO / S3-compatible
存储。 -
文件安全扫描接口预留；未接入扫描器时明确标记环境风险，不伪称已扫描。 -
创建 Document 记录及初始状态。 - 上传完成后投递 Ingestion Job。

**验收标准：** - 合法文件上传后有 Document
ID、Hash、大小、类型和状态。 -
非白名单文件、超限文件、空文件和异常文件被拒绝。 -
重复上传按定义的去重策略处理，不产生不可追踪的重复索引任务。 -
上传接口响应不等待完整解析和索引完成。 -
对象存储失败时不留下状态为成功的 Document。 -
文件访问受权限控制，不允许通过可猜测 URL 直接访问私有文件。

#### P2-05 Celery 异步任务框架

**负责人：** Backend / Platform\
**依赖：** P0-02、P1-07\
**工作内容：** - 建立 Celery App、RabbitMQ Broker、任务队列和 Worker。 -
定义 ingestion、evaluation、cleanup 等队列。 -
实现任务状态、重试次数、错误摘要、幂等键和超时策略。 -
处理重复投递、Worker 重启、任务超时和死信/失败任务。 - 建立任务状态查询
API。

**验收标准：** - 重复投递同一幂等任务不会重复创建业务结果。 - Worker
重启后未完成任务可按配置恢复或安全重试。 -
超过最大重试次数后进入明确失败状态并可定位原因。 -
队列积压、失败率和任务耗时可观测。 - 任务执行不依赖 Web
请求进程生命周期。

#### P2-06 Ingestion 状态机与任务追踪

**负责人：** Backend / RAG\
**依赖：** P2-04、P2-05\
**工作内容：** - 实现
UPLOADED、PARSING、PARSED、CHUNKING、EMBEDDING、INDEXING、INDEXED、PUBLISHED、FAILED、DELETING、DELETED
等状态。 - 记录状态变更时间、错误码、错误摘要、重试信息。 - Document 与
IngestionJob 分离，支持一个文档多次处理版本。 -
设计状态变更合法性校验。 - Admin 展示上传状态与可检索状态的区别。

**验收标准：** - 状态只能按合法状态机迁移。 -
上传成功不等于可检索；只有发布成功才显示可检索。 -
任务失败可查看阶段和错误摘要。 - 重试不会覆盖已发布的有效索引版本。 -
状态与真实对象存储、任务队列、索引状态一致，异常时可通过补偿任务修复。

#### P2-07 Provider / Model / KB 管理页面

**负责人：** Frontend\
**依赖：** P2-01、P2-02、P2-03\
**工作内容：** - Provider 列表、编辑、禁用、删除确认和模型子表。 - Model
列表、默认模型、限流和状态。 - KB 列表、详情、创建/编辑、权限展示。 -
按角色呈现只读和可编辑状态。 - 所有高风险操作提供二次确认。

**验收标准：** - 页面字段与 API Contract 一致。 - 角色 UI
与后端权限一致，但后端仍为最终授权点。 - Provider
禁用时模型状态同步呈现。 - 错误、空态、加载态、删除冲突均有明确反馈。 -
高危操作成功后可在审计日志查询到记录。

-   [ ] KB CRUD 和资源 ACL 生效。
-   [ ] 文件上传、Hash 去重、对象存储和任务投递闭环通过。

-   [ ] 上传态与可检索态在数据和 UI 上明确区分。
-   [ ] Provider、Model、KB、文档关键操作均写入审计。

## 8. P3：完整 Ingestion、Elasticsearch 索引与版本发布（第 6--7 周）

### 阶段目标

建立可重复、可恢复、可验证的离线知识入库链路，使文档从上传最终进入已发布索引，并具备失败恢复和版本回滚能力。

### 任务清单

#### P3-01 Parser Adapter 与 Docling 集成

**负责人：** RAG/AI；Backend 配合\
**依赖：** P2-06、P2-02\
**工作内容：** - 定义 Parser Adapter 接口。 - 集成 Docling，输出统一
ParsedDocument。 -
统一段落、标题、表格、页码、来源定位、图片/附件引用等结构。 -
记录解析器版本、解析参数和解析质量信息。 -
对异常文件、扫描件、复杂表格和超大文件进行失败分类。

**验收标准：** - 代表性样本可解析，输出结构符合 Schema。 - Parser
失败不会产生伪成功状态。 - 解析结果包含可追踪的 Document
ID、Version、页码或定位信息。 -
同一文件使用相同解析版本和配置可重复得到一致结构（允许明确记录的非确定性除外）。 -
解析耗时、页数、失败类型可观测。

#### P3-02 MinerU 备选 Parser 路由

**负责人：** RAG/AI\
**依赖：** P3-01、P0-03\
**工作内容：** - 仅在 POC 证明 Docling 对目标复杂 PDF 有明显缺口时接入
MinerU。 - 建立 Parser Router 的规则配置和回退策略。 - 保留原始 Parser
结果和版本元数据。 - 避免无条件对所有文件双重解析，控制成本和耗时。

**验收标准：** - Parser Router 选择逻辑可测试、可解释。 -
只有匹配规则的文档才调用备选解析器。 -
备选解析失败时按策略回退或标记失败，不静默丢失内容。 -
每份文档可追溯实际 Parser、版本和参数。 - 若 POC 证明不需要
MinerU，本任务记录为"保留
Adapter，不启用实现"，不为了完成任务而增加无效复杂度。

#### P3-03 Metadata 标准化与 ACL 继承

**负责人：** Backend / RAG\
**依赖：** P3-01、P2-03\
**工作内容：** - 统一
document_id、kb_id、document_version、source、file_type、title、created_at
等元数据。 - 定义 Chunk ACL 的继承规则：默认继承 Document / KB
ACL；必要时允许更严格的 Chunk 级限制，不允许无意扩大权限。 -
标准化部门、角色、用户组等主体表达。 - 在索引写入前验证 ACL
字段完整性。 - 处理 ACL 变更触发的重建或增量更新。

**验收标准：** - 每个 Chunk 都有可用于权限过滤的稳定标识和 ACL 字段。 -
Chunk 权限不得宽于其父 Document 的有效权限。 - 缺失或非法 ACL
的文档默认不进入可发布索引。 - ACL
更新后旧权限不会继续通过缓存或旧索引被访问。 - ACL
规则有正向和负向自动化测试。

#### P3-04 Structure-aware Chunking

**负责人：** RAG/AI\
**依赖：** P3-01、P3-03\
**工作内容：** - 基于标题层级、段落、列表、表格等结构切片。 - 定义 Chunk
Size、Overlap、最大 Token、最小长度等可配置参数。 - 建立 Parent-Child
或等效父子上下文关系。 - 保存页码、章节路径、段落序号、来源定位。 -
避免表格行列、标题与正文被无意义拆散。 - 切片参数与 Parser
版本纳入索引版本元数据。

**验收标准：** - Chunk 不超过配置的 Token 上限。 -
标题、正文和表格结构在可行范围内保持语义完整。 - 每个 Chunk 可回溯到原始
Document 和页码/章节位置。 - 重复运行切片可得到可解释、可复现的结果。 -
Golden 样本上人工抽检无大面积截断、重复和结构丢失。

#### P3-05 Embedding Pipeline

**负责人：** RAG/AI / Backend\
**依赖：** P2-02、P3-04\
**工作内容：** - Embedding 统一经 Model Gateway。 -
支持批量、限流、失败重试和批次记录。 - 记录模型
ID、维度、版本和向量生成时间。 - 校验向量维度、空向量、NaN/Inf
和文本空值。 - 设计模型切换时的重建索引策略。

**验收标准：** - 所有向量维度与索引 Mapping 一致。 -
单批失败可重试，不重复覆盖已完成批次的有效数据。 - Embedding
模型变更会触发新的 Index Version，不直接混写不同维度或模型向量。 -
失败任务可定位到文档、Chunk 和批次。 -
供应商限流时队列能够退避，不形成无限快速重试。

#### P3-06 Elasticsearch Index Adapter

**负责人：** Backend / RAG\
**依赖：** P0-03、P3-03、P3-05\
**工作内容：** - 建立 Search Adapter，隔离 Elasticsearch API。 - 创建
BM25 字段、Dense Vector、Metadata、ACL、版本字段。 -
实现批量写入、刷新、删除、健康检查和查询。 - 为索引 Mapping 和 Analyzer
版本化。 - 约束业务层只能通过 Search Adapter 访问 ES。

**验收标准：** - 文档 Chunk 可批量写入并按 ID 幂等更新。 -
BM25、Dense、Metadata Filter、ACL Filter 均可单独验证。 -
错误写入有失败记录和可重试机制。 - 业务 API 和 Agent 层无直接 ES
客户端调用。 - ES 不可用时服务返回可识别错误，不伪造空检索结果。

#### P3-07 索引版本、验证与原子发布

**负责人：** Backend / RAG / Tech Lead\
**依赖：** P3-06\
**工作内容：** - 设计 Index Version、索引 Alias 和版本状态。 -
新版本先构建到独立索引。 - 构建完成后进行文档数、Chunk
数、向量维度、抽样检索、ACL 和健康校验。 - 验证通过后原子切换 Alias。 -
保留上一个有效版本用于回滚。 - 发布失败不影响当前线上有效版本。

**验收标准：** - 构建中的版本不可被普通检索请求读取。 -
只有验证通过的版本能发布。 - Alias
切换是原子操作或实现等效一致性保障。 -
新版本发布失败时旧版本仍可检索。 - 回滚可恢复到上一个已验证版本。 -
每次发布、回滚均有操作审计。

#### P3-08 删除与重建索引任务

**负责人：** Backend / RAG\
**依赖：** P3-07\

## 9. P4：Standard RAG Engine 与 Employee Chat 闭环（第 8--9 周）

### 阶段目标

问答链路，使员工能基于授权知识库进行多轮、流式、带引用的问答，并能对答案进行追踪和质量验证。

### 任务清单

#### P4-01 Retriever API 与 Search Pipeline

**负责人：** RAG/AI / Backend\
**依赖：** M3\
**工作内容：** - 定义 RetrieverRequest / RetrieverResult。 - 实现 Query
normalization、必要的 Query Rewrite。 - 实现 BM25、Dense、Hybrid
检索。 - 实现 RRF 融合。 - 实现 Metadata / ACL Filter。 - 实现可插拔
Reranker。 - 实现 Parent Context Expansion。 -
提供检索调试信息，但不将敏感内部信息暴露给普通员工。

**建议初始参数（需评测调优）：** - Dense Top K：40。 - BM25 Top
K：40。 - RRF rank constant：60。 - Reranker 输入：20。 - 最终上下文
Chunk：5--10。

以上为初始实验参数，不是不可变常量。需通过 Golden Dataset 评估后冻结。

**验收标准：** - 同一请求可记录
Query、Filter、召回候选、融合排名和最终结果。 - ACL
在检索阶段生效，不是只在返回后过滤。 - Reranker 可关闭或替换，不影响 API
Contract。 - 无有效索引、无权限或检索服务异常时返回明确状态。 -
Retriever 不依赖 Chat UI，也不直接拼接最终用户 Prompt。

#### P4-02 Intent / Query Router

**负责人：** RAG/AI / Backend\
**依赖：** P4-01\
**工作内容：** - 实现轻量意图识别和路由规则。 - MVP
路由类型至少包含：普通知识问答、需要查询澄清、无知识库范围、后续业务
Tool 查询（当前返回未启用或 Mock）。 - 根据问题复杂度决定是否 Query
Rewrite。 - MVP 普通知识问答默认走 Standard RAG，不调用 LangGraph 复杂
Agent。 - 记录路由决策与原因。

**验收标准：** - Golden Dataset 中典型意图可正确路由。 -
普通知识问答不会无条件进入 Agent Runtime。 - 路由失败有安全默认路径。 -
不将用户自然语言中的指令当作系统权限或 Tool 授权。 -
路由结果可追踪和评测。

#### P4-03 Context Assembly 与 Token Budget Manager

**负责人：** RAG/AI\
**依赖：** P4-01、P2-02\
**工作内容：** - 统计系统 Prompt、历史消息、检索上下文和回答预留
Token。 - 按模型上下文窗口动态分配预算。 -
对历史对话做摘要或截断策略（保留必要最近消息和关键指代信息）。 - 对
Chunk 按相关性、来源多样性和长度排序。 - 防止单个超长文档占满上下文。 -
保存本次上下文组装的可追踪元数据。

**验收标准：** - 所有请求在发送前通过 Token Budget 校验。 -
输入不会超过配置的模型上下文上限（含输出预留）。 -
超预算时按策略裁剪、摘要或拒答，不发生静默截断。 - 被选入上下文的 Chunk
可追溯到检索结果。 - 历史消息裁剪不破坏基本多轮指代场景。

#### P4-04 Prompt Assembly 与安全防护

**负责人：** RAG/AI / Tech Lead\
**依赖：** P4-03\
**工作内容：** - 统一 Prompt Template 版本管理。 -
明确系统指令、用户问题、历史消息、检索证据的边界。 -
将检索文档视为不可信数据，防范 Prompt Injection。 -
对敏感信息执行必要脱敏。 - 要求模型基于证据回答，缺乏证据时明确说明。 -
对引用输出使用结构化格式，不只依赖模型生成自由文本引用。

**验收标准：** - 文档中的恶意指令不能改变系统策略或触发工具权限。 -
Prompt 版本可追踪。 - 模型不能自行扩大 ACL 或宣称访问了无权限数据。 -
无证据问题按策略拒答或提示知识库未覆盖。 - Prompt、用户内容和检索内容在
Trace 中按敏感级别处理。

#### P4-05 Generation、SSE 与停止生成

**负责人：** Backend / Frontend\
**依赖：** P2-02、P4-04\

event。 - 定义 start、delta、citation、complete、error 等事件。 -

**验收标准：** - 前端可稳定接收流式输出。 -

仅查看，不出现未授权修改和明细导出入口。 -
数据缺失时明确展示"暂无数据/延迟"，不伪造 0 值。

#### P5-07 配置中心

**负责人：** Backend / Frontend\
**依赖：** P1-05、P1-06\
**工作内容：** -
实现通讯录同步开关和间隔等第一期配置（若首期身份源支持）。 -
配置项定义类型、默认值、合法范围、是否需重启和审计等级。 -
明确不存在可绕过法定/企业强制删除策略的会话永久保存开关。 -
配置变更写审计并记录前后值。

**验收标准：** - 仅超级管理员可修改，审计员只读。 -
配置值通过服务端校验。 - 修改结果可追溯，非法配置不会生效。 -
不存在绕过离职生命周期删除规则的开关。 - 配置更新的生效方式有明确提示。

#### P5-08 Evaluation Pipeline 与回归门禁

**负责人：** RAG/AI / QA\
**依赖：** P4-09、P5-01\
**工作内容：** - 建立离线评测任务和结果存储。 -
支持数据集版本、模型版本、Prompt 版本、索引版本关联。 -
评估检索质量、答案忠实度、相关性、引用有效率和拒答表现。 -
建立版本对比和回归阈值。 - 对 ACL 泄漏样本设置硬门禁。

**验收标准：** - 每次评测可复现输入、配置和版本。 -
报告包含样本数、失败样本、指标和版本差异。 - ACL
泄漏样本出现任何未授权内容即判定失败。 - 关键指标低于 PO / Tech Lead
冻结阈值时不得发布。 - 评测任务具备状态、日志、失败原因和重试能力。

#### P5-09 安全加固与威胁测试

**负责人：** QA / Tech Lead / Backend\
**依赖：** P1--P5 核心功能完成\
**工作内容：** - 执行 OWASP Top 10 相关检查。 - 测试 IDOR、RBAC
绕过、ACL 过滤绕过、Prompt Injection、敏感信息泄露。 -
测试文件上传恶意内容、路径穿越、超大文件和 MIME 欺骗。 - 测试 SSRF
风险（尤其未来 Connector / URL 接入边界）。 - 测试模型供应商密钥、日志和
Trace 脱敏。 - 测试速率限制、并发限制、滥用和资源耗尽。 - 测试 Tool
Gateway 默认拒绝策略和 Mock Tool 权限。

**验收标准：** - Critical / High
安全问题全部修复或经风险负责人书面豁免。 - 未授权用户无法通过 API、猜测
ID、修改请求参数或前端绕过访问资源。 - 文档 Prompt Injection
不可改变系统权限或执行未授权 Tool。 -
密钥和个人敏感信息不出现在日志、Trace、错误栈和前端。 -
限流和并发限制可触发并返回稳定错误。 -
所有豁免项有风险说明、缓解措施、负责人和到期时间。

#### P5-10 性能、容量与稳定性测试

**负责人：** QA / Platform / Backend\
**依赖：** P4、P5-01\
**工作内容：** - 对 Chat API、SSE、Retriever、Model
Gateway、上传和异步任务进行压测。 - 观察 API
P50/P95/P99、错误率、队列积压、ES 查询耗时、DB 连接池和 Redis。 -
测试模型供应商限流、ES 不可用、Worker 崩溃、RabbitMQ
短暂不可用等故障。 - 验证缓存失效和权限变更后的数据一致性。 -
根据结果调整并发、队列、超时和资源限制。

**建议 MVP 初始门槛（需 P0 冻结）：** - 非 LLM 的常规 API：目标环境下
P95 ≤ 500 ms（不含外部依赖和大文件传输）。 - Retriever：目标环境下 P95 ≤
2 s（数据集规模和硬件配置必须固定）。 - SSE 首个可见事件：目标环境下 P95
≤ 3 s（模型供应商延迟单独统计）。 - 持续压测期间服务端错误率目标低于
1%（排除明确注入的依赖故障）。 -
任务失败可恢复，队列积压有告警和容量策略。

**验收标准：** -
测试报告记录机器配置、数据规模、并发模型、请求分布和依赖版本。 -
报告提供 P50/P95/P99、吞吐量、错误率和资源使用。 -
不以单次最好成绩作为验收依据。 - 未达标项有明确瓶颈分析和优化计划。 -
所有目标以 P0 冻结的容量假设为准。

#### P5-11 备份、恢复与发布演练

Elasticsearch 索引可重建范围与备份策略。 - 定义 RPO /
RTO（由业务方确认）。 -
演练数据库恢复、对象存储恢复、服务重新部署和索引重建。 -

**验收标准：** - 至少完成一次隔离环境恢复演练。 -

## 13. MVP 最终验收场景（UAT）

以下场景必须由 QA 执行，并由业务验收人抽检。

### UAT-01 登录与身份状态

-   正常员工登录成功。
-   无效、过期或被篡改身份凭据登录失败。
-   待离职和已离职用户不能建立新会话。
-   外部身份重复绑定被阻止。

### UAT-02 知识库权限隔离

-   用户 A 只能访问授权 KB。
-   用户 B 无权访问的 KB 文档不会出现在检索候选、回答和引用中。
-   直接猜测 KB / Document / Chunk ID 不能越权。
-   权限撤销后缓存和旧索引不会继续泄露内容。

### UAT-03 文档入库

-   上传支持类型的文件。
-   系统显示 UPLOADED、PARSING、CHUNKING、EMBEDDING、INDEXING、PUBLISHED
    等状态。
-   上传成功不被误显示为已可检索。
-   解析失败可定位并重试。
-   索引发布失败不影响旧版本。

### UAT-04 RAG 问答

-   提问可获得基于证据的回答。
-   引用可打开到真实文档定位。
-   无答案问题明确拒答或说明未找到证据。
-   多轮追问能处理基本指代。
-   超长上下文按预算裁剪，不超过模型限制。

### UAT-05 Chat 历史与 Trace

-   员工可查看自己的历史会话。
-   员工不能访问其他员工会话。
-   每条回答有 TraceId。
-   TraceId 可复制并由授权 Admin 查询。
-   普通 Trace 查询不展示员工身份信息。

### UAT-06 Admin 权限

-   超级管理员拥有管理权限。
-   知识库管理员只查看授权 KB 和聚合信息，不能修改或删除。
-   审计员只读，不能执行管理操作或高危溯源。
-   前端隐藏与后端 API 拒绝结果一致。

### UAT-07 高危溯源

-   超级管理员输入 TraceId、填写理由、二次确认后才能查看身份映射。
-   审计员无法溯源。
-   每次溯源生成审计记录。
-   无效 TraceId 或失效身份映射不能被恢复访问。

### UAT-08 离职生命周期

-   标记待离职立即阻止登录。
-   7 天内恢复正常可按规则恢复访问。
-   缓冲期结束后自动删除会话明细。
-   删除任务失败可重试并告警。
-   自动删除过程写入审计。
-   后台没有绕过策略的手动批量删除或永久保留开关。

### UAT-09 审计与密钥

-   Provider / Model / KB / 角色 / 配置变更均可查审计。
-   审计记录不能通过普通 API 删除。
-   API Key 掩码展示，数据库加密保存。
-   日志和 Trace 不包含明文密钥或 OAuth Token。

### UAT-10 运行稳定性

-   ES、RabbitMQ、Worker 或模型供应商短暂故障时系统给出明确错误。
-   异步任务可重试或进入失败状态。
-   服务重启后业务数据和任务状态符合恢复策略。
-   备份可恢复，发布失败可回滚。

## 14. 发布门禁（Go / No-Go）

### 14.1 Go 条件

同时满足以下条件才可发布：

-   [ ] 所有 MVP P0/P1 功能完成并通过 UAT。
-   [ ] 核心 API Contract 与数据库迁移冻结。
-   [ ] 身份认证、RBAC、KB ACL 和用户隔离测试通过。
-   [ ] 文档入库、索引版本发布和删除闭环通过。
-   [ ] RAG 回答、引用校验、无证据拒答和 Token Budget 通过。
-   [ ] Trace、Audit、用户生命周期功能通过。
-   [ ] Golden Dataset 回归达到冻结阈值。
-   [ ] Critical 缺陷为 0；High 缺陷为 0 或有正式风险豁免。
-   [ ] 性能与容量测试完成，未达标项已评估。
-   [ ] 备份恢复与发布回滚演练完成。
-   [ ] 监控、告警、Runbook 和值班责任明确。
-   [ ] PO、Tech Lead、QA、Platform 共同签署发布结论。

### 14.2 No-Go 条件

任意一项出现即阻断发布：

-   存在 ACL 泄漏、跨用户会话访问或 RBAC 绕过。
-   API Key、OAuth Token
    或其他秘密可从日志、Trace、前端或数据库明文读取。
-   文档删除后仍能通过检索、缓存或对象存储访问。
-   用户离职生命周期规则无法执行或可被配置绕过。
-   引用可伪造，或引用来源无法验证。
-   核心索引发布失败会破坏当前有效索引。
-   关键任务无法追踪、重试或恢复。
-   没有可验证的备份恢复方案。
-   Critical 安全缺陷未关闭。

## 16. 任务管理模板与 Definition of Ready / Done

### 16.1 Task 管理字段

建议在 Jira / Linear / GitHub Projects 中为每个任务设置：

  字段                  说明
  --------------------- -----------------------------------------
  Task ID               例如 P3-07
  Title                 明确可交付结果
  Epic / Phase          所属 Epic 与阶段
  Owner                 唯一 DRI
  Reviewer              代码或设计审核人
  Priority              P0 / P1 / P2
  Estimate              Story Point 或人日
  Dependencies          前置 Task ID
  API / Schema          相关 Contract
  Acceptance Criteria   可验证的完成标准
  Test Evidence         CI、测试报告、截图或 Trace
  PR / Commit           实现关联
  Risk                  风险和回退方案
  Status                Todo / In Progress / Review / QA / Done

### 16.2 Definition of Ready（DoR）

任务进入 Sprint 前必须满足： - 目标和范围清楚。 -
输入、输出和业务规则清楚。 - 依赖已完成或已确认可并行。 - API / Schema
变更有草案。 - 验收标准可测试。 - 任务规模可在一个 Sprint
内完成；过大必须拆分。 - 安全、数据和异常场景已识别。

### 16.3 Definition of Done（DoD）

任务只有同时满足以下条件才能标记 Done： - 实现符合 Contract
和架构边界。 - 代码通过 Lint、类型检查和 CI。 -
单元测试、集成测试按任务要求通过。 -
关键异常、权限负向和幂等场景已覆盖。 - 日志、Trace、Metrics
和审计按要求接入。 - API、DB、配置和运维文档同步更新。 - Reviewer
已批准，QA 已验证。 - 无未处理的 Critical / High 缺陷。 -
交付物可在目标环境复现。

## 18. 后续阶段扩展路线（不纳入本次 MVP 验收）

MVP 稳定后，可按业务价值逐步扩展：

1.  **Agent Runtime**：基于 LangGraph 实现 Planner /
    Executor、Checkpoint、Retry、Human-in-the-loop、审批和多步任务。
2.  **Tool Gateway 生产化**：从 Mock Connector 扩展到 REST、SQL、MCP
    Server；统一 Tool Contract、身份代理、Policy Engine、审计和限流。
3.  **Agent 管理**：Agent 定义、版本、Prompt、Tools
    授权、发布、回滚和评测。
4.  **Memory**：区分 Conversation Memory、User Preference Memory、Task
    Memory；建立 TTL、权限、删除和可解释策略。
5.  **高级 RAG**：Query Decomposition、Multi-hop
    Retrieval、GraphRAG、Hybrid rerank 优化和多模态检索。
6.  **企业集成**：通讯录同步、文档系统 Connector、工单/CRM/HR
    等业务系统只读查询。
7.  **平台运营**：企业内部权限、配额、成本中心、模型路由策略、Agent
    质量和使用分析。

扩展时仍遵守：Agent Runtime 不直接访问底层 Search / DB /
企业系统；所有能力经平台 Contract、Gateway 和 Policy Engine。

## 20. 结论

本计划将 MVP 拆为 6 个阶段、12 个建议周次，并以 M0--M5 里程碑和 Exit
Criteria 控制交付。真正的完成标准不是页面数量或代码行数，而是：

-   文档能可靠入库、版本化发布、权限隔离和删除。
-   员工能获得可验证引用、受 Token Budget 保护的 Standard RAG 回答。
-   管理员能配置模型、知识库并审计关键操作。
-   Trace 默认匿名，高危溯源受严格授权和审计。
-   离职用户生命周期与自动删除规则可执行、可验证。
-   系统有可重复的评测、性能、安全、恢复和发布证据。

**研发执行时应先完成 P0 的范围、样本、容量假设和 POC
冻结，再按阶段推进。任何阶段 Exit Criteria
未通过，不应仅因计划日期到达而进入下一阶段。**
