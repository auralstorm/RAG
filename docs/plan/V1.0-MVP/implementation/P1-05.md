# P1-05 RBAC 与权限执行

日期：2026-11-25。交付 V1.0 的后端固定角色、自定义只读角色、当前权限查询、目的隔离的 KB ACL 与统一 Policy 执行基础。基于 P1-03 的规范 User、显式来源关联及 P1-04 的真实本地会话，不新增租户或后续版本能力。

## 权限与范围

运行目录位于 `iam/domain/rbac.py`；0004 迁移保存独立冻结的历史矩阵。23 个操作码覆盖 dashboard、provider、model、kb、document、trace、user、role、permission、employee、audit、config、acl。

| 角色 | 操作权限 | KB 内容范围 |
|---|---|---|
| SUPER_ADMIN | 全部 23 项，含管理与 trace.reveal_identity | 当前用途下的显式 READ/MANAGE Grant |
| KB_ADMIN | dashboard.read、kb.read、document.read | 分配范围只读，即使 Grant 为 MANAGE 也不能管理 |
| AUDIT_READONLY | 全部 13 项 read | 当前用途下显式分配，只读，无身份溯源 |
| 自定义角色 | 只能选择上述 read 集合 | 操作许可与显式 Grant 同时成立 |
| Chat 身份 | kb.read | Chat 用途的显式 Grant；后台角色不授予 Chat 内容 |

固定角色的代码、保护标记和权限关系不可改删；数据库也保护矩阵和权限标识。自定义角色不允许声明系统角色、使用固定代码或获得管理/身份溯源能力；即使数据库中意外出现自定义角色的管理权限关系，执行层也过滤它。审计员可读角色及权限目录，遵循数据库/API 详设第 7 节和 UAT-06；早期接口草案中的“仅超级管理员读角色”不作为最终矩阵。

`acl.manage` 是不可委派的全局安全管理操作，只有 SUPER_ADMIN 能显式建立第一份授权或撤销授权，且必须确认和审计。它允许配置 ACL，不直接授予内容访问；超级管理员查询 KB 内容/范围仍必须有显式 Grant。ACL 明细查询同时要求 acl.read 和目标 KB 的 kb.read，不能用猜测 ID 查看未分配 KB 的主体清单。后续 P2 创建 KB 时须在创建用例中明确建立所需初始授权，不能靠角色名绕过 Policy。

Grant 按 admin/chat 分开持久化，支持 USER、ROLE、ADMIN_USER、EMPLOYEE。来源 ID 必须有显式 SubjectBinding，类型不同但 UUID 相同也不合并；生成列与外键阻止不存在的主体。通用契约保留 GROUP，但当前没有组成员事实源，API/数据库不接受 GROUP，执行快照为空组集合，拒绝而不猜测成员关系。

P2-03 尚未实现 KB 实体；本任务只提供授权范围 ID 和访问判断，不生成虚假知识库列表、名称或内容。`kb_resource_grants.kb_id` 当前是不透明引用，没有 KB 外键；P2 建表时须核对现有 Grant、清理孤立引用后添加 FK，并覆盖 KB 删除生命周期。当前可由授权管理员预配置 ID，不代表实体已存在。

## 执行、事务与审计

- `PolicyEnforcer` 在调用方事务中读取当前平台会话、用户/身份/入口许可、角色关系、来源关联和目的匹配的 Grant，再构造内部 AccessContext/AuthorizationSnapshot。JWT 与请求头不提供角色或资源授权；这些内部模型不进入实际 OpenAPI 或前端类型。
- 所有已实现 RBAC/范围端点经过统一服务。角色/权限/Grant 每次从数据库读取；角色撤销、权限修改、角色软删除和 ACL 撤销对已有 JWT 的下一次请求立即生效。
- Policy 单例行的共享锁/排他锁保证受控读写一致；角色/权限/关联/Grant 的数据库触发器递增版本。写入要求 expected_policy_version，旧版本返回 409。版本是失效/并发依据，不是访问凭据。
- 管理变更同时校验当前 Admin 会话、精确 Origin、会话 CSRF、confirm=true、操作能力与当前版本。confirm 是明确的二次确认钩子，不等价于重新认证或 MFA；没有实现完整身份溯源操作。
- 角色替换不能移除最后一名 ACTIVE、具有有效 Admin 入口身份的超级管理员。后续用户停用/身份管理用例也须维护同一不变量，本任务不提供这些管理入口。
- 成功业务变更与成功审计同事务提交；审计写入失败返回 503 并回滚。逻辑拒绝/冲突通过 savepoint 撤销变更和成功事件，再保存 DENIED/FAILED 事件。P1-05 初始交付的 Origin/DTO/未认证入口失败沿用 HTTP 错误处理；[P1-06](P1-06.md) 已补齐写操作的 Origin 和会话验证拒绝，追加匿名 DENIED，不伪造已知审计操作者。DTO 校验仍由 HTTP 入口处理。
- 角色创建、权限编辑、删除记录启用状态及权限 ID 前后摘要；角色分配记录角色 ID 前后集合；ACL 变更记录明确的 Grant 与用途。AuditSnapshot 增加可选 resource_grant/resource_purpose，旧记录缺字段仍能读取，新字段成对校验，不接受任意原始 JSON 摘要。
- `RbacService.require` 是后续模块的只读检查入口；存在业务写入时必须通过调用方事务中的 PolicyEnforcer 重新授权并闭合变更/审计，不能把一次事务外检查或旧 PolicyDecision 当作长期授权。

## HTTP 与契约

以下路径均以 `/api/v1` 开头。列表沿用分页 Envelope，响应 no-store，失败使用现有脱敏错误；未认证 401、越权 403、保护/版本冲突 409、依赖或审计故障 503。

| 方法与路径 | 能力 |
|---|---|
| GET authorization/{application}/me | 当前用途、角色、安全操作码与 Policy 版本 |
| GET authorization/{application}/knowledge-bases | 当前主体的 KB 范围 ID 与 can_manage |
| GET authorization/{application}/knowledge-bases/{kb_id} | 当前 KB 读取判断与管理标记，越界 403 |
| GET admin/roles、admin/permissions | 当前角色及固定权限目录 |
| POST admin/roles | 创建自定义只读角色 |
| PATCH / DELETE admin/roles/{role_id} | 编辑或软删除非固定角色 |
| PUT admin/users/{user_id}/roles | 原子替换当前用户角色 |
| GET / PUT admin/kb-access/{kb_id} | 读取 ACL / 显式配置目的与主体授权 |
| DELETE admin/kb-access/{kb_id}/{grant_id} | 撤销指定 Grant |

OpenAPI、JSON Schema 和 TypeScript 通过 `make contracts` 生成；api-client 导出安全 DTO，双应用类型检查与构建覆盖生成契约消费者。本任务不增加角色/权限管理 UI，也不将 P1-02 的完整业务权限联调标记完成。

**前端接续（2026-11-25）：** [P1-02 当前权限联调](P1-02.md#p1-05-接续当前权限联调2026-11-25) 已消费当前操作码和 Policy 版本；CapabilityView 增加规范主体 `subject_id` 供跨请求一致性检查。Admin 工作台要求 dashboard.read，Chat 应用入口不因缺 KB Grant 拒绝。权限失败/撤销清理和真实浏览器证据见该记录；后端资源授权语义不变，不关闭企业身份/M1 验收。

## 配置与迁移

1. 运行 `make db-upgrade`，再用 `make db-current` 确认 `0004_rbac_policy`。
2. 按 [P1-04](P1-04.md#本地配置与迁移) 创建具有 Admin 入口许可的本地用户。角色不会自动随账号或应用启动创建。
3. 使用该规范 User.id 显式运行以下命令；占位符必须替换为实际 UUID，不能填写来源主体或角色 ID。

   ```bash
   uv run --locked python -m scripts.bootstrap_rbac --user-id <USER_UUID> --config .poc-results/auth/local.json
   ```

4. 命令在私密配置文件锁下生成独立伪名密钥，再在数据库 Policy 锁下授予首位有效管理员并审计。已有有效管理员时拒绝重复 bootstrap，应改用已认证角色管理。命令拒绝 production；不是生产超级管理员恢复通道。
5. 以 `ENTERPRISE_RAG_LOCAL_IDENTITY_CONFIG_REF=.poc-results/auth/local.json make dev-backend` 重启 API。旧配置无 pseudonymization_key 时认证仍兼容，但 RBAC 返回 503，不能退回默认密钥或绕过授权。后续新建本地账号保留既有密钥。

配置文件与数据库不是一个跨介质原子事务：密钥先安全替换，数据库任一步失败不授予角色，可排障后重试；数据库失败不会破坏既有签名密钥和账号。更换伪名密钥需评估历史关联和轮换，不与 JWT 签名密钥共用。本任务没有自动提升本机 local-developer。

回退至 0003 会删除全部 KB Grant、Policy 版本、固定矩阵保护及固定角色权限关联，保留权限目录和自定义角色关系；重新升级恢复固定矩阵，不恢复已删除 ACL。仅在隔离库验证回退，开发库采用前向升级，业务环境需备份并暂停相关写入。
