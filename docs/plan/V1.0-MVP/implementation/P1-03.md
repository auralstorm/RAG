# P1-03 身份、权限与审计基础表

日期：2026-11-25。对应 [实施计划 P1-03](../06-完整研发实施计划与阶段验收标准.md)，迁移为 [0002_iam_audit](../../../../backend/migrations/versions/0002_iam_audit.py)，沿用 P1-01 的 Alembic、PostgreSQL 和事务级迁移锁。本项交付持久化基础，不代表登录、RBAC 默认矩阵或审计服务闭环已经完成。

## 调查与兼容决策

- 修改前盘点后端、前端及脚本：实际消费者使用 P0-04 的 User、ExternalIdentity、SubjectBinding 契约，没有读取 admin_users/employees 的存储代码或业务外键。开发 PostgreSQL 的 public schema 没有业务表；此结论仅针对本地开发库。
- 新建 users、identities、subject_bindings、roles、permissions、user_roles、role_permissions、audit_events 八张表。没有表重命名、UUID 回填或旧 FK 改写，没有新增租户实体。
- users.id 是规范平台主体。subject_bindings 的主键是 `(principal_type, principal_id)`，user_id 外键指向 users。同一个来源类型只能有一个映射；不同来源类型使用相同 UUID 时仍可属于不同用户。
- 目前不存在来源档案表，因此不额外创建空的 admin_users/employees，也不虚构来源 FK。principal_id 保留原来源 ID；将来导入真实来源时，由可信导入/身份服务验证来源记录并显式建立关联，不按 UUID、姓名或 email 推断。未来业务 FK 直接引用规范 users.id。
- 公共 User、身份及授权 Schema、OpenAPI 和前端生成类型保持兼容；本次没有新增 HTTP 路由或改变公开字段。

## 表与约束

| 表 | 关键规则 |
|---|---|
| users | 五种既有状态；仅 ACTIVE 可用于后续登录。软删除记录不得保持 ACTIVE；创建、更新时间及删除时间有顺序约束 |
| identities | 精确 provider_key、issuer、subject 唯一；user_id 外键。停用或软删除仍保留唯一身份键，防止新用户重新占用 |
| subject_bindings | ADMIN_USER/EMPLOYEE 来源类型与原 ID 组成主键；user_id 外键及反向查询索引 |
| roles | code 唯一；预置 SUPER_ADMIN、KB_ADMIN、AUDIT_READONLY 的稳定 UUID；约束保护系统标志，触发器阻止保护角色改 ID/编码、解除保护、软删除、硬删除及整表 TRUNCATE |
| permissions | code 唯一且精确等于 resource.action；资源和操作使用既有小写格式 |
| user_roles / role_permissions | 复合主键防重复；双端外键防孤儿，反向查询列有索引；不预先授予默认角色权限 |
| audit_events | 事件、请求、Trace、主体、结果、风险及变更摘要列；actor_user_id 外键。触发器拒绝 UPDATE、DELETE、TRUNCATE，匿名登录失败可不绑定主体 |

实体采用 TIMESTAMPTZ；users、identities、roles、permissions 在 UPDATE 时由触发器刷新 updated_at。关系表仅记录创建时间；审计记录不可变，仅记录发生及入库时间。

身份键采用固定 UTF-8 的 SHA-256 表达式唯一索引，避免合法的 2048 字符 issuer 加 256 字符 subject 在多字节输入下超过 PostgreSQL B-tree 单项长度限制。原始值仍受限保存，精确匹配不能改为仅凭摘要认领身份；摘要碰撞只会拒绝写入。后续 Repository 必须同时匹配三个原始字段，不允许通过冲突行自动关联其他主体。

审计角色 ID、object_id 和 protected_reason_ref 是历史快照或跨模块引用，不强绑尚未存在的资源表；身份揭示成功审计必须有受限原因引用。摘要 JSONB 在本阶段只约束为对象，P1-06 写入器继续按 AuditSnapshot 白名单校验、脱敏并绑定可靠事务。数据库所有者可修改 DDL 或关闭触发器；生产部署仍须将迁移身份与普通服务身份分离，仅为审计写入身份授予 SELECT/INSERT。触发器不替代数据库权限配置或独立安全评审。

## 删除与回退

- 用户、身份及自定义角色采用软删除；身份/来源映射仍占用唯一键，不因删除自动转移归属。用户停用、待离职或离职时的会话撤销和登录拒绝由 P1-04 接入，清理调度按后续生命周期任务交付。
- 外键采用 RESTRICT，没有静默级联删除。关系撤销和无引用权限/自定义角色的物理清理由应用在授权、审计的事务中显式执行；受保护角色不能删除。
- 已被审计引用的用户保留最小主体记录，可将显示名匿名化，不通过删除用户级联删除审计。普通业务路径不提供审计删除，受控保留期清理由后续治理任务实现。
- 升级命令为 `make db-upgrade`，查询为 `make db-current`，测试配置使用 `PROFILE=test`。迁移通过一个 PostgreSQL 事务执行，失败回滚，重复升级不重复建表或插入角色。
- 开发空库可用 `uv run --locked python -m scripts.migrate_database downgrade 0001_baseline` 回退。该操作删除八张业务表、数据与相关函数；仅适用于可丢弃开发库。已有业务数据的环境先停写、保留并验证备份恢复，再选择前向修复或在隔离环境演练恢复，不能直接执行破坏性 downgrade。不得修改已应用的历史迁移。
