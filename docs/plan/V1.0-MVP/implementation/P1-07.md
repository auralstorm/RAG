# P1-07 基础健康检查与可观测性

日期：2026-11-25。沿用 P0-02 的隔离基础设施、P1-01 的请求关联与事务入口，完成 V1.0 P1-07 的技术日志、基础指标和 HTTP/数据库 Trace。未实现 P5 的完整 RAG 阶段追踪、Trace 查询页面或身份溯源，不据此关闭 POC-06 全链路或 M1。

## 请求与日志

根入口 `make dev-backend` 使用 `backend/logging.json` 输出 JSON 行，并关闭 Uvicorn 原始访问日志。其他部署也须使用同一配置与 `--no-access-log --no-proxy-headers`；仅安装 SDK 不代表宿主日志系统已采用脱敏配置。Formatter 只输出固定事件、级别、组件、进程 ID，以及受控的技术字段；不展开任意日志消息/参数或异常正文。未知 HTTP 故障保留最多 5 层异常类型链，每层最多 8 个应用内相对代码位置（函数、行号），关联当前 Request/Trace；不包含源码、局部变量或绝对路径。第三方消息归为 component_log，保留级别和组件类别。

RequestContextMiddleware 位于 CORS 外层，记录正常响应、401/403/422、未知路径、CORS 提前拒绝和未处理异常。SafeFailureMiddleware 在 CORS 内层转换未知错误，500 保持脱敏响应与允许来源的 CORS 头。每个请求只记录一个 http_request_completed，包含当前服务端 Request ID、Trace ID、根 Span ID、服务端路由模板、受限方法、实际 HTTP 状态、总时长与 completed/error/aborted/cancelled。未知路径统一为 `<unmatched>`，不以实际 URL、资源 UUID、Query 或请求方方法字符串建立标签。

ContextVar 绑定当前异步请求，结束或取消后恢复；并行请求不能互相继承身份或关联。流式请求不缓存正文，时长覆盖 ASGI 调用直到完成/中断。响应开始后保留已发状态，不补发第二个 500；异常被转换为固定的中断错误。取消原样传播，单独计数。

## OpenTelemetry 与导出

OpenTelemetry API、SDK 和 OTLP gRPC Exporter 固定为 1.45.2，与既有 FastAPI 的 API 依赖一致。版本和导出接口核对 [官方 Exporters 文档](https://opentelemetry.io/docs/languages/python/exporters/) 及实际安装的 API。SDK 实现集中在 Adapter，API/业务层通过技术端口使用；不安装全局 Provider，不启用自动 HTTP/SQL/供应商内容抓取。资源只包含明确的 service.name/version/instance.id、部署环境及 Phoenix 项目名，不运行环境 Resource detector。

每个应用在 lifespan 启动独立 Provider、周期 Reader 和采样任务，关闭时先结束采样，再关闭监测客户端、Trace Processor 和 Metrics。服务器根 Span 的 Trace ID/Span ID 同步进入响应、错误和审计的关联上下文。单个有效 W3C 父上下文保留 Trace ID 与父 Span；无效/重复输入重建根。采样由服务端比率控制，返回的 sampled 标志是 SDK 决策，客户端上下文不授予权限，tracestate/baggage 不采信。

依赖探测产生 dependency.* Span，已存在的 PostgreSQL 事务在原连接/提交/回滚边界外增加 postgres.transaction 子 Span，不修改事务语义、不记录 SQL/参数。Trace 只含请求关联、方法、路由模板、状态、结果和固定错误分类，无账号、用户/身份 ID、Cookie、Authorization、Token、IP、正文或来源身份键。实际问答阶段、Worker 传播和私有身份引用随 P2/P4/P5 用例继续接入。

默认启用 SDK/指标，网络 Trace 导出需显式启用并提供私密凭据引用。当前固定 Phoenix 镜像的 REST/OTLP 入口要求认证，不能将 healthz 可用当作匿名采集可用；flush=True 仅表示处理器完成排空，不等于入库成功。网络导出 Adapter 使用官方 encode_spans 和公共 gRPC 接口解析采集端回执：成功数扣除 partial_success.rejected_spans，部分拒收计一个失败批次，非法拒收数或 RPC 失败不计成功。注入的测试 Exporter 仍由 ObservedSpanExporter 包装。失败记 telemetry_export_failed，不输出采集端错误正文。批量队列最多 2048 Span，每批最多 256，单次 OTLP 网络超时 2 秒；每批只尝试一次，部分拒收不重放整批，后续批次可随采集端恢复继续发送。满队列或采集端失败可能丢失技术 Trace，不能替代 P1-06 的事务审计。

## 本地配置

1. `make infra-up` 启动已固定的 Phoenix。通过其受控管理员入口签发服务 API Key；现有镜像的初始密码须按 Phoenix 自身要求变更，生产不得沿用测试初始化流程。
2. 在交互终端运行 `uv run --locked python -m scripts.collector_credentials`，不回显地输入已签发 Token。工具只向忽略的 `.poc-results` 保存 owner-only 文件，默认 `.poc-results/observability/collector.json`；拒绝覆盖已有文件或写入可提交路径，不打印 Token。非交互输入拒绝，避免 getpass 回退为回显。
3. 配置并重启 API：

```bash
ENTERPRISE_RAG_TELEMETRY_TRACE_EXPORT_ENABLED=true \
ENTERPRISE_RAG_TELEMETRY_CREDENTIALS_REF=.poc-results/observability/collector.json \
make dev-backend
```

凭据文件只允许 `bearer_token`，要求当前操作系统用户拥有、普通文件、无其他用户权限；拒绝符号链接、FIFO、过大文件、未知字段及 Header 控制字符。错误不包含原文件内容，凭据只在启动时解析并作为 OTLP metadata 发送。真实部署须挂载对应运行 UID 的私密文件，并配置受保护的采集地址/TLS；更换引用或撤销 Key 后重新启动，不承诺热轮换。

开发 OTLP 默认 `http://127.0.0.1:14317`，test profile 为 `http://127.0.0.1:24317`。可通过 `ENTERPRISE_RAG_TELEMETRY_OTLP_ENDPOINT` 改为明确的 http/https host/port；拒绝 URL 内凭据、路径、Query 和 Fragment。Phoenix 固定项目名 enterprise-rag-api，按响应 X-Trace-ID 在其受控入口核查。

`ENTERPRISE_RAG_TELEMETRY_INTERVAL_SECONDS` 默认 30（5–300 秒），`TELEMETRY_SAMPLE_RATIO` 默认 1（0–1），`TELEMETRY_QUEUES` 是最多 20 个服务器配置队列名的 JSON 数组，例如 `["celery"]`。队列未正式创建时留空，不由观测模块创建业务队列。关闭 `TELEMETRY_ENABLED` 时保留既有 Request/Trace 关联和日志；不得同时开启网络导出。

## 指标与读法

指标经 OpenTelemetry SDK 聚合，定期以 metrics_snapshot JSON 行进入同一受控日志出口，不新增公开 /metrics 或 Admin 业务 API、不另部署监控产品。计数器/直方图是进程内累积值，包含开始/观测时间和单位；进程重启清零，按 process_id 与时间识别重置，取相邻快照差值，不能逐条累加快照。

| 指标 | 含义 |
|---|---|
| http.server.requests | 按方法、路由模板、实际状态和结果统计完成/中断/取消请求 |
| http.server.duration | 秒单位的总请求时长；显式桶、count/sum 可估计分位数 |
| http.server.active_requests | 当前在途请求，完成/取消后释放 |
| dependency.available / dependency.probe.duration | 各依赖最后一次探测状态与耗时；与 ready 响应使用同一探测路径 |
| db.server.connections / db.observation.available | 当前数据库的服务器连接数（排除该次统计连接）与观测可用性；不是尚未引入的应用连接池指标 |
| messaging.queue.ready / messaging.observation.available | 已配置队列等待投递的消息数与观测可用性；不包含已投递未确认消息，不代表 Worker 执行中任务 |
| telemetry.spans.exported / telemetry.export.failures | 采集端确认的 Span 数 / 失败批次数，不按 flush 调用次数冒充入库 |

服务错误率按请求增量中 5xx 或 error/aborted 计算，取消另行观察，401/403 等业务拒绝不冒充服务异常。Gauge 是最后一次完整采样值，按采样周期理解，不跨进程累加服务器连接数/队列全局值。源不可用时不输出该数值，available=0；不能把未知连接数或未知积压写成 0。AMQP 只被动查询，既不创建、消费也不清空队列；PostgreSQL 查询只聚合 pg_stat_activity，不返回连接主体、SQL 或数据库凭据。

### 2026-11-25 非作者复核整改

以 `feaf2e7...a7594fa` 为固定范围，分别执行规范与需求复核，确认两项 P2 问题并整改：

- 未知异常缺少可诊断的因果链：在调用 logger 前提取有界异常类型与应用相对位置，不向任何 Handler 传递原始 `exc_info`。每条最多 5 个 cause、每个 cause 最多 8 个应用栈帧；消息、源码、局部变量和绝对路径均不记录。避免只依靠 JSON Formatter 脱敏、却被其他 Handler 输出敏感原始异常。
- 标准 gRPC Exporter 丢弃 `partial_success`：使用公开 protobuf 编码与 gRPC 调用读取实际回执，仅累计未被拒绝的 Span。部分拒绝、非法计数与传输失败分别计为失败批次；不保留采集端错误文本，不重发部分成功批次。每批单次调用，连接恢复等待与传输共用 2 秒 deadline。

实际本地 gRPC 回归覆盖部分/全部拒绝、非法回执、不可用及恢复；与观测专项合计 `18 passed`。完整后端非基础设施测试 `289 passed, 71 deselected`，Ruff lint/format 与严格 Pyright 通过。传输整改后的独立 Phoenix 复验通过：真实认证入库、原进程与原通道停机恢复、运行中撤销 Key、旧 Key 重启拒绝全部成立，退出码 0；恢复断言同时提供脱敏的接收数/导出数/失败数，便于区分查询与导出故障。冷启动曾出现 RabbitMQ unhealthy，等待原隔离环境恢复后重跑通过，不修改健康门槛。HTTP 契约制品与仓库检查通过。
