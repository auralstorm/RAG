## 1. 文档目的与使用方式

本文件定义 Enterprise Agentic AI Platform 从 MVP 到完整企业级平台的产品演进路径，回答以下问题：

1. 最终平台要具备哪些能力，整体架构如何分层？

5. 每个版本如何验收，怎样判断可以进入下一阶段？
6. 如何控制技术选型、数据兼容、升级迁移、风险和架构变更？

**使用规则：**
- 本文件负责总体方向、版本边界、跨版本依赖和架构治理。
- 各版本详细设计负责本版增量、实现、任务和验收；技术架构 Phase 是能力分层，不作为排期依据。
- 公共实体、字段、状态、事件、权限和迁移映射以 [统一契约与跨版本演进规则](../architecture/统一契约与跨版本演进规则.md) 为设计解释源，实施前与代码仓生成的 OpenAPI、JSON Schema、Alembic 制品一致性核对。
- 如果本文件与 V1.0 详细设计在实现细节上存在差异，以经评审批准的最新 ADR 和详细设计为准；若差异影响总体架构边界，必须同步修订本文件。
- 本文件中的性能目标、容量目标和时间安排均需通过 POC、压测和团队估算确认，不应将规划值误认为已验证结果。

## 2. 产品愿景与最终目标

### 2.1 产品定位

平台不是单一的企业知识库问答产品，而是面向企业内部知识、工具、Agent 和业务流程的统一 Agentic AI Platform。

平台最终支持：

- 员工通过统一 Chat 入口使用知识问答、业务 Agent、任务执行和审批能力。
- 开发者通过 Admin 创建、配置、测试、评测、发布和运营 Agent。
- 管理员统一治理模型、知识库、工具、连接器、身份权限、策略、审计和运行质量。
- Agent 在可信身份、权限策略、预算、审批和审计约束下调用企业知识与业务系统。
- 平台支持从单 Agent、单部门场景逐步扩展到多团队、多 Agent、多业务系统和企业级规模化运营。

### 2.2 最终能力地图

| 能力域 | 最终目标 |
|---|---|
| Chat Experience | 统一对话、Agent 选择、任务状态、审批交互、引用与反馈 |
| Admin & Developer Platform | Agent/KB/Model/Tool/Connector 管理、Playground、发布、评测、运维 |
| Model Gateway | 多供应商、多模型统一接入、路由、限流、配额、成本和审计 |
| RAG Engine | 文档治理、混合检索、重排、上下文管理、Advanced/Agentic RAG |
| Agent Runtime | 单 Agent、多 Agent、状态管理、Checkpoint、重试、人工介入 |
| Tool Gateway | 统一工具调用、身份传递、权限检查、参数校验、执行审计 |
| Connector Framework | REST、SQL、MCP 及企业系统连接器 |
| Policy & Identity | 统一身份、RBAC/ABAC、资源 ACL、策略决策和策略执行 |
| Memory & Context | 会话记忆、任务记忆、用户偏好、摘要、压缩和生命周期治理 |
| Workflow | 确定性业务流程、审批、事件触发、定时任务、补偿与状态管理 |
| Evaluation & Governance | RAG、Agent、Multi-Agent、Workflow 的质量评测与发布门禁 |
| Observability & Audit | 统一 Trace、Metrics、Logs、业务审计和高危操作追溯 |
| Enterprise Operations | 高可用、容量治理、灾备、成本与安全运营 |

## 3. 总体架构与长期边界

### 3.1 逻辑架构

```text
┌─────────────────────────────────────────────────────────────────┐
│                         Experience Layer                         │
│                    Chat                         Admin             │
└───────────────────────────────┬─────────────────────────────────┘
                                │
┌───────────────────────────────▼─────────────────────────────────┐
│                     API / Application Layer                      │
│ Auth · Conversation · Task · Approval · Agent/KB/Model Management │
└───────────────┬────────────────┬─────────────────┬──────────────┘
                │                │                 │
       ┌────────▼──────┐  ┌───────▼────────┐  ┌─────▼────────────┐
       │ Query Router  │  │ Agent Runtime  │  │ Workflow Engine  │
       │ Intent/Route  │  │ LangGraph      │  │ Deterministic    │
       └───────┬───────┘  └───────┬────────┘  └─────┬────────────┘
               │                  │                 │
       ┌───────▼──────────────────▼─────────────────▼────────────┐
       │                    Capability Layer                      │
       │ RAG Engine · Tool Gateway · Memory/Context · Approval    │
       └──────────────┬──────────────────┬────────────────────────┘
                      │                  │
             ┌────────▼────────┐  ┌──────▼─────────────────────┐
             │ Search Gateway  │  │ Connector / Tool Adapters  │
             │ Elasticsearch   │  │ REST · SQL · MCP · Systems │
             └────────┬────────┘  └──────────┬─────────────────┘
                      │                      │
             ┌────────▼──────────────────────▼─────────────────┐
             │             Enterprise Data & Systems             │
             │ PostgreSQL · Object Storage · Redis · ES · HR/CRM │
             └──────────────────────────────────────────────────┘

 Cross-cutting: Model Gateway · Policy Engine · Identity · Evaluation
                 Observability · Audit · Security · Quota/Budget
```

该图表达逻辑职责，不代表必须按图拆成独立微服务。V1.0 采用模块化单体，后续根据负载、团队边界和故障隔离需求决定是否拆分部署单元。

### 3.2 必须保持的架构边界

1. **RAG Engine 与 Agent Runtime 分离**：Agent 通过稳定的 Retriever API 使用 RAG，不直接访问 Elasticsearch 或内部索引表。
2. **Agent Runtime 与 Workflow Engine 分离**：LangGraph 负责 Agent 内部智能执行；Workflow Engine 负责确定性业务流程、审批、超时、补偿和状态推进。不能让 LLM 自由规划替代企业流程规则。
3. **Tool Gateway 是工具调用的统一入口**：Agent 不得绕过 Tool Gateway 直接访问企业业务系统。
4. **Policy Engine 是可信策略边界**：权限不能只依赖前端隐藏或 Prompt 约束；资源访问和工具执行前必须进行服务端授权。
5. **Model Gateway 统一模型接入**：业务模块不直接耦合供应商 SDK 或散落保存供应商 Key。
6. **Memory 与 Conversation 分离建模**：会话消息、短期上下文、长期记忆和任务状态具有不同用途、权限和保留周期。
7. **Evaluation 与 Observability 独立于运行框架**：框架可替换，评测数据、Trace Schema 和业务审计由平台控制。
8. **业务数据模型归平台所有**：框架对象不得成为平台唯一持久化格式。

### 3.3 V1.0 就要确定的架构边界

即使 V1.0 不实现全部能力，也应在代码和数据设计中明确以下模块边界：

- `identity`：用户、服务身份、身份映射和认证上下文。
- `policy`：RBAC、KB ACL 的策略接口；后续扩展 Tool、Agent、Workflow Policy。
- `model_gateway`：统一模型调用 Contract、供应商和模型配置。
- `knowledge` / `ingestion`：知识库、文档、解析、切片、索引生命周期。
- `rag`：检索、重排、上下文组装和引用校验。
- `agent`：Agent 定义和运行边界；V1.0 可只保留接口或最小占位。
- `tool_gateway` / `connector`：Tool Contract 和 Connector Adapter 边界；V1.0 先用 Mock。
- `conversation` / `memory`：会话与未来记忆能力的边界。
- `evaluation`：Golden Dataset、评测任务和结果。
- `observability` / `audit`：技术 Trace 与业务操作审计分开。
- `workflow`：未来确定性流程的边界，V1.0 不建设完整流程引擎。

预留不等于提前建设完整功能。禁止为了“未来可能用到”而在 V1.0 实现复杂、没有当前验收价值的子系统。

## 4. 版本总览


| 版本 | 产品阶段 | 核心目标 | 主要交付 |
|---|---|---|---|
| V1.0 | MVP：Enterprise Knowledge RAG | 建立可信、可运营的企业知识问答基础 | KB、Ingestion、Hybrid Search、Standard RAG、Chat/Admin、权限、Trace、审计、基础评测 |
| V1.1 | Agent Platform Foundation | 建立 Agent 执行和工具调用底座 | LangGraph Runtime、Tool Gateway、Connector Contract、Memory/Context 基础能力 |
| V1.2 | Agent Development Platform | 让开发者可以配置、测试和发布 Agent | Agent Registry、Prompt/Tool Binding、Playground、版本、发布与回滚 |
| V1.3 | Advanced Agentic AI | 支持复杂任务和多 Agent 协作 | Planner、Task Decomposition、Agentic RAG、Multi-Agent、HITL、长任务恢复 |
| V1.4 | Enterprise Workflow & Integration | 连接真实业务系统并安全执行流程 | 生产 Connector、Workflow、审批、事件触发、补偿和业务审计 |
| V2.0 | Enterprise-Grade Platform | 实现企业级规模化、安全治理和运营 | 高可用/弹性扩展/成本治理/统一安全与质量治理/灾备 |


版本数量是规划基线，不代表必须按固定日历发布。可根据客户价值、团队资源和技术验证结果调整，但不得跳过关键依赖。

## 5. 各版本范围与验收

## 5.1 V1.0 — MVP：Enterprise Knowledge RAG

### 目标
交付一个可以在企业内部真实使用的知识库问答系统，重点是知识可信、权限正确、链路可观测、管理可运营。

### 功能范围
- Chat：登录、会话、流式问答、引用展示、反馈、TraceId 展示。
- Admin：仪表盘、供应商与模型、知识库、链路追踪、后台用户、问答用户、角色、操作审计、配置中心。
- Ingestion：上传、校验、去重、解析、标准化、切片、Embedding、索引、发布、失败重试和删除。
- Parser：Docling 默认，MinerU 作为复杂 PDF 备选适配器。
- Search：Elasticsearch，Dense + BM25 + Hybrid Search + Metadata/ACL Filter + RRF。
- RAG：Query Router 的基础版本、检索、Reranker、Context Assembly、Token Budget、Prompt、生成、Citation Validation。
- Model Gateway：平台 Facade + LiteLLM 底层代理。
- Async：RabbitMQ + Celery；Redis 用于缓存和短期状态。
- 数据：PostgreSQL、S3 Compatible/RustFS。
- Security：登录、RBAC、KB ACL、API Key 加密、敏感操作二次确认。
- Evaluation：P0 最小 Golden Dataset、适用的基础 RAGAS/确定性指标与回归门禁；复杂实验及扩展指标可列 P1。
- Observability：OpenTelemetry + Phoenix，记录 RAG Trace。
- Audit：管理操作审计与技术 Trace 分离。

### 非目标
- 不交付可视化 Agent Builder。
- 不交付多 Agent 协作。
- 不交付通用 Workflow Engine。
- 不接入真实 HR/CRM/ERP 生产系统；仅保留 Mock 和 Contract。
- 不做跨区域灾备和复杂自动扩缩容。
- 不以“支持所有文件格式”为目标，先覆盖明确验收的文件类型。

### V1.0 Exit Criteria
- 文档上传、解析、切片、索引、发布链路可追踪，失败可重试，重复任务具备幂等保护。
- 发布前可验证索引；新版本构建失败不破坏当前可用版本。
- 用户只能检索其有权访问的知识内容；通过越权测试验证服务端 ACL 生效。
- Standard RAG 能输出可验证引用；无证据时按策略拒答或明确说明不确定。
- 上下文 Token Budget 生效，超长对话不会无控制地突破模型上下文限制。
- Trace 能关联检索、重排、Prompt、模型调用、耗时、Token 和错误。
- 管理操作产生不可篡改或受控留存的审计记录，关键变更可查看前后值。
- Golden Dataset 评测结果达到项目评审设定的基线；具体阈值由 POC 确认。
- 备份恢复、删除生命周期、权限边界和关键安全测试通过。
- 部署、配置、升级和回滚有可重复操作文档。

### 进入 V1.1 的前置条件
V1.0 的核心数据模型、身份上下文、Model Gateway、Policy 接口、Trace Schema 和 Retriever API 已稳定；遗留问题有明确风险接受记录。

## 5.2 V1.1 — Agent Platform Foundation

### 目标
从知识问答系统演进为具备 Agent 执行能力的平台底座。重点不是丰富 Agent 产品界面，而是建立安全、可恢复、可观测的运行时。

### 功能范围
- Agent Runtime：基于 LangGraph 的执行适配层、状态模型、Checkpoint、节点执行、超时、重试、取消和错误处理。
- Agent Definition：先采用受控配置/代码注册方式，定义 Agent 的名称、指令、模型、Retriever 和 Tool。
- Tool Gateway：统一 Tool Contract、工具注册、参数 Schema 校验、超时、幂等键、结果标准化。
- Connector Framework：REST、SQL、MCP 的接入适配边界；先实现 Mock 和少量演示 Connector。
- Policy：工具调用前授权、资源范围检查、身份上下文传递和策略决策日志。
- Memory/Context：Conversation Context、任务内短期状态、上下文摘要和 Token Budget 协同。
- Agent Trace：将 Agent Run、Node、Tool Call、Retriever Call 关联到统一 Trace。
- 基础并发治理：按用户、Agent、模型和工具设置并发/速率限制。
- Human Approval 基础接口：高风险工具可暂停并等待外部审批结果，不在本版本建设完整审批中心。

### 非目标
- 不做通用拖拽式 Agent Builder。
- 不做复杂多 Agent Supervisor。
- 不允许 Agent 自主获得任意数据库或网络访问权限。
- 不做无边界的长期用户记忆自动写入。
- 不将 LangGraph Checkpoint 当作平台唯一的业务状态和审计存储。

### V1.1 Exit Criteria
- 至少一个 Agent 能在受控配置下调用 Retriever 和 Mock Tool 完成任务。
- 每次 Agent Run 有可查询状态、执行步骤、输入输出摘要、耗时和错误。
- Tool 调用前执行服务端 Policy Check，越权调用被拒绝并记录。
- Checkpoint 可支持中断后恢复；重试不会导致不可控的重复副作用。
- 超时、取消、模型失败、工具失败和上下文超限均有明确处理路径。
- Agent 与 RAG Engine、Tool Gateway、Model Gateway 通过稳定 Contract 通信。
- 基础并发压测和资源限制测试通过。

## 5.3 V1.2 — Agent Development Platform

### 目标
把 Agent 从“工程师写代码才能运行”升级为“开发者可配置、测试、发布和管理”的平台能力。

### 功能范围
- Agent Registry：Agent 元数据、定义、所有者、权限、状态和版本。
- Agent Configuration：Prompt、Model、Retriever、Tool Binding、参数和运行策略配置。
- Prompt Management：版本、变量、模板校验、变更记录和回滚。
- Tool Catalog：工具说明、输入输出 Schema、权限要求、风险等级和版本。
- Agent Playground：交互式调试、输入变量、运行过程查看、Tool Call 检查。
- Agent Evaluation：测试集、回归测试、轨迹评测、结果对比和发布门禁。
- Lifecycle：Draft、Testing、Published、Deprecated 等状态；发布、回滚和版本锁定。
- RBAC 扩展：Agent 创建、编辑、测试、发布和运行权限。
- Observability：按 Agent、版本、用户授权范围、运行结果和成本分析。
- 环境隔离：开发/测试/生产配置隔离，敏感凭据按环境管理。

### 非目标
- 不将任意 Python 代码直接作为无隔离的用户脚本执行。
- 不在本版本实现复杂 Multi-Agent。
- 不允许发布绕过评测、权限检查和安全策略。
- 不把 Prompt 文本本身当作权限控制机制。

### V1.2 Exit Criteria
- 开发者可在不修改平台核心代码的情况下创建、配置和测试一个 Agent。
- Agent 版本不可变或具有明确版本快照；运行记录可追溯到确切版本。
- Agent 发布前执行 Schema、权限、安全和评测门禁。
- 支持版本回滚，回滚不会丢失历史运行记录。
- 不同角色只能执行授权的 Agent 管理操作。
- 至少完成一个可复用业务示例（例如 HR FAQ Agent），但不得接入未授权真实数据。

## 5.4 V1.3 — Advanced Agentic AI

### 目标
支持复杂问题、多步骤任务和多个专用 Agent 协作，同时保证过程可控、可恢复、可解释。

### 功能范围
- Planner / Executor：任务拆解、步骤依赖、执行计划和结果汇总。
- Advanced RAG：Query Decomposition、Multi-hop Retrieval、跨文档证据整合、检索结果验证。
- Multi-Agent：Supervisor/Coordinator、专用子 Agent、消息和任务交接协议。
- State & Checkpoint：跨步骤状态持久化、恢复、重试、取消和人工接管。
- Human-in-the-loop：关键步骤审批、补充信息、拒绝和恢复。
- Guardrails：工具风险分级、输出约束、Prompt Injection 防御、敏感数据处理和策略拦截。
- 长任务：任务队列、进度状态、超时策略、部分结果和恢复策略。
- Evaluation：多步骤任务成功率、工具选择准确率、证据质量、成本和延迟评估。
- Trace：展示 Agent 间调用关系、父子 Run、计划步骤和工具链路。

### 非目标
- 不让 Agent 对企业核心数据执行不可逆操作而无审批。
- 不允许 Multi-Agent 绕过统一 Tool Gateway 或 Policy Engine。
- 不用模型生成的“计划正确”替代业务规则校验。
- 不将所有简单问答强制路由到 Agentic RAG；简单问题仍优先 Standard RAG。

### V1.3 Exit Criteria
- 复杂任务可拆解为有状态步骤，并可查看计划、执行和最终证据。
- 子 Agent 权限不高于调用者授权范围；身份和权限上下文不可被模型伪造或提升。
- 关键步骤可暂停等待人工决策，并能在决策后恢复。
- 部分步骤失败时按策略重试、回滚或终止，不产生未审计副作用。
- 已经场景与单 Agent 基线评审准入的 Multi-Agent 能力，Trace 能完整关联父子执行链路；若拟延后，须在 M3 开始前以范围 ADR 更新本版验收。
- 在 Golden Task Set 上达到经评审设定的成功率、证据质量、成本和延迟门槛。

## 5.5 V1.4 — Enterprise Workflow & Integration

### 目标
让平台从“能回答、能调用工具”进一步走向“能在企业制度约束下完成真实业务流程”。

详细设计与 Backlog/验收见 [V1.4 开发包](V1.4-Enterprise-Workflow-and-Integration/README.md)。用户已选择工单创建→审批→结果确认；平台申请/草稿与外部写入分开，写入在绑定参数获得审批后执行。真实工单系统、接口及审批制度在 M0 冻结，当前开发包不代表生产验收通过。

### 功能范围
- 生产 Connector：按实际业务优先级接入 HR、CRM、ERP、OA、工单或其他系统。
- Connector Governance：凭据管理、连接健康检查、版本、权限范围、限流、审计和轮换。
- Workflow Engine：确定性流程定义、状态迁移、条件分支、定时器、超时、重试和补偿。
- Approval Center：审批人、审批组、授权委托、超时升级、拒绝和撤回。
- Event Trigger：业务事件触发、Webhook、定时触发和去重。
- Business Actions：在 Policy、审批、参数校验和幂等保护下执行真实业务写操作。
- Long-running Workflow：跨天任务、等待外部事件、恢复和人工介入。
- Workflow Audit：记录流程实例、步骤、决策、审批和业务系统响应。
- Agent + Workflow 协作：Agent 负责理解、建议和非确定性判断；Workflow 负责规则化执行和状态推进。

### 非目标
- 不把企业核心审批规则全部交给 LLM 决定。
- 不把外部系统的权限视为平台权限的替代品；仍需平台侧授权和审计。
- 不承诺一次性覆盖所有企业系统；按业务价值和接入成本排序。
- 不允许工具重试造成重复付款、重复建单等副作用；必须有幂等和补偿设计。

### V1.4 Exit Criteria
- 至少一个真实业务流程端到端完成，覆盖身份、权限、审批、执行、结果确认和审计。
- 所有写操作有调用者身份、策略决策、审批凭证、幂等键和外部响应记录。
- 外部系统故障、超时、重复事件和部分成功有明确恢复/补偿方案。
- Workflow 状态机可恢复，关键操作可人工介入。
- 生产 Connector 有凭据轮换、健康检查、限流和故障告警。
- 业务负责人确认流程结果符合制度要求，安全/审计负责人完成验收。

## 5.6 V2.0 — Enterprise-Grade Platform

### 目标
将平台提升为可供多个部门、团队和业务场景长期运行的企业级基础设施，重点解决规模、安全、治理、运营和韧性。

详细设计、Backlog 与验收见 [V2.0 开发包](V2.0-Enterprise-Grade-Platform/README.md)。所有版本按单一企业内部部署交付，保留企业内部身份/角色/资源权限。SLO、容量、RPO/RTO 和价格/制度依真实证据冻结。

### 功能范围
- Enterprise Authorization：企业内组织/部门/Workspace 成员与资源 ACL，复用可信身份和 Policy。
- 高可用：关键服务多实例、无状态扩展、队列可靠性、数据库高可用和故障隔离。
- 弹性伸缩：按任务队列、模型并发、工具调用和检索负载扩缩容。
- Model Routing：按质量、成本、延迟、上下文窗口、区域和任务类型路由。
- Cost Management：Token/模型/Agent/部门成本归集、预算、配额、告警和成本优化。
- Enterprise Security：密钥轮换、网络隔离、数据分级、保留策略、合规报表和安全事件响应。
- Agent Governance：Agent 风险等级、发布审批、权限审查、版本治理和退役。
- Evaluation Governance：统一测试集管理、质量门禁、线上反馈、漂移监控和回归分析。
- Observability：平台 SLO、容量、队列积压、模型供应商质量、Agent/Workflow 运行质量。
- DR：备份、恢复演练、RPO/RTO 目标和跨区域恢复策略（如业务要求）。
- Admin Operations：企业运营、资源配额、策略管理、运维审计和平台健康管理。

### 非目标
- V2.0 不意味着所有企业功能一次性完成；仍需按用户与业务规模、合规要求和业务 SLA 分阶段实施。
- 不为了微服务化而拆分；拆分必须有明确的独立扩缩容、团队所有权或故障隔离理由。
- 不宣称满足某项合规认证，除非完成正式评估和审计。

### V2.0 Exit Criteria
- 企业内授权测试覆盖跨用户/角色/KB/Workspace 的读写、检索、缓存、对象、工具、费用与审计访问，未授权请求失败。
- 关键服务达到经业务确认的可用性、延迟和容量目标。
- 完成压力、故障注入、恢复和灾备演练。
- 模型/Agent/Workflow 的预算、配额和成本归集可用。
- Agent、Tool、Connector、Workflow 有统一治理和审计。
- 质量评测贯穿开发、发布和线上运行，异常可告警并触发治理动作。
- 安全、运维、业务和平台负责人共同签署生产验收。

### 7.2 不应颠倒的依赖

- 没有统一身份与策略上下文，不应开放 Agent Tool 的生产访问。
- 没有 Tool Contract、幂等和审计，不应开放有副作用的业务写操作。
- 没有 Agent 版本快照和评测门禁，不应规模化发布 Agent。
- 没有稳定的状态持久化、Checkpoint 和恢复机制，不应承接长任务。
- 没有审批与补偿机制，不应自动化高风险企业流程。

- V1.1 Runtime 与 Tool Contract 设计；

- V1.3 评测数据集建设与复杂任务场景调研；

- V2.0 容量、SLO、安全和企业内部权限需求调研。

## 8. 核心 Contract 与数据模型演进策略

### 8.1 平台自有 Contract

以下 Contract 应由平台定义和版本化，不能直接暴露底层框架对象：

- `ModelCallRequest/Response`
- `RetrieverRequest/Response`
- `Document/Chunk/KnowledgeBase`
- `IngestionJob/IndexVersion`
- `AgentDefinition/AgentRun/AgentStep`
- `ToolDefinition/ToolCall/ToolResult`
- `ConnectorDefinition/Connection`
- `PolicyContext/PolicyDecision`
- `Conversation/Message/MemoryItem`
- `WorkflowDefinition/WorkflowInstance`（后续流程契约）与 `ApprovalRequest/ApprovalDecision`（前序最小暂停/决定协议）分别演进
- `TraceEvent/AuditEvent`
- `EvaluationDataset/EvaluationRun/EvaluationResult`

### 8.2 Contract 兼容原则

1. 新增字段优先采用可选字段，避免破坏旧客户端。
2. 删除或改变字段语义必须经过版本升级和迁移计划。
3. API 对外版本化；内部模块接口也应有兼容测试。
4. 枚举值新增时，消费者必须能处理未知值或明确拒绝。
5. 不把 LangGraph State、LlamaIndex Node 等框架内部结构作为长期公共 API。
6. 关键事件采用 Schema Version，支持历史事件读取。
7. 数据库迁移采用 Expand-Migrate-Contract：
   - Expand：先新增字段/表，保持旧逻辑可运行；
   - Migrate：双读/双写或批量迁移并校验；
   - Contract：确认所有消费者迁移后再删除旧结构。
8. 对外 API、事件和持久化结构分别管理版本，不能把三者混成一个版本号。

### 8.3 关键数据对象建议

| 对象 | V1.0 最低要求 | 后续扩展 |
|---|---|---|
| User / Identity | 用户、角色、登录来源、状态 | 服务身份、委托身份 |
| KnowledgeBase | 所有者、ACL、状态、配置 | 部门归属、策略标签 |
| Document | 来源、Hash、解析状态、版本 | Connector Source、保留策略、血缘 |
| Chunk | 内容、元数据、ACL 继承、索引版本 | 多模态片段、结构关系、细粒度策略 |
| Conversation / Message | 会话、消息、用户归属、删除状态 | Agent 会话、记忆引用、授权范围 |
| Model / Provider | 供应商、模型、配置、密钥引用 | 路由策略、配额、成本和区域 |
| Trace | TraceId、匿名运行信息、阶段耗时 | Agent/Workflow 父子链路、资源授权维度 |
| AuditEvent | 操作者、对象、动作、结果、变更前后 | Tool/Approval/Workflow 业务审计 |
| AgentDefinition | 预留版本化边界 | Prompt、Tool Binding、发布状态 |
| AgentRun | 预留运行关联边界 | State、Checkpoint、预算、父子 Run |
| ToolDefinition | Mock Contract/Schema | 权限、风险等级、幂等和版本 |
| WorkflowInstance | 暂不完整实现 | 状态、审批、补偿和事件 |

### 8.4 单企业部署与内部权限原则

依据已确认的 [ADR-0013](../adr/0013-single-enterprise-deployment-scope.md)，所有版本采用单一企业内部部署。资源保留稳定 ID、Owner、可信父子关系、用户/角色/KB ACL，Organization/Workspace 仅用于本企业组织协作。

服务端授权覆盖检索、缓存、对象、队列、工具、评测、观测和管理动作；部署 namespace 区分环境。后续版本增量升级按兼容窗口与存量校验执行，具体规则见 [统一契约](../architecture/统一契约与跨版本演进规则.md) 第 2/11 节。

## 9. 技术选型基线与变更规则

### 9.1 当前技术基线

| 领域 | 当前基线 | 职责与边界 |
|---|---|---|
| Backend | Python + FastAPI | API 与业务模块 |
| Frontend | Vite + React + TypeScript | Chat/Admin 两个独立应用，共用后端 API |
| RAG Framework | LlamaIndex | Ingestion/Retriever/Query 组件适配 |
| Agent Runtime | LangGraph | Agent 状态化执行 |
| Parser | Docling 默认；MinerU 备选 | 统一 Parser Adapter |
| Search | Elasticsearch 默认；OpenSearch 候选 | Search Adapter 隔离 |
| Model Proxy | 自研 Model Gateway Facade + LiteLLM | 平台治理与底层供应商适配 |
| Async | RabbitMQ + Celery | 异步任务 |
| Cache | Redis | 缓存和短期状态 |
| Business DB | PostgreSQL | 平台业务数据 |
| Object Storage | S3 Compatible / RustFS | 原件和解析产物 |
| Observability | OpenTelemetry + Phoenix | Trace/观测 |
| Evaluation | RAGAS + Golden Dataset | RAG/Agent 质量评测 |
| Dependency | uv + pnpm workspace | Python 依赖与前端应用/公共包分别管理 |
| Runtime | Docker | 容器化交付 |

工程组织采用已确认的 [ADR-0014](../adr/0014-monorepo-and-independent-frontend-apps.md)：同一 Monorepo 管理前后端及基础设施，两个前端应用独立构建/部署，通过公共包复用组件、API 客户端与工具。详细目录以 V1.0 代码结构文档为初始化依据。

### 9.2 选型治理原则

- 以上是当前项目基线，不代表已经全部完成 POC 验证。
- POC 的目的在于验证基线是否满足明确的硬性需求，而不是无限重开选型。
- 只有在性能、功能、许可、稳定性、运维或成本等硬性要求无法满足时，才提交 ADR 讨论替换。
- 所有框架通过 Adapter/Facade 接入；平台业务模型和核心 Contract 不依赖框架私有对象。
- 不在 MVP 同时引入多个同类技术栈，除非存在明确的业务或验证理由。

### 9.3 ADR 变更流程

每个技术变更 ADR 至少包含：
1. 问题和触发原因；
2. 当前基线及其不满足项；
3. 可选方案与评估维度；
4. POC 设计、数据和测试结果；
5. 对 API、数据模型、运维、团队能力和成本的影响；
6. 迁移、回滚和兼容方案；
7. 决策人、决策日期和复审条件。

## 10. 研发阶段与版本交付治理

每个版本统一采用以下交付节奏，可按团队规模调整迭代长度：

1. **需求与场景确认**：明确用户、业务价值、边界和非目标。
2. **架构评审**：检查依赖、Contract、权限、数据生命周期和可观测性。
3. **技术验证 / POC**：验证高风险依赖，不以演示成功代替验收。
4. **详细设计**：API、数据模型、状态机、异常路径和安全策略。
5. **研发实现**：按模块拆分任务，建立自动化测试。
6. **集成测试**：覆盖跨模块、权限、失败恢复和兼容。
7. **质量评测**：Golden Dataset、回归、压测和安全测试。
8. **灰度发布**：限制用户、流量或功能开关，观察指标。
9. **版本验收**：产品、研发、安全、运维和业务代表签署。
10. **复盘与下一版本规划**：更新 ADR、风险台账和路线图。

### 10.1 每版本必须提交的交付物

- 版本需求与范围说明（包含明确的非目标）；
- 架构设计与必要 ADR；
- API / Event / Data Schema 变更说明；
- 数据库迁移脚本和回滚方案；
- 自动化测试与测试报告；
- 安全与权限测试报告；
- Evaluation 报告（适用时）；
- 压测和容量报告（适用时）；
- Trace、Dashboard、告警配置；
- 部署、升级、回滚和故障处理手册；
- 已知问题、风险接受记录和后续 Backlog。

### 10.2 版本准入与退出治理

版本开始前：
- 上游版本的关键 Exit Criteria 已通过，或遗留风险已由负责人书面接受。
- 依赖模块提供稳定接口和测试环境。
- 高风险技术点有 POC 计划。
- 数据迁移和安全影响已评审。

版本结束前：
- 需求完成不等于版本完成；必须完成验收、回归、安全、可观测和运维交付。
- 所有 P0/P1 缺陷关闭，或有明确风险接受、缓解措施和责任人。
- 不允许通过关闭权限校验、审计或质量门禁来换取进度。
- 发布失败必须可回滚；数据迁移必须有验证和恢复方案。

## 11. 非功能目标与验证策略

| 维度 | V1.0 | V1.1–V1.3 | V1.4–V2.0 |
|---|---|---|---|
| 性能 | RAG 首 Token/总耗时基线 | Agent/Tool 额外开销与长任务 | 业务流程端到端时延与容量 |

| 可靠性 | 异步重试、索引发布回滚 | Checkpoint、取消、恢复 | Workflow 补偿、HA、DR |
| 安全 | RBAC、KB ACL、Key 加密 | Tool/Agent Policy、注入防御 | 业务写操作审批、企业资源授权 |
| 可观测 | RAG Trace、审计 | Agent/Tool Trace | Workflow Trace、SLO、成本 |
| 质量 | Golden RAG Dataset | Agent Task Evaluation | Multi-Agent/Workflow 质量治理 |
| 生命周期 | 文档/会话删除规则 | Memory/Run 生命周期 | 企业数据保留与合规治理 |

### 11.1 性能验证必须区分的指标

- API 请求延迟与模型首 Token 延迟；
- 首 Token（TTFT）与完整回答时间；
- 检索、重排、上下文组装、模型生成各阶段耗时；
- 入库吞吐、解析耗时、Embedding 吞吐和索引发布耗时；
- 并发请求数、队列积压、失败率和重试率；
- Agent 每次 Run 的模型调用次数、Tool 调用次数、Token 和总耗时；
- Workflow 端到端成功率、等待时间和补偿成功率。

## 12. 安全、隐私与数据生命周期的跨版本要求

安全和隐私不是 V2.0 才建设的功能。每个版本都必须遵守：

- 服务端强制授权；不得把前端隐藏、Prompt 指令或模型自我约束作为安全边界。
- Agent、Tool、Connector 使用可信身份上下文，禁止权限提升。
- API Key、Connector Secret 加密存储，展示时掩码；访问和轮换有审计。
- Prompt Injection、恶意文档、工具参数污染和输出泄露纳入安全测试。
- 用户会话、记忆、技术 Trace、身份映射和业务审计分开管理，分别定义保留与删除规则。
- 个人数据删除不能误删依法或按制度必须保留的审计记录；审计留存也不能成为无限保留会话正文的借口。
- 删除必须覆盖原件、解析产物、Chunk、索引、缓存、记忆和相关派生数据，并记录删除任务结果。
- 高危溯源和高风险业务操作必须具备理由、授权、二次确认（按风险等级）和审计。
- 企业内部授权边界覆盖数据、检索、缓存、对象存储、队列、工具和观测数据。

## 13. 主要风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| MVP 范围膨胀 | 延期、质量下降 | 锁定 V1.0 非目标；后续能力进入路线图 |
| 框架耦合 | 后续难替换、升级成本高 | 自有 Contract、Adapter、框架对象不外泄 |
| ACL 设计不足 | 越权检索或工具调用 | 服务端统一 Policy、负向测试、结果复核 |
| Agent 不可控 | 错误调用、循环、成本失控 | Tool Allowlist、预算、超时、最大步数、审批 |
| 长任务状态丢失 | 重复执行或任务无法恢复 | Checkpoint、幂等键、状态机和恢复测试 |
| 外部系统副作用 | 重复建单/重复操作 | 幂等、审批、补偿、外部响应对账 |
| 评测集质量差 | 指标虚高、线上效果差 | 业务专家审阅、版本化 Golden Set、线上反馈 |
| 上下文无限增长 | 超限、延迟和成本增加 | Token Budget、摘要、检索式记忆和生命周期 |
| 观测与隐私冲突 | 过度暴露个人信息 | Trace 匿名化、身份映射隔离、高危溯源审计 |
| 微服务过早拆分 | 运维复杂、开发效率低 | 模块化单体起步，基于指标和组织边界拆分 |
| 模型供应商变化 | 业务接口频繁改动 | Model Gateway Facade、模型能力声明和回归评测 |

## 14. 架构拆分与部署演进原则

### V1.0–V1.2
- 以模块化单体为主，异步 Worker 独立部署。
- 允许 API、Worker、Scheduler 等进程分开部署，但共享清晰领域模块和 Contract。
- 优先解决模块边界、数据一致性、任务可靠性和测试隔离。

### V1.3–V1.4
- 根据 Agent Run、Tool Gateway、Workflow 的负载和故障隔离需求，评估独立部署。
- 对需要独立扩缩容的执行 Worker、Connector Worker、Workflow Worker 可先拆部署单元，不必立即拆成大量微服务。
- 明确事件、重试、幂等、超时和服务间鉴权。

### V2.0
- 只有在团队所有权、独立扩缩容、SLO 或故障域要求明确时，才拆分为独立服务。
- 服务拆分必须包含数据归属、API Contract、部署、监控、故障处理和迁移计划。
- 避免分布式事务；优先采用 Outbox、Saga、幂等消费者和补偿模式。

## 15. 发布、迁移与向后兼容策略

- 每个版本发布前生成版本清单，列出 API、数据库、索引、Prompt、模型配置和 Agent Definition 的变化。
- 数据库迁移采用可重复执行、可观测、可验证的迁移脚本。
- Elasticsearch 索引结构变化优先采用新索引版本构建、验证、原子切换和旧版本保留窗口。
- Embedding 模型或维度变化必须触发重新 Embedding 和索引版本发布，不允许混用不兼容向量。
- Prompt、Agent Definition、Tool Schema 和 Workflow Definition 均应版本化。
- 任务执行时绑定确定的 Agent/Tool/Prompt/Model 配置快照，避免运行中配置变化导致不可复现。
- 发布采用灰度或功能开关；发现问题可回滚应用版本或切回旧索引/配置版本。
- 对不可逆数据迁移，必须先备份、验证迁移结果并准备补偿方案。
- 对旧 API/Contract 的废弃应经过公告、迁移窗口、调用方盘点和兼容测试。

## 16. 项目治理与决策机制

### 16.1 角色建议

| 角色 | 主要责任 |
|---|---|
| Product Owner | 版本目标、业务价值、范围优先级和验收 |
| Platform Architect / CTO | 总体架构、边界、技术基线和 ADR |
| Backend Lead | API、数据模型、RAG、Runtime、Tool 和 Workflow 实现 |
| Frontend Lead | Chat/Admin 体验与权限交互 |
| AI/RAG Engineer | 检索、评测、Prompt、模型效果和成本优化 |
| Security/Compliance Owner | 身份、权限、数据生命周期、安全评审 |
| QA / Evaluation Owner | 自动化测试、Golden Dataset、回归和质量门禁 |
| DevOps / SRE | 部署、监控、容量、备份、恢复和故障响应 |
| Business System Owner | 真实 Connector、业务规则和流程验收 |

小团队可以由同一人承担多个角色，但责任必须明确到人。

### 16.2 需要 ADR 管理的事项

- Search Engine 从 Elasticsearch 切换到 OpenSearch 或其他方案；
- Parser 默认实现变化；
- LlamaIndex 或 LangGraph 重大版本升级及适配策略；
- Model Gateway/LiteLLM 职责变化；
- 新增 Workflow Engine 或替换实现；
- 核心 Contract 破坏性变更；
- 服务拆分、数据库拆分和事件架构变化；
- 身份、权限、数据保留和删除规则变化。

### 16.3 架构评审检查清单

每个版本评审至少回答：
- 是否破坏既定模块边界？
- 是否出现绕过 Model/Tool/Search Gateway 的直接调用？
- 是否在服务端执行权限检查？
- 是否有超时、重试、幂等、取消和恢复设计？
- 是否记录必要 Trace 和 Audit？
- 是否定义数据保留、删除和敏感信息处理？
- 是否有自动化测试和负向安全测试？
- 是否有迁移、灰度、回滚和兼容方案？
- 是否引入了没有明确价值的基础设施或微服务？
- 是否为下一版本提供了稳定 Contract，而不是提前实现全部功能？

## 17. 建议的版本优先级与取舍

在资源有限时，建议按以下顺序投入：

1. **先保证 V1.0 的可信性**：知识权限、索引正确性、引用可信、删除闭环、可观测和可运营优先于花哨交互。
2. **再建设 V1.1 的执行安全底座**：Agent 能力的核心不是“会调用工具”，而是身份、权限、状态、预算、恢复和审计。
3. **再建设 V1.2 的开发者生产力**：当 Runtime 稳定后，才让开发者自助配置、测试和发布。
4. **随后建设 V1.3 的复杂智能能力**：先完成单 Agent Planner 和 Agentic RAG；M0 确定真实协作场景与单 Agent 基线，M3 前比较质量、成本和延迟。收益未证实则由产品/架构通过范围 ADR 决定是否延后，并同步交付清单；不能仅按版本号触发 Multi-Agent 实现。
5. **再进入 V1.4 的真实业务执行**：先读后写、先低风险后高风险；写操作必须有审批、幂等和补偿。
6. **最后完成 V2.0 规模化治理**：基于实际用户/业务负载、容量、SLO 和合规需求投资，而不是提前堆叠基础设施。

如果业务场景暂时不需要 Multi-Agent，可以延后 V1.3 的部分能力；如果真实业务集成价值更高，也可以在单 Agent Runtime 和 Tool Policy 稳定后优先推进少量 V1.4 试点，但不得跳过安全、审批和审计依赖。

## 18. 最终目标态验收定义

当平台达到 V2.0 目标态，应同时满足以下条件：

- 员工通过 Chat 使用知识问答、Agent、任务和审批能力。
- 开发者通过 Admin 自助创建、调试、评测、发布和治理 Agent。
- Standard RAG、Agentic RAG 和实时 Tool 查询按请求意图合理路由。
- Agent Runtime 与 Workflow Engine 分工清晰，可协作但不混淆。
- 企业工具和 Connector 通过统一 Gateway、Contract、Policy 和 Audit 管理。
- 身份权限贯穿用户、Agent、Tool、Connector、Workflow 和数据资源。
- Memory、Conversation、Task State、Trace 和 Audit 有独立的数据模型与生命周期。
- 模型、Agent、RAG、Tool 和 Workflow 有统一评测与发布门禁。
- 平台具备经验证的容量、可用性、故障恢复、成本和安全治理能力。
- 所有关键变更、运行和业务副作用可追踪、可审计、可恢复或可解释。

**文档结论：**以 V1.0 建立可信的企业知识底座，以 V1.1–V1.2 建立可治理、可开发的 Agent 平台，以 V1.3–V1.4 扩展复杂智能与真实业务执行能力，最终在 V2.0 完成企业级规模化治理。始终坚持“先定义总架构边界，再按版本实现能力；先权限与可靠性，再扩大 Agent 自主性；先验证业务价值，再增加系统复杂度”。
